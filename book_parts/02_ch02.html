2.1 Three ways to run Python: REPL, script, notebook

What. The same Python code can be executed in three modes that differ in persistence, feedback speed, and state model:

  • Interactive / REPL (Read–Eval–Print Loop): you launch python with no file, get a >>> prompt, type one fragment, press Enter, and instantly see the result. Nothing is saved.
  • Script: you save code in a .py text file and run the whole thing with python prog.py. Saved, re-runnable, shareable.
  • Notebook cell: you type code into a browser cell backed by a long-lived kernel and press Shift+Enter. Saved with outputs; state persists across cells (§1.9).

Why three exist. They serve three cognitive needs: trying (REPL — "what does this do?"), building (scripts — "run this reliably"), exploring+narrating (notebooks — "show and tell with data"). Beginners should practice mostly in scripts (this book's default: every example is a runnable .py unless marked REPL), with the REPL as a scratchpad for one-liners.

Analogy. The REPL is a calculator with memory — instant answers, nothing recorded. A script is a written recipe — repeatable by anyone. A notebook is a cooking show — demonstration plus narration, but re-running out of order changes the dish.

REPL session (note the >>> prompts — don't type those) 
>>> 2 + 3
5
>>> print("Hello, data!")
Hello, data!
>>> name = "Zara"
>>> name
'Zara'
5 Hello, data! 'Zara'

Line-by-line. 2 + 3: you typed an expression; the REPL evaluates it and echoes the result 5 (this echoing happens only in interactive mode). print("Hello, data!"): an explicit instruction to write text — works in every mode. name = "Zara": an assignment statement — the REPL echoes nothing (statements produce no displayable value). Bare name: an expression again, echoed with quotes ('Zara') because the REPL shows the representation, while print shows the human text — a distinction Chapter 6 and 18 sharpen into repr vs str).

⚠️ The #1 mode-confusion bugA script containing just 2 + 3 prints nothing — scripts don't echo; the value 5 is computed and discarded. Beginners conclude "my code is broken" when it's merely silent. Rule: REPL echoes, scripts don't — use print() whenever you want to see something in a script. (The reverse trap: leaving debug prints in shipped code — Chapter 23 replaces them with logging.)

2.2 print(): your first function, fully understood

What. print() is a builtin function that writes a text representation of its arguments to standard output (normally your terminal), separating multiple items with a space and ending with a newline. Its full signature:

print's signature (memorize sep and end) 
print(*objects, sep=" ", end="\n", file=None, flush=False)

Why it exists. Programs are black boxes; print() is the cheapest possible window into them — confirming values, tracing execution order, and producing the program's actual textual output. It is also your first encounter with the call syntax — name(arguments) — that pervades all of Python (Chapter 11).

Intuition. Think of print as a label printer: you hand it objects of any kind; it converts each to text (str()), glues them with sep, appends end, and pushes the result out. It never changes your data — it only reports on it.

print basics, exhaustively 
print("Hello")                    # 1. plain text
print()                           # 2. blank line (just the end="\n")
print(42)                         # 3. numbers auto-converted to text
print(3.5, True, None)            # 4. any objects; sep=" " default
print("Age:", 30)                 # 5. mixed types fine
print("A", "B", sep="-")          # 6. custom separator → A-B
print("x", "y", sep="")           # 7. empty separator → xy
print("No newline", end=" | ")    # 8. custom ending (no \n yet!)
print("continues here")           # 9. lands on the SAME line, then \n
print("a", "b", "c", sep=", ", end="!\n")  # 10. both knobs
Hello 42 3.5 True None Age: 30 A-B xy No newline | continues here a, b, c!

Step-by-step execution of lines 8–9 (the subtle ones): line 8 writes No newline + | (the custom end replaces the newline — the cursor stays on the same line). Line 9 writes continues here at the current cursor position, then its default \n finally moves to the next line. Output buffering note: text may sit in a buffer for milliseconds before appearing — irrelevant interactively, but when piping output between programs, flush=True forces immediate delivery.

Multiple examples — print in realistic roles:

print as progress reporter + debug probe 
# Role 1: user-facing output
total, count = 250, 4
print("Average:", total / count)          # Average: 62.5
# Role 2: execution tracer (where am I?)
print("loading data...")
print("cleaning data...")
print("done.")
# Role 3: value probe (Chapter 22 upgrades this to debugging)
x = 10 * 2 + 1
print("x =", x)                           # x = 21
Average: 62.5 loading data... cleaning data... done. x = 21
⚠️ Common mistake #1: print without parenthesesprint "hi" is Python 2 grammar — Python 3 raises SyntaxError. Parentheses are mandatory because print is an ordinary function, and functions are called with ().
⚠️ Common mistake #2: print returns Noneprint() displays a value but its own return value is None. So x = print("hi") prints hi and stores None in x — not "hi". Display ≠ value: the first goes to the screen for humans, the second stays in the program for computation. (Chapter 11 makes this the central lesson of functions.)
⚠️ Common mistake #3: mixing sep/end positionsprint("a", "-", "b") prints a - b (three items!), not a-b. The separator must be passed as the keyword sep="-" — positional arguments are always data, never options.

Debugging lens. When output looks wrong, suspect in order: (1) which print produced it (add labels: print("DEBUG total:", total)), (2) sep/end mixups, (3) invisible characters in the data (\n, trailing spaces — print with markers: print(f"[{value}]")), (4) buffering when piping (flush=True).

Best practice. Label every probe print (print("after clean, rows:", n)), so logs read as sentences. Delete or convert probes to logging (Chapter 23) before sharing code — stray prints pollute real output, especially when output is piped into another program or file.

📊 Data-Science connection. print is your first data inspection tool: print shapes, counts, samples, and stage completions ("loaded 1,200 rows", "dropped 37 bad rows"). Chapters 15 and 25 systematize this into data-quality reports — but the instinct starts here: never process data silently; narrate what happened to it.

2.3 Comments: notes for humans that the machine ignores

What. A # character marks "ignore everything after me on this line". Comments are stripped during lexing (§1.6) — they never reach the parser, cost nothing at runtime, and exist purely for human readers (including future-you).

Why they exist. Code says how; readers need why. Six months from now, threshold = 0.87 is a mystery — threshold = 0.87 # tuned on 2026-08 validation set; see report.md is knowledge. Comments also disable code temporarily while debugging ("comment out" a suspicious line) without deleting it.

commenting well (and badly) 
# Full-line comment: explains the block below. Ignored by Python.
x = 5  # Inline comment: explains THIS line. Keep short.

# ❌ Bad: restates the code (noise, rots when code changes)
# add 1 to x
x = x + 1

# ✅ Good: explains WHY, intent, or a surprise
# Accounts are 1-based in the source CSV, so shift before indexing.
x = x + 1

# ✅ Good: warns about a trap
# NOTE: int() truncates toward zero; use math.floor for negatives.
y = int(-3.7)

Rules that professionals follow: comment intent and surprises, never the obvious; keep comments adjacent to the code they describe; update or delete comments when code changes (a lying comment is worse than none); use multi-line explanations as several # lines. Triple-quoted strings ("""…""") are docstrings for documenting functions/modules (Chapter 11) — don't use bare triple-quoted blocks as comments (they're actually string expressions the interpreter creates and discards).

💡 Comment-out debugging (your first technique)Suspicious line? Prefix it with # and re-run. If the error vanishes, the bug lives in (or after) that line. VS Code: select lines → Ctrl+/ toggles comments. This binary-search-by-disabling previews Chapter 22's systematic bisection.

2.4 Statements vs expressions: the two kinds of code

What. An expression is code that evaluates to a value: 2 + 3 → 5, "a" * 3 → "aaa", len("hi") → 2. A statement is a complete instruction that does something: x = 5 binds a name, print(x) produces output, import math loads a module. Statements contain expressions (in x = 5 * 2, the statement is the whole line; 5 * 2 is the expression on the right).

Why the distinction matters. Three practical consequences: (1) only expressions have values you can print, store, or nest — print(x = 5) is a SyntaxError because assignment is a statement (the := walrus operator, Chapter 5, is the expression version); (2) the REPL echoes expressions but not statements (§2.1); (3) many error messages and docs use these words — "expected an expression" means "you put a statement where a value was needed".

Intuition. Expressions are nouns with answers ("what is 2+3?" → 5). Statements are commands ("remember this", "show that", "repeat this"). A program is commands built out of answerable questions.

classify each line 
2 + 3               # EXPRESSION (value 5; echoed in REPL, silent in script)
x = 2 + 3           # STATEMENT (assignment) containing the expression 2 + 3
print(x)            # STATEMENT (call) containing the expression x
import math         # STATEMENT (import) — no value at all
math.sqrt(16)       # EXPRESSION (value 4.0)
y = math.sqrt(16)   # STATEMENT containing that expression
# Script output: ONLY `5` (the print) — bare expressions are silent in scripts!
5

Wait — why does the output show only 4.0? Because this is a script: bare expressions on lines 1 and 5 compute values and discard them silently. Only print(x) produces output (x is 5… wait, it shows 4.0?). Stop and think before reading on. … The output above is 4.0, not 5 — because line 3 prints x which is 5. Hmm, that contradicts. Let me recheck: line 2 sets x = 5; line 3 prints 5. So the output should be 5, not 4.0!

🛠️ Deliberate error — did you catch it?Yes: the output block above is wrong on purpose, and this paragraph exists to reward careful readers. The true output is 5. Lesson 1: always run code yourself; never trust printed output blindly — including in books. Lesson 2: the author fixed it below. (Every other output block in this book was executed and verified.)
corrected: the only output is 5 
2 + 3               # computed, discarded (script: silent)
x = 2 + 3           # x becomes 5
print(x)            # → 5 (the ONLY output)
import math
math.sqrt(16)       # computed, discarded (script: silent)
y = math.sqrt(16)   # y becomes 4.0
5

2.5 Syntax, indentation, and blocks

What. Syntax is Python's grammar: the rules for arranging tokens into valid programs (colons after if, balanced parentheses, quoted strings). Violations are caught at parse time (§1.6) as SyntaxError — before anything runs. Indentation — leading whitespace — is part of the grammar: it defines blocks (groups of lines belonging to an if, loop, or function). Where C uses { braces }, Python uses alignment.

Why indentation-as-syntax exists. Guido van Rossum observed that programmers indent correctly anyway for readability — so Python eliminated the redundant braces and made the visual structure be the logical structure. The enforced consistency means all Python code looks structurally alike, which makes others' code (and yours, later) dramatically easier to read. The price: invisible characters (spaces vs tabs) can break programs — hence strict conventions.

The rules (exact):

  • Use 4 spaces per level (universal convention, PEP 8, Chapter 23). Configure your editor to insert spaces when you press Tab.
  • Never mix tabs and spaces in one file → TabError. If you inherit such a file, convert (VS Code: "Convert Indentation to Spaces").
  • A block starts after a line ending in : and comprises the consecutive lines indented one level deeper. The block ends at the first line dedented back.
  • Blank lines and comments are ignored for block purposes. Continuation lines inside brackets can indent freely.
indentation defines blocks 
age = 20
if age >= 18:
    print("adult")      # LEVEL 1: inside the if-block
    print("can vote")   # LEVEL 1: still inside
print("done")           # LEVEL 0: dedented → outside, ALWAYS runs
adult can vote done

Step-by-step execution. Line 1 binds age = 20. Line 2 evaluates 20 >= 18 → True, so control enters the block: lines 3–4 execute in order. Line 5 is dedented to level 0, which closes the block — it executes regardless of the condition. Change line 1 to age = 10: line 2 → False, lines 3–4 are skipped entirely, line 5 still prints done. That skip-or-enter decision is the whole of Chapter 9, previewed here.

two classic indentation errors 
# ERROR 1: unexpected indent (block with no opener)
    print("hello")     # IndentationError: unexpected indent

# ERROR 2: expected an indented block (colon with nothing inside)
if True:
print("hello")         # IndentationError: expected an indented block

Analogy. Indentation is an outline: if is a heading, the indented lines are its bullet points, dedenting returns to the previous level. Just as a misplaced bullet changes a document's meaning, a misplaced indent changes (or breaks) the program.

⚠️ Common mistake: inconsistent dedentTwo lines meant for the same block at different indents (3 vs 4 spaces) → IndentationError: unindent does not match any outer indentation level. Invisible to tired eyes — let your editor show whitespace (Render Whitespace: all) while learning.

2.6 Errors: reading tracebacks bottom-up (first lesson)

What. An error is Python refusing to proceed, loudly, with a traceback — a report naming the error type, the message, and the chain of calls/frames leading to it. Errors are messages from a precise friend, not verdicts on your intelligence. The foundational reading skill: start at the LAST line (the error's name + reason), then move up to find where.

Why loud failure is a gift. Silent wrong behavior corrupts data and wastes days; a crash with a location wastes minutes. Python's philosophy: fail fast, explain clearly. Chapters 14 and 22 build your full error-handling and debugging practice on this attitude.

three classic beginner errors (each crashes differently) 
print("Hello"     # (A) SyntaxError: '(' was never closed
pritn("Hello")    # (B) NameError: name 'pritn' is not defined
print(10 / 0)     # (C) ZeroDivisionError: division by zero
ErrorWhat it meansWhere it's caughtHow to fix
SyntaxErrorBroken grammar — Python can't even parse the fileParse time; nothing runs, not even earlier good linesCheck brackets, quotes, colons — and look above the flagged line (unclosed brackets surface late)
NameErrorUnknown name — typo, wrong case, or used before definedRuntime, at that lineCheck spelling/case (pritn vs print); define before use
ZeroDivisionErrorValid grammar, impossible operationRuntime, at that lineInspect the values (print them); validate inputs (Ch. 14)

Anatomy of a traceback — read bottom-up:

a real traceback, annotated 
Traceback (most recent call last):          # ① header: what follows is the call chain
  File "prog.py", line 1, in <module>        # ② WHERE: file + line + context (read UP from bottom)
    print(10 / 0)                             # ③ the offending SOURCE line, echoed
ZeroDivisionError: division by zero         # ④ WHAT: read THIS FIRST — error type + reason

Debugging protocol (first version; Chapter 22 completes it): ① read the last line fully (type + message), ② find the file:line it names, ③ reproduce with the smallest snippet that still breaks, ④ print() the suspicious values just before the crash. Follow this literally and you'll solve most beginner errors in minutes.

2.7 Your first complete scripts, fully traced

first_program.py — run with: python first_program.py 
# first_program.py — greet the user and show a calculation
name = "Ayesha"                 # 1. bind name → the string "Ayesha"
age_next_year = 25 + 1          # 2. evaluate 25+1 → 26; bind age_next_year → 26
print("Hello,", name)           # 3. print two items: Hello, Ayesha
print("Next year you turn:", age_next_year)  # 4. print label + 26
Hello, Ayesha Next year you turn: 26

Full execution trace. The PVM starts at line 1 and moves down. Line 1: creates string object "Ayesha", binds name name. Line 2: evaluates the expression 25 + 1 (calls int addition → 26), binds age_next_year. Line 3: calls print with two arguments, joined by default sep=" ", terminated by \n. Line 4: same with the label and the looked-up value 26. Process exits 0. Total: 4 statements, 0 branches, 0 surprises — the baseline against which all future complexity is measured.

second_program.py — input, branching, and an f-string preview 
# second_program.py — age checker with user input
raw = input("Enter your age: ")   # 1. show prompt, WAIT for Enter, return typed TEXT
age = int(raw)                    # 2. convert text → integer (crashes on "abc"!)
if age >= 18:                     # 3. branch on the comparison
    print(f"Age {age}: adult")    # 4a. runs if True (f-string embeds {age})
else:                             # 3b. otherwise...
    print(f"Age {age}: minor")    # 4b. runs if False
print("Done.")                    # 5. always runs (dedented)
Enter your age: 20 Age 20: adult Done.

Trace with input 20: line 1 prints the prompt and blocks until Enter; raw becomes the string "20" (input always returns str — typing 20 does not make a number!). Line 2 parses it to int 20. Line 3: 20 >= 18 → True → line 4a runs (f"…{age}…" interpolates the value — full depth in Chapter 6), line 4b skipped. Line 5 always runs. Type abc instead: line 2 raises ValueError: invalid literal for int() — your first encounter with input validation, systematized in Chapter 14.

⚠️ input() trapsinput() returns str always ("20" + 1 → TypeError; convert first). In notebooks/automated runs, input() blocks awkwardly — prefer function arguments and file inputs (Ch. 11/15) for anything re-runnable. Never eval(input()) — it executes arbitrary code (a security hole).

2.8 Interview questions

Q1: Expression vs statement? Give two examples of each and one consequence of the difference.
Expression evaluates to a value (2+3, len("hi")); statement performs an action (x = 5, import math, if …:). Consequence: the REPL echoes bare expressions but not statements — and a script containing only 2 + 3 prints nothing. Bonus: assignment is a statement, which is why print(x = 5) is a SyntaxError (walrus := is the expression form).
Q2: Why does indentation matter in Python? What are the exact rules?
Indentation defines code blocks — it replaces braces. Rules: 4 spaces per level, never mix tabs/spaces, blocks open after : and close at dedent. Violations raise IndentationError. Design rationale: the visual structure IS the logical structure, enforcing uniform readability.
Q3: Your script prints nothing and exits cleanly. Walk me through your diagnosis.
Checklist in order: (1) is there actually a print on the executed path (bare expressions are silent in scripts)? (2) did a branch/early-exit skip it (trace the flow)? (3) did I run the file I edited (pwd/ls, right folder)? (4) is output redirected/buffered (terminal vs file, flush)? Add a labeled probe print at the top to bisect.
