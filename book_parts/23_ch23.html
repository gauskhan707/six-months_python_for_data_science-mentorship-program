Craft

Writing Professional Python

▾

What/why. Code is read 10× more than written — by future-you (who forgot everything), teammates, reviewers, and interviewers. "Working" is the minimum; professional means readable (PEP 8, names, small functions — readable code gets fixed faster and breaks less), reliable (tested, logged, configured — failures are caught early and diagnosed fast), and reusable (DRY, modular, documented — the second use costs ~zero). This chapter turns working scripts into maintainable software: style automation, naming, function craft, logging, configuration, type-checking, and pytest testing — with the economics of why each practice pays.

23.1 PEP 8 + automation: style without arguments

What. PEP 8 is Python's style guide (naming, spacing, line length, idioms). The professional move isn't memorizing it — it's automating it: formatters rewrite code (Black/Ruff-format: canonical layout, zero decisions) and linters flag problems (Ruff/Flake8: unused imports, shadowing, banned patterns, complexity). Run both on every save + in CI: style debates end forever, diffs stay minimal, reviews discuss logic.

  return [(r["name"], r["price"] * TAX_MULT)
    for r in rows if r["price"] > 0]
Named constant, named fields, docstring, one idea — readable in seconds.

23.2 Naming + function craft (the readability core)

Naming economics. Names are read hundreds of times per write — every extra second of name-decoding multiplies across readers × readings. Rules: full words (count not cnt — except universal i/n/df/ax), units in names (timeout_s, size_mb, price_cents — prevents Mars-orbiter-class bugs!), booleans as predicates (is_valid, has_rows, needs_retry), functions as verb+object (parse_date, total_revenue), collections plural (rows, users), no type-encoding (name_str — hints do this!), no lies (get_ must not mutate; list must be a list).

Function craft (from §11.9, enforced). One job (no "and") · ~5–20 lines · ≤3–4 params (bundle config!) · pure core, I/O shell · return values, print at edges · guards over nesting · no magic literals (name them!) · docstring + hints on anything shared. Plus: DRY with judgment — duplicate twice, abstract on the third (premature abstraction couples things that merely look alike — "rule of three"). And YAGNI (You Aren't Gonna Need It): no speculative generality — extension points earn their existence.

magic → named, nested → guarded (before/after) 
# BEFORE: magic + nesting (works; unreadable; untestable pieces)
def proc(r):
    if r:
        if len(r) < 10000:
            t = 0
            for x in r:
                if x > 0:
                    t += x * 1.2
            return t / len(r)
    return 0

# AFTER: named + guarded + decomposed (same math, professional)
TAX_MULT = 1.2
MAX_ROWS = 10_000

def mean_taxed(values):
    """Mean of positive values scaled by TAX_MULT (empty → 0.0)."""
    if not values:
        return 0.0
    if len(values) >= MAX_ROWS:
        raise ValueError(f"{len(values)} rows exceeds {MAX_ROWS}")
    taxed = [v * TAX_MULT for v in values if v > 0]
    return sum(taxed) / len(values)

print(proc([10, -5, 20]), mean_taxed([10, -5, 20]))  # 12.0 12.0 — same answer, different futures
12.0 12.0

23.3 Logging: diagnostics that scale (never print in libraries)

What/why. logging replaces prints with leveled, named, routable, lazy diagnostics: levels filter noise (DEBUG<INFO<WARNING<ERROR<CRITICAL), logger names locate sources (sales.readers), handlers route (console/file/syslog…), lazy %s-args skip formatting when disabled, and exception() attaches tracebacks in one call. Prints have none of this — and pollute stdout (which may be piped data!).

logging: setup once, log everywhere 
import logging
logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(name)s: %(message)s")
log = logging.getLogger("sales")          # module logger (use __name__ in real modules!)

rows_loaded = 1200
log.debug("raw sample: %r", [1, 2])       # hidden at INFO (zero format cost — lazy %s!)
log.info("loaded %d rows", rows_loaded)   # normal operations (no f-string — lazy!)
log.warning("dropping %d bad rows", 37)   # concerning but handled
try:
    1 / 0
except ZeroDivisionError:
    log.exception("math failed")          # ERROR + FULL TRACEBACK, one call
# Levels: DEBUG (diagnose) < INFO (normal) < WARNING (handled-bad) < ERROR (failed op) < CRITICAL (dying)
# Libraries: NEVER basicConfig (app owns config!) — just getLogger(__name__) + NullHandler default.
... INFO sales: loaded 1200 rows ... WARNING sales: dropping 37 bad rows ... ERROR sales: math failed Traceback (most recent call last): ... ZeroDivisionError: division by zero

Log craft. Log decisions and boundaries (loaded N, dropped M because…, retrying, using fallback X) — not every loop iteration (volume!). Include counts + reasons + samples (dropping 37 rows (bad age); e.g. row 8812). Errors log once, at handling time (with traceback) — re-logging up the chain spams. Secrets never (passwords/tokens/keys — neither values nor full URLs-with-credentials).

23.4 Configuration: no magic in code (args/env/files)

What/why. Paths, thresholds, URLs, batch sizes, model names — anything that varies by run/machine/secret — must live outside code: CLI args (argparse — per-run knobs), environment variables (per-machine/secrets: os.environ["API_KEY"] — never in git!), config files (TOML/JSON/YAML — structured, reviewable, versioned). Hardcoding forces code edits for ops changes (risky), leaks secrets into git history (forever!), and blocks reuse across environments.

config layering: defaults < file < env < CLI (precedence!) 
import argparse, os

def build_config(argv=None):
    p = argparse.ArgumentParser(description="Analyze sales.")
    p.add_argument("--input", default=os.environ.get("SALES_INPUT", "sales.csv"))
    p.add_argument("--min-age", type=int, default=18)     # type-checked + documented free!
    p.add_argument("--verbose", action="store_true")
    args = p.parse_args(argv)
    if args.min_age < 0:                                # validate EARLY (fail fast, clear msg)
        p.error("--min-age must be ≥ 0")
    return args

cfg = build_config(["--input", "q3.csv"])
print(cfg.input, cfg.min_age, cfg.verbose)  # q3.csv 18 False
# Secrets pattern: token = os.environ["API_KEY"]  (KeyError = loud missing-secret — GOOD!)
# Never: API_KEY = "sk-..." in code (git history remembers FOREVER — rotate + purge if leaked!)
q3.csv 18 False

23.5 Type hints + mypy: static safety for dynamic code

hints that pay rent (3.9+ builtin generics) 
from __future__ import annotations  # (3.7–3.9 nicety; 3.10+ fine without for most)

def mean(xs: list[float]) -> float: ...
def get_user(uid: int) -> dict[str, object] | None: ...   # 3.10+ X | None (or Optional[X])

# mypy (install: pip install mypy; run: mypy src/): finds WRONG-TYPE calls WITHOUT running:
#   get_user("abc")  →  error: Argument 1 has incompatible type "str"; expected "int"
# Adopt gradually: hint NEW code fully → `mypy --strict` on new modules → expand.
# Hints are DOCS the IDE enforces (autocomplete, inline errors) + the reviewer reads.

Hint economics. Cost: ~5% more keystrokes on signatures. Payoff: IDE catches wrong-arg bugs while typing, mypy catches cross-file type bugs pre-commit, signatures become executable documentation (types > prose for contracts). Skip hints only for throwaway 5-liners. (Runtime enforcement (pydantic, beartype) exists for boundaries that must verify — APIs, configs, plugins.)

23.6 Testing with pytest: prove it works (the reliability core)

What/why. Tests are executable specifications: they prove behavior today and guard it forever (refactors/bugfixes verified in seconds, regressions caught at commit-time not customer-time). pytest: write plain test_*.py functions with assert — no boilerplate, great failure output, fixtures/parametrize for scale. What to test: pure functions exhaustively (happy + empty + edge + error paths — §11.1's testability argument!), I/O boundaries with tmp fixtures (tmp_path), regressions per fixed bug (§22.5). Coverage target: critical paths 100%, overall high — but meaningful asserts over percentage theater.

tests/test_analysis.py — the shape of good tests 
# tests/test_analysis.py  →  run: pytest -q  (add -x: stop at first fail, -v: verbose, -k: filter)
import pytest

def mean(xs):
    if not xs:
        raise ValueError("mean of empty")
    return sum(xs) / len(xs)

def test_mean_basic():                        # happy path
    assert mean([1, 2, 3]) == 2.0

@pytest.mark.parametrize("xs,expected", [    # MANY cases, one function (table-driven!)
    ([5], 5.0), ([0, 0], 0.0), ([-2, 2], 0.0), ([0.1, 0.2], pytest.approx(0.15)),
])
def test_mean_cases(xs, expected):
    assert mean(xs) == expected                # approx for FLOATS (§4.2 — never ==)!

def test_mean_empty_raises():                 # error path (contract!)
    with pytest.raises(ValueError, match="empty"):
        mean([])

def test_mean_does_not_mutate():              # purity/contract property
    xs = [3, 1, 2]
    mean(xs)
    assert xs == [3, 1, 2]                    # input untouched (aliasing guard — Ch. 3!)

Test craft. Name as specifications (test_empty_raises_value_error). One behavior per test (failures pinpoint!). Arrange-Act-Assert structure. Parametrize tables over copy-paste. approx for floats. tmp_path fixture for files (auto-cleaned). monkeypatch for env/time/randomness (deterministic!). Run on every save (watch) + every commit (CI gate) — unrun tests are fiction.

23.7 READMEs + review checklist (the professional surface)

README skeleton (3 commands to green!) 
# sales-tool — one-line WHAT + WHY
# Setup:  python -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt
# Usage:  python -m sales_tool.cli profile data/sales.csv --min-age 18
# Tests:  pytest -q  |  Lint: ruff check . && ruff format --check .
# Layout: readers/ (I/O) → analysis/ (pure) → cli (shell)  +  decisions (WHY, not what)

Self-review checklist (before every commit/PR). ☐ Formatted + linted? ☐ Names honest? ☐ Functions small/pure/guarded? ☐ No magic (constants/config)? ☐ No prints (logging)? ☐ Errors narrow + messaged? ☐ Hints on new signatures? ☐ Tests for new behavior (+ regressions)? ☐ README/decisions updated? ☐ No secrets? Run it literally for a month — then it's instinct.

23.8 Interview questions

Q1: logging vs print — the full technical case?
Levels (filterable verbosity), logger names (source location), handlers (console/file/syslog routing), lazy %-args (zero-cost-when-disabled), exception(traceback) in one call, thread-safety, and config-without-code-edits. Prints lack all six and pollute stdout (piped data!). Libraries must never configure logging (app owns it) — only emit via module loggers.
Q2: What makes code "clean" — beyond working? (Give the review checklist.)
Readable (names/units/verbs, small fns, guards, no magic, formatted), reliable (tested incl. edges+errors, logged, configured, hinted), reusable (DRY-by-three, modular, documented decisions). Cite §23.7's checklist + economics (read-10×-written; tests pay at refactor-time; names multiply across readers).
Q3: How do you test data-analysis code? (pure vs I/O vs floats vs determinism)
Pure cores exhaustively (happy/empty/edge/error, parametrized tables, approx for floats, purity asserts). I/O via tmp_path fixtures + golden files. Randomness/time/env via monkeypatch seeds (deterministic!). Regressions per bug (fail-old/pass-new proven). Run on save + CI gate. Untestable shape (I/O-mixed giants) → refactor to pure-core/imperative-shell first.

23.9 Exercises

Level 1 · Understand
  1. Install ruff; run check + format on 3 old scripts; accept everything; journal each change class (what rule? why better?).
  2. Convert 8 prints to leveled logs (right level each + lazy args); add one exception(); show level-filtering (INFO hides DEBUG).
  3. Rename-a-thon: take a cryptic 40-liner; rename every name per §23.2 (units! predicates! verbs!); diff readability.
Level 2 · Apply
  1. Refactor a 60-line script: extract 3+ pure functions + constants + config (argparse) + main() + guard + 8 pytest tests (incl. 2 error-paths). Before/after line counts + test run.
  2. Hint a module fully; run mypy; fix every error (no ignores); note which errors were REAL bugs vs annotation gaps.
  3. Write the §23.7 README for a project; hand it to someone cold; fix every step they stumble on.
Level 3 · Interview
  1. Review a peer's PR-diff (or your old code) with §23.7's checklist: file every finding as rule + evidence + fix (review-shaped, not complaint-shaped).
  2. Design logging strategy for a nightly pipeline (levels per event class, rotation, alerting thresholds, secret-safety); defend each choice against "just print".
