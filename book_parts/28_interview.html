What/why. Interviews test fluency under pressure: can you explain precisely (theory), code correctly (live), reason about trade-offs (design), and debug systematically (practical)? This section compresses the book into interview-shaped preparation: the guaranteed-asked canon (with chapter pointers — never memorize, always understand + demo), live-coding strategy, DS-role specifics, red flags to avoid, and a 2-week prep plan. Every answer here should be reproducible on a whiteboard with a marker — that's the bar.

I.2 Live-coding strategy (the performance, not just the code)

✅ Do (scores points)
Repeat the problem + examples back (alignment!) · ask edge-cases (empty? None? dupes? types?) BEFORE coding · narrate approach + Big-O FIRST (verbal design!) · brute-force then optimize (working > clever!) · test with 3 cases aloud (happy/edge/error) · name well + guard + comment WHY.
❌ Don't (red flags!)
Silent coding (they can't score thoughts!) · jumping to code with no plan · ignoring edge cases (until prompted twice) · clever one-liners needing explanation · "it works, dunno why" · blaming the language · never testing (not even mentally!).

The 5 classic live problems (drill until fluent). ① FizzBuzz-with-twist (guards + test table). ② Word-frequency top-N (Counter + stopwords + ties!). ③ Parse CSV → per-group means (csv + defaultdict + float-safe). ④ Flatten nested lists (recursion + base cases + depth limit!). ⑤ Retry-with-backoff decorator (factory + wraps + re-raise — §21.2 verbatim!). Each: state Big-O, handle 2+ edges, write 3 asserts.
