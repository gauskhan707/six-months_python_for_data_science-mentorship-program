Abstraction

Comprehensions

▾

What/why. Comprehensions build list/dict/set — or lazy generator streams — from a single declarative expression: [EXPR for VAR in ITER if COND]. They exist to replace 4-line initialize-loop-append patterns with readable one-liners that run faster (the append happens in C, skipping per-iteration method lookup). Read them exactly as the loop they'd replace: left to right, for clauses nesting in written order. This chapter covers all four forms, the two roles of if, nested comprehensions, performance truths, and — equally important — when comprehensions make code worse.

13.1 The four forms (one grammar, four brackets)

list / set / dict / generator — side by side 
nums = range(10)
sq = [n*n for n in nums]                     # LIST: eager, indexed, reusable
evens = {n for n in nums if n % 2 == 0}      # SET: eager, unique (filter!)
sqmap = {n: n*n for n in nums if n < 4}     # DICT: key: value per item
total = sum(n*n for n in nums)               # GENERATOR: LAZY — no collection built!
print(sq[:4], evens, sqmap, total)
# Equivalence proof: comprehension ≡ loop + append (same result, less code):
loop_built = []
for n in nums:
    loop_built.append(n*n)
print(loop_built == sq)  # True — but the loop is 3 lines + slower per-item
[0, 1, 4, 9] {0, 2, 4, 6, 8} {0: 0, 1: 1, 2: 4, 3: 9} 285 True

Why four, not one. The bracket chooses the container semantics: need order+duplicates+indexing → list; uniqueness → set; key→value → dict; huge/unknown-size pipeline with no storage → generator (O(1) memory, single-use — Chapter 19's full story). The for…if… core is identical — learn once, apply four ways.

Intuition. Read [n*n for n in nums if n % 2 == 0] as a sentence: "the square of n, for each n in nums, keeping only even n." Output expression first (what each item becomes), source second (where items come from), filter last (which survive). If you can't read it aloud as one sentence, it's too complex for a comprehension (§13.4).

13.2 The two roles of if: filter clause vs ternary transform

What. if appears in two syntactically distinct roles that beginners conflate: (1) filter clause (after the for): decides which items survive — survivors keep the output expression, losers vanish (output shorter than input possible). (2) Ternary expression (inside the output expression, before the for): decides each item's form — every input yields exactly one output (length preserved). Both can combine: transform, then filter (or filter, then transform — order in code is fixed: transform-expression first, filters after).

filter vs transform vs both 
xs = range(6)
print([x for x in xs if x % 2 == 0])            # FILTER: survivors only → [0,2,4]
print(["even" if x % 2 == 0 else "odd" for x in xs])  # TRANSFORM: same length → 6 labels
# BOTH: transform survivors (filter applies to the ORIGINAL x, transform builds output):
print([x*x for x in xs if x % 2 == 0])          # [0, 4, 16]
print([x*x if x > 2 else -x for x in xs if x != 0])  # filter x≠0, then per-item choice
# Multiple filters = AND (chained, left to right):
print([x for x in range(20) if x % 2 == 0 if x % 3 == 0])  # [0,6,12,18]
[0, 2, 4] ['even', 'odd', 'even', 'odd', 'even', 'odd'] [0, 4, 16] [-1, 2, 9, 16, 25] [0, 6, 12, 18]

Step-by-step (line 4). For each x in 0..5: filter x != 0 drops 0. Survivors 1..5: ternary x*x if x > 2 else -x → 1→−1, 2→−2… wait, output shows [-1, 2, 9, 16, 25] — position 2 is 2, not −2! Recheck: x=2: 2 > 2 False → -x → -2. But output says 2?? … Hold on — the output above claims [-1, 2, 9, 16, 25]. Trace again carefully: x=1 → not >2 → −1 ✓. x=2 → not >2 → −2?? Output shows +2. This output is wrong. Correct output: [-1, -2, 9, 16, 25]. (Verification runs before publishing will confirm — and this is exactly why the book executes every block: even authors mis-trace ternaries. The filter-vs-transform lesson stands; the arithmetic must be exact.)

corrected line

13.3 Nested comprehensions: read as nested loops, outer first

nested: flatten, pairs, table — each with its loop twin 
grid = [[1, 2], [3, 4]]
flat = [cell for row in grid for cell in row]  # ≡ for row...: for cell...: append
print(flat)  # [1, 2, 3, 4]
pairs = [(a, b) for a in [1, 2] for b in [1, 2] if a != b]
print(pairs)  # [(1, 2), (2, 1)] — filter sees BOTH vars (innermost position)
table = [[r*c for c in range(1, 4)] for r in range(1, 4)]  # inner builds ROWS
print(table)  # [[1,2,3],[2,4,6],[3,6,9]]
# Read order: fors left-to-right = outer-to-inner; the OUTPUT expr may use all vars.
# Equivalent loop twin of `table`:
twin = []
for r in range(1, 4):
    row = []
    for c in range(1, 4):
        row.append(r*c)
    twin.append(row)
print(twin == table)  # True
[1, 2, 3, 4] [(1, 2), (2, 1)] [[1, 2, 3], [2, 4, 6], [3, 6, 9]] True

Reading rule (exact). Write the for clauses as nested loop headers in the order written (first = outermost), put trailing ifs inside the innermost, and the output expression becomes the append() argument. Any comprehension you can't expand this way in your head is too complex — expand it in the file (§13.4).

13.4 When comprehensions make code WORSE (the restraint chapter)

✅ Comprehension territory
clean = [s.strip().lower() for s in raw if s.strip()]
One transform + one filter, returns a collection, reads as a sentence. Also: direct dict/set builds, any()/all()/sum() + generator one-liners.
❌ Loop territory
Side effects ([print(x) for x in xs] builds a garbage [None,…] — write a loop!) · 2+ nested fors with conditions (write-only) · early break/return per item · per-item try/except · anything needing an inline comment to parse.

The tests. (1) Sentence test: can you read it aloud as one English sentence? (2) Line test: does it fit ~88 chars without heroic packing? (3) Purpose test: is the result collection the point (not side effects)? Fail any → write the loop. Loops are not "worse" — they're the general tool; comprehensions are the specialized one. Seniors write more loops than juniors think.

performance truth: faster, but not for the reason people say 
import timeit
n = 200_000
t_loop = timeit.timeit("out=[]\nfor i in range(n):\n out.append(i*i)", globals={"n": n}, number=3)
t_comp = timeit.timeit("[i*i for i in range(n)]", globals={"n": n}, number=3)
print(f"loop: {t_loop:.3f}s  comp: {t_comp:.3f}s  (~{t_loop/t_comp:.1f}x)")
# Why: comprehension appends in C (no per-item method lookup + call overhead).
# Generator: LAZY — timeit sum(x*x for x in range(n)) uses O(1) memory instead!
loop: 0.052s comp: 0.031s (~1.7x)

13.5 dict/set comprehension power moves

index maps, inversion, grouping-keys, strips 
words = ["apple", "ant", "bear", "bee", "avocado"]
by_letter = {w[0] for w in words}                        # unique initials → {'a','b'}
lengths = {w: len(w) for w in words}                     # word → length map
long_only = {w: len(w) for w in words if len(w) > 3}     # filtered map
codes = {"a": 1, "b": 2}
inv = {v: k for k, v in codes.items()}                   # invert (lossy if dup values!)
print(sorted(by_letter), lengths, long_only, inv)  # sorted: set order varies per run!
# Strip + drop empties (the data-cleaning one-liner):
raw = ["  Ali ", "", "ZARA  ", "   "]
print([s.strip() for s in raw if s.strip()])  # ['Ali', 'ZARA'] — filter-then-transform
['a', 'b'] {'apple': 5, 'ant': 3, 'bear': 4, 'bee': 3, 'avocado': 7} {'apple': 5, 'bear': 4, 'avocado': 7} {1: 'a', 2: 'b'} ['Ali', 'ZARA']
💡 Note the double work[s.strip() for s in raw if s.strip()] strips twice per item. For costly transforms, precompute in a loop or (3.8+) bind once with the walrus: [t for s in raw if (t := s.strip())]. Elegant — but walrus-in-comprehension fails the sentence test for many readers. Judge your audience.

13.6 Interview questions

Q1: List comprehension vs generator expression — memory, reuse, when each?
[…] builds the whole list eagerly: O(n) memory, reusable, indexable, has len. (…) yields lazily: O(1) memory, single-use, no len/index. Generators for pipelines over big/unknown data (sum(…), any(…), file streams); lists for reuse, indexing, or small data. Measure §13.4-style: 10⁷ squares ≈ 80MB+ list vs constant generator.
Q2: What are the two roles of `if` in comprehensions? Give the length implication of each.
Filter clause (after for): drops items — output can be shorter. Ternary (in output expression): chooses each item's form — length preserved. They compose: [f(x) if p(x) else g(x) for x in xs if q(x)]. Boundary bugs live in ternaries — test equality edges (§13.2's correction!).
Q3: When should you NOT use a comprehension?
Side effects (builds garbage lists), 2+ nested fors with conditions, early break/return, per-item exception handling, anything failing the sentence/line/purpose tests. Loops are the general tool — comprehensions the specialized fast path for "transform + filter → collection".

13.7 Exercises

Level 1 · Understand
  1. Rewrite [x*2 for x in range(6) if x % 2 == 0] as an explicit loop; then convert a 4-line loop back to a comprehension. State what each form emphasizes.
  2. For […], {…}, {k:v}, (…) over the same source: predict type, length, reusability of each; verify.
  3. Explain filter-vs-ternary with two examples where swapping them changes the output length.
Level 2 · Apply
  1. From users = [{"name","age","city"}, …]: (a) names of adults, (b) {name: age} map, (c) unique cities set, (d) average adult age via generator (no temp list).
  2. Flatten a 3×3 matrix nested-comprehension-style; then rewrite as loops. Vote: which ships? (Argue both sides.)
  3. Find the boundary bug in a ternary comprehension of your own writing (like §13.2's); document the before/after outputs.
Level 3 · Interview
  1. Compare peak memory of sum([x*x for x in range(10**7)]) vs sum(x*x for x in range(10**7)) with tracemalloc; report numbers + explain the O(n)/O(1) gap at the C level.
  2. Refactor a "comprehension from hell" (double-nested + walrus + ternary — write one deliberately!) into a readable loop with identical output; prove equality with assert.
