Python Debugging

▾

What/why. Debugging is not guessing, tweaking, or hoping — it is the scientific method applied to code: observe precisely, hypothesize explicitly, predict observably, test minimally, fix at the cause, verify + lock with a regression test. Seniors debug faster than juniors not by knowing more answers but by following a workflow instead of thrashing (random changes destroy evidence and breed new bugs). Memorize this chapter's loop; it scales from typos to distributed outages — only the instruments change.

Figure 22.1 — The professional debugging workflow (follow literally)
1 · UNDERSTAND the error (read it FULLY — type + message + which line)
↓
2 · READ traceback bottom-up (WHAT last line → WHERE frames above)
↓
3 · LOCATE failure (which line? which value? print suspects!)
↓
4 · REPRODUCE minimally (smallest snippet that still breaks — bisect!)
↓
5 · INSPECT state (print/assert/pdb — assumptions vs reality)
↓
6 · TEST one hypothesis (single change → PREDICT → run → confirm/refute)
↓
7 · FIX at the cause (not the symptom!) → 8 · RETEST + REGRESSION TEST (lock it!)

22.1 Traceback mastery: anatomy + bottom-up protocol + chaining

traceback anatomy, fully annotated 
def mean(xs):
    return sum(xs) / len(xs)     # line 2: the crash site (division)

mean([])                         # line 4: the trigger (empty input)
# Traceback (most recent call last):                 ← ① header: frames follow, oldest FIRST
#   File "prog.py", line 4, in <module>               ← ② outer frame (read UP from bottom)
#     mean([])                                       ← ③ its source line (the CALL)
#   File "prog.py", line 2, in mean                   ← ④ inner frame (most recent = crash site)
#     return sum(xs) / len(xs)                       ← ⑤ offending line (0/0!)
# ZeroDivisionError: division by zero                ← ⑥ WHAT: read FIRST — type + reason

Bottom-up protocol (exact). ① Read the last line fully: exception type (which rule broke?) + message (which values?). ② Move up to the innermost frame (last File… block): file + line number + function + echoed source. ③ Walk outward (up the frames): who called whom with what? — the story of how execution reached the crash. ④ Distinguish crash site (where it died — often innocent!) from fault site (where badness originated — empty list passed at line 4!). Beginners fix the crash site (wrap line 2 in try!) — professionals fix the fault (validate at line 4 / in mean's contract — §22.5).

Chained tracebacks ("During handling… caused by…"). raise New from old (§14.3) prints both chains: read the bottom chain's last line (the final error), then the upper chain (the root cause). During handling of X, another occurred (implicit, no from) = error-inside-handler — the upper X is context, the lower is what killed you. Long chains in frameworks (10+ frames of library internals): scan for YOUR files (the outermost YOUR-frame = your trigger; innermost YOUR-frame = your last touch before library land).

22.2 Reproduce minimally: bisection + the minimal snippet

What. Bisection: repeatedly halve the suspect (code, data, or time) while preserving the failure — 1M rows → 500k → … → 3 rows that still break. Minimal repro: the smallest self-contained snippet exhibiting the bug (ideally <10 lines, no files, no network). Why: tiny repros isolate variables (only one suspect left), run in milliseconds (fast hypothesis cycles), and are shareable (teammates/Stack Overflow/forums demand them — "minimal reproducible example").

bisection in action (data + code) 
# Symptom: pipeline dies on full data. Bisect the DATA:
#   rows[:500_000] ✓ works → bug in second half → [:750_000] 💥 → [:625_000] ✓ ...
#   → 3 guilty rows found in ~20 runs (log₂(1M) ≈ 20 — bisection is LOGARITHMIC!)
# Then bisect the CODE: comment halves (§2.3's comment-out!) until 5 guilty lines remain.
# Then FREEZE it as regression material (Ch. 23):
def mean(xs):
    if not xs:                                   # ← the FIX (fault site: contract!)
        raise ValueError("mean of empty sequence")
    return sum(xs) / len(xs)
# Minimal repro preserved as a TEST (fails pre-fix, passes post-fix):
assert mean([2, 4]) == 3.0
try:
    mean([])
    raise AssertionError("should have raised!")
except ValueError:
    print("regression locked: empty → ValueError ✓")
regression locked: empty → ValueError ✓

Bisection discipline. Change one variable per run (halve data OR disable code — never both, or evidence confounds). Keep notes (run # : change → result). Stop at understanding, not just green ("it works now, dunno why" = bug relocated, not fixed — it will return). The minimal repro becomes the regression test (§22.5) — debugging output is a test asset, not trash.

22.3 Instruments I: print-probes + f-string debugging + asserts

probe craft: labels, !r, =, and strategic placement 
def pct(part, whole):
    print(f"[pct] in: {part=!r}, {whole=!r}")   # ={ } self-documents; !r exposes whitespace/type!
    result = 100 * part / whole
    print(f"[pct] out: {result=}")
    return result

print(pct(3, 4))
# Strategic placements: function ENTRY (args?) / BRANCH points (which path?) /
# LOOP (first/last iterations? use `if i < 3 or i > n-3`) / BEFORE crash line (suspects!) /
# INVARIANTS (assert, below — executable assumptions!)

def withdraw(balance, amount):
    assert balance >= 0, f"balance {balance} already negative (caller bug!)"
    assert amount > 0, f"amount {amount} not positive"
    assert amount <= balance, f"overdraft: {amount} > {balance}"
    return balance - amount
print(withdraw(100, 30))
# withdraw(100, 500) → AssertionError: overdraft: 500 > 100 (fault PINPOINTED, not downstream!)
# RULE: assert INTERNAL invariants (your logic's promises); validate EXTERNAL input with if/raise (Ch. 14)!
# (python -O STRIPS asserts — never rely on them for user-facing validation!)
[pct] in: part=3, whole=4 [pct] out: result=75.0 75.0 70

Probe hygiene. Label every probe ([fn] prefix — grep-able!), print !r (hidden chars visible) + type() when types suspect, throttle loop probes (first/last N — million-line logs help nobody), and remove or log-level them after (stray probes pollute real output — Ch. 23's logging replaces them permanently).

22.4 Instruments II: pdb + breakpoint() + IDE debugging + post-mortem

pdb: the 10 commands that cover 95% 
# Insert EXACTLY where confused (Python 3.7+):
#   breakpoint()          # drops into pdb HERE (honors PYTHONBREAKPOINT=0 to disable globally!)
# At the (Pdb) prompt:
#   l / ll      list code around / LONG-list whole function (know where you are!)
#   n           NEXT line (step OVER calls)
#   s           STEP INTO the call (descend!)
#   c           CONTINUE to next breakpoint / end
#   r           RETURN from current function (run to its exit)
#   p expr      PRINT any expression (full Python! call functions, slice, anything)
#   pp expr     PRETTY-print (nested structures readable!)
#   w           WHERE: stack trace (which frames? how deep?)
#   u / d       UP / DOWN frames (inspect CALLERS' variables!)
#   b line      BREAKpoint at line (b func, b file:line, conditional: b 12, x>5)
#   q           QUIT (abandon — careful: kills program!)
# Post-mortem (inspect the CORPSE after a crash — no repro needed!):
#   python -m pdb script.py  →  c  →  (crash)  →  w, u, p suspects...
# IDE equivalent (VS Code/PyCharm): gutter-click breakpoint → F5 → hover vars,
# WATCH panel (live exprs), CALL STACK pane (click frames!), STEP OVER/INTO buttons.

When pdb beats probes. Deep stacks (inspect 5 frames up — probes can't), loops (conditional breakpoints beat 10k prints), unknown unknowns ("WHAT is this variable?!" — p type(x), x answers instantly), heisenbugs probes perturb (timing-sensitive — though logging perturbs less than prints). When probes beat pdb: quick single-value checks, production-attached processes (can't interrupt), async/multi-threaded flows (pdb serializes confusingly — log instead). Professionals use both daily.

💡 Rubber-duck debugging (the zero-tech instrument)Explain your code line by line, aloud (to a duck, a teammate, or the air) — stating what each line actually does (not what you intended). Half of all bugs confess mid-sentence ("…and then i increments — wait, NO, continue SKIPS the increment!"). Do this before escalating to tools or teammates — it's the highest-ROI minute in debugging.

22.5 Fix at the cause + the strategy table + regression habit

Cause vs symptom (the senior distinction). Symptom fix: wrap the crash line in try/except (crash gone, corruption continues — the empty-mean now silently returns None and poisons downstream stats!). Cause fix: enforce the contract at the fault site (mean raises on empty; caller validates input upstream). Tests: would the fix survive different triggers of the same fault? does it make the bug impossible (validation/types) or merely silent? Symptom fixes multiply; cause fixes divide.

SymptomFirst moveUsual cause → fix site
Exception + tracebackBottom-up read (§22.1); minimal reproBad value/type at named line → validate at source
Wrong result, no errorAssert intermediates; bisect probesLogic/off-by-one/aliasing → the wrong line, + test
Works once, fails laterDiff states (mutation? globals? exhausted gen?)Shared mutable / single-use iterator → copy/factory
Only on big dataShrink (bisect rows); profile memoryO(n²)/materialization/leak → stream (Ch. 19/24)
Only on their machineCompare exe + versions (§17.5)Wrong venv / drifted pins → freeze + recreate
Flaky / intermittentSeed randomness; log orderingsSet/dict-order assumptions, races, time — make deterministic
Slow (not wrong)Profile (Ch. 24!) — never guessHotspot ≠ hunch 90% of the time → measure first
✅ The regression habit (debugging's deliverable)Every fixed bug earns a regression test (Ch. 23) that FAILS on old code and PASSES on new — run it against both to prove it. Bugs recur (refactors resurrect them); tests remember. A fix without a test is a rumor. File the minimal repro AS the test — §22.2's pattern, every time.

22.6 Interview questions

Q1: Walk me through your debugging workflow on a production traceback.
Recite §22.0's loop with a real example: read last line (type+message) → innermost frame (crash site) → outward frames (trigger story) → separate crash site from fault site → minimal repro (bisect data/code) → probes/pdb single-hypothesis tests → fix at cause (contract/validation, not symptom-suppression) → retest + regression test. Mention rubber-ducking and one-change-per-run discipline.
Q2: pdb vs print-debugging — when each? Name the key pdb commands.
pdb: deep stacks (u/d frames), loops (conditional b), unknowns (p anything), post-mortem (python -m pdb). Probes: quick checks, uninterruptible processes, async flows (log instead). Commands: l(ist), n(ext), s(tep), c(ontinue), p/p(p), w(here), u/d, b(reak), q(uit). IDE: same power visual (watch/call-stack/hover).
Q3: Cause vs symptom fix — with an example of each for the same bug.
Bug: mean([]) ZeroDivisionError. Symptom fix: try/except around the division returning None — crash gone, but silent None corrupts downstream stats (and every caller must None-check). Cause fix: mean raises ValueError on empty (contract!) + caller validates upstream — impossible states unrepresentable, fault localized, regression-tested. Test: does the fix survive other triggers of the same fault?

22.7 Exercises

Level 1 · Understand
  1. Take 3 old tracebacks; annotate every frame (file/line/fn) + the bottom line in plain words; mark crash site vs fault site for each.
  2. Add 5 asserts to a past function (entry/branch/exit invariants); trigger 2 deliberately; note how assertion messages beat raw tracebacks.
  3. Solve one bug using ONLY breakpoint() + n/p/w/u (no probes). Journal each command + what it revealed.
Level 2 · Apply
  1. Debug blind (full workflow + journal): avg(xs) = sum/len called with [], ["3"], a generator, None. Deliver: repros, fault analysis, cause-fix, regression tests.
  2. Bisect a 10k-row CSV with one poison row to the exact row in ≤14 runs (log₂); automate the bisection loop.
  3. Post-mortem drill: crash a 3-level script under python -m pdb; navigate to the outermost YOUR-frame; inspect + explain without re-running.
Level 3 · Interview
  1. "Passes on 1k rows, OOMs on 10M": full diagnosis plan (which stage grows? list vs gen? tracemalloc evidence?) + streaming fix + before/after peak-RSS numbers.
  2. "Flaky test, fails 1 in 20": determinism audit (seeds? set-order? time? tmp collisions?) → reproduce reliably → fix → prove 200 green runs.
