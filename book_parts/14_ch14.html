Robustness

Errors and Exception Handling

▾

What/why. Three failure kinds stalk every program: syntax errors (broken grammar — nothing runs), runtime exceptions (valid grammar, impossible operation — the ValueError/KeyError/FileNotFoundError family), logic errors (runs fine, wrong answer — the dangerous ones, no exception to catch). Exceptions exist so errors cannot be silently ignored: unhandled, they crash loudly with a traceback pinpointing the failure; handled with try/except, they become controlled branches for the inevitable (dirty CSV cells, missing keys, dead network). Data work is exception-heavy by nature — this chapter is survival gear, and Chapter 22 builds the debugging workflow on top of it.

14.1 The failure taxonomy (know your enemy)

The critical judgment: bug vs condition. Bugs (your code is wrong: bad index math, None where a list was promised) must crash loudly — never catch-and-hide them, or corruption spreads silently. Conditions (the world is messy: user typed "abc", file vanished, row malformed) must be handled gracefully — validate, convert-or-collect-errors, retry, or report. Most exception misuse is catching bugs (hiding them) or crashing on conditions (fragility). Ask per except: "is this the world's fault (handle) or mine (fix)?"

Hierarchy note (practical). All catchable errors derive from Exception (which derives from BaseException — home also to KeyboardInterrupt/SystemExit/GeneratorExit, which ordinary except Exception deliberately doesn't catch). Catch specific classes (ValueError, FileNotFoundError); except Exception is for top-level safety nets that log + re-raise or exit — never silent. Bare except: catches even Ctrl+C — banned (§14.5).

14.2 The full try anatomy: try / except / else / finally

every clause, each justified 
def safe_div(a, b):
    try:
        result = a / b            # RISKY LINES ONLY — keep this block tiny (one idea!)
    except ZeroDivisionError:     # specific exception FIRST...
        return "can't divide by zero"
    except TypeError as e:        # ...`as e` captures details for messages/logging
        return f"bad types: {e}"
    else:
        return result             # runs ONLY if NO exception — the SUCCESS path
    finally:
        pass                      # ALWAYS runs (cleanup) — `with` usually obsoletes it

print(safe_div(10, 2), "|", safe_div(10, 0), "|", safe_div(10, "x"))
# Multiple types, one handler: except (TypeError, ValueError) as e:
# Handler ORDER matters: subclasses before parents (FileNotFoundError before OSError)!
5.0 | can't divide by zero | bad types: unsupported operand type(s) for /: 'int' and 'str'
Figure 14.1 — Exception flow (trace it!)
try block runs, line by line
↓ exception raised?
YES → abandon try instantly → jump to FIRST matching except (subsequent try-lines SKIPPED) → else SKIPPED → finally runs
· vs ·
NO → skip ALL excepts → else runs (success path) → finally runs

Why else exists (not just style). Code in else runs on success but is not protected by the excepts — so a bug in your success path crashes loudly instead of being mis-caught as the anticipated failure. Putting success code inside try widens the net: an unexpected error there gets mislabeled as the expected one (misdiagnosis!). Rule: try = the exact risky lines; else = what success enables.

Why finally is rare now. It guarantees cleanup (close/release) even across return/break/exceptions — but with statements (Ch. 15/21) package try/finally into readable one-liners (with open(…) as f:). Write raw finally only when no context manager exists for your resource (then consider writing one — Ch. 21).

⚠️ Handler order + widthHandlers test top-down; put subclasses before parents (FileNotFoundError before OSError — else the parent swallows everything and the child is dead code). Keep try blocks to one idea / few lines — a 30-line try means you can't tell which line failed, and you'll catch errors you never anticipated from lines you never suspected.

14.3 raise: failing loudly and helpfully + exception chaining

What. raise ValueError("age must be ≥ 0") throws an exception now — for validation ("caller broke the contract"), impossible states ("this should never happen"), and re-throwing with context. Bare raise (inside except) re-raises the current exception, preserving its traceback — the only correct re-throw.

raise patterns: validate, re-raise, chain, suppress-context 
def set_age(age):
    if not isinstance(age, int) or isinstance(age, bool):
        raise TypeError(f"age must be int, got {type(age).__name__}")  # contract!
    if age < 0:
        raise ValueError(f"age must be ≥ 0, got {age}")                # message = data!
    return age

for bad in ["x", -5]:
    try:
        set_age(bad)
    except (TypeError, ValueError) as e:
        print("rejected:", e)

# Translate low-level errors into DOMAIN errors (with chaining):
def load_config(path):
    try:
        return open(path, encoding="utf-8").read()
    except FileNotFoundError as e:
        raise RuntimeError(f"missing config: {path}") from e  # `from e`: chain (both tracebacks!)
# `raise ... from None`: deliberate translation, hide the low-level cause (use sparingly)
rejected: age must be int, got str rejected: age must be ≥ 0, got -5

Message craft (matters enormously). Include: what was expected, what arrived, and where — f"age must be ≥ 0, got {age}" beats "invalid age" beats "error". Future-you debugs at 2 AM from these strings alone — write them generously. Include values with !r when whitespace/type confusion is plausible (f"expected int, got {age!r}").

14.4 Custom exceptions + EAFP vs LBYL

What. Custom exceptions (class DataError(ValueError): …) name domain failures — catchable precisely, self-documenting, and carrying structured context (row numbers, field names). Derive from the closest builtin (ValueError for bad values, RuntimeError for state problems, Exception + a project-base-class for hierarchies) so generic handlers still work.

domain exceptions + EAFP parsing 
class DataError(ValueError):
    """A dataset row failed validation (carries row + reason)."""
    def __init__(self, row_no, reason):
        super().__init__(f"row {row_no}: {reason}")
        self.row_no, self.reason = row_no, reason

def parse_age(text, row_no):
    try:
        age = int(str(text).strip())       # EAFP: TRY first...
    except (TypeError, ValueError):        # ...handle failure (one place, all causes)
        raise DataError(row_no, f"bad age {text!r}") from None
    if not 0 <= age <= 120:
        raise DataError(row_no, f"age {age} out of range")
    return age

rows = ["30", "abc", "999", None]
good, problems = [], []
for i, t in enumerate(rows):
    try:
        good.append(parse_age(t, i))
    except DataError as e:                # collect-and-continue (never crash the batch!)
        problems.append(str(e))
print("good:", good)
print("problems:", problems)
good: [30] problems: ["row 1: bad age 'abc'", 'row 2: age 999 out of range', 'row 3: bad age None']

EAFP (Easier to Ask Forgiveness than Permission — try, catch) vs LBYL (Look Before You Leap — if-check, then act). EAFP wins by default: atomic (check-then-act races: file deleted between exists() and open()), complete (one handler covers all failure modes, not just the ones you foresaw), fast in the common case (no double lookup: d[k] once vs k in d + d[k]). LBYL fits when: the check is cheap and failure is routine control flow (if not rows: return []), or exceptions would be obscenely frequent (tight loops where 99% fail — measure first!).

✅ The collect-and-continue pattern (data pipelines live here)Batch jobs must never die on row 9,000,001: wrap per-item work in try/except, append successes, collect (row_no, error) failures, and report counts at the end. Distinguish fatal (schema wrong, file missing — abort) from row-local (bad cell — collect). Chapters 15/25 and every project implement exactly this.

14.5 The bans (never do these) + logging errors

🚫 Banned patterns (each with its horror story)① Bare except: — catches KeyboardInterrupt/Ctrl+C (un-killable programs!) and hides everything. Always name the class. ② except Exception: pass — silent data corruption: the #1 worst bug shape in data science (rows vanish, means drift, nobody knows). Log or count, always. ③ except Exception as e: print(e) and continue as if fine — same silence, plus stdout noise. ④ Catching to return None indistinguishably (caller can't tell "missing" from "broken" — raise or use sentinel types). ⑤ 30-line try blocks (which line failed? unknowable).
log, don't print, errors (preview of Ch. 23 done right) 
import logging
logging.basicConfig(level=logging.INFO, format="%(levelname)s: %(message)s")
log = logging.getLogger("demo")

def robust_int(text):
    try:
        return int(str(text).strip())
    except (TypeError, ValueError):
        log.warning("unparseable int %r — using None", text)  # lazy args, level, logger name
        return None  # documented choice: caller handles None (vs raise — pick per contract!)

print(robust_int("42"), robust_int("abc"))
WARNING: unparseable int 'abc' — using None 42 None

14.6 Debugging with exceptions (bridge to Chapter 22)

Exceptions are the debugger's raw material: the last traceback line names the failure, frames above locate it, and as e carries the evidence. Workflow preview: reproduce minimally → read bottom-up → inspect the raise-site values → decide bug-vs-condition (§14.1) → fix or handle → add a regression test proving it stays fixed (Ch. 23). Two power tools: traceback.print_exc() (dump current traceback anywhere — log it, don't lose it) and post-mortem python -m pdb script.py (inspect the corpse — Ch. 22).

14.7 Interview questions

Q1: try/except/else/finally — what goes where, and why does else exist?
try: only the lines that may raise the caught exception (one idea, few lines). except: narrow, specific handlers, subclasses first. else: success-path code — runs only without exception AND unprotected, so success-path bugs crash loudly instead of being mis-caught. finally: guaranteed cleanup — usually replaced by with.
Q2: EAFP vs LBYL — define, compare, and say when each wins.
EAFP: try first, handle failure — atomic (no check-act race), complete (all failure modes), single lookup. LBYL: check then act — two lookups, races in file/threaded code. EAFP default (dicts, casts, files); LBYL when checks are cheap and failure is routine flow, or exceptions would dominate hot loops (measure!).
Q3: What's wrong with `except: pass` and `except Exception: return None`?
Bare except: catches even KeyboardInterrupt/SystemExit and hides all evidence. pass/silent-None converts failures into silent corruption (missing rows, wrong stats) — the costliest bug shape. Always: narrowest class + log/count + recover, retry, or re-raise with context.
Q4: How do you design exceptions for a data pipeline?
Hierarchy: project base (PipelineError(Exception)) → SourceError (fatal: abort), SchemaError (fatal), RowError (collect-and-continue with row_no). Raise domain errors with rich messages (expected/got/where); chain low-level causes (from e); top level logs + exit code. Show §14.4's collect loop.
