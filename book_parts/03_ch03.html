Core mental model

Variables and Memory

▾

The single most important mental-model chapter in the book. In Python, x = 5 does not "put 5 into box x". It creates the object 5 in memory and attaches the name x to it. Variables are names (references) pointing at objects — not boxes holding values. This one correction dissolves half of all Python surprises you will ever meet: mutable aliasing bugs, == vs is, function side effects, default-argument traps, and "why did my other variable change?!". Read slowly; draw every diagram yourself.

3.1 The core model: objects, names, references, assignment

What — four definitions to memorize exactly:

  • Object: a region of memory holding a value plus its type and bookkeeping metadata (notably a reference count). In Python, everything is an object — numbers, strings, lists, functions, classes, modules, even None. There are no "primitive values" living outside the object system (unlike Java's int vs Integer).
  • Variable (name): a label, stored in a namespace (a name→object table — Chapter 12), that refers to an object. Names are entries in a dictionary-like structure; they occupy no "value space" themselves.
  • Reference: the arrow from a name to its object. Multiple names can reference the same object; one name references exactly one object at a time.
  • Assignment (=): the act of binding (or rebinding) a name to an object. It evaluates the right side to an object, then points the left-side name at it. Assignment never copies data. Ever.

Why this design exists. Uniformity: with everything-an-object and assignment-as-binding, the language needs only one mechanism for all data — no separate rules for "primitives vs objects", no manual memory copying on =, cheap function calls (passing a huge list passes one reference, not a copy). Memory safety follows: since names never contain values, the memory manager (reference counting + cyclic GC, §1.12 Q5) can track exactly how many arrows point at each object and free it precisely when the last arrow leaves.

Intuition: balloons and strings. Objects are balloons floating in memory; variables are strings tied to them. x = [1, 2] inflates a balloon (the list) and ties string x to it. y = x ties a second string to the same balloon — no new balloon exists. Let air out through y (mutate) and x's balloon deflates too — same balloon. x = [9] inflates a new balloon and reties string x to it; string y still holds the old one. When a balloon has zero strings, Python pops it (frees the memory).

Syntax + smallest example. Assignment is name = expression. Multiple assignment and unpacking are the same mechanism, repeated:

the balloon demo — aliasing, mutation, rebinding 
x = [1, 2]
y = x               # second string, SAME balloon (no copy!)
print(x is y)       # True: identical object (identity operator)
print(id(x) == id(y))  # True: same memory address
y.append(3)         # let air out through y...
print(x)            # ...x's balloon deflated too: [1, 2, 3]
x = [9]             # retie ONLY x to a NEW balloon
print(x, y)         # [9] [1, 2, 3] — y untouched. Proof.
True True [1, 2, 3] [9] [1, 2, 3]

Step-by-step execution. Line 1: list object [1,2] created (refcount 1), name x bound. Line 2: name y bound to that same object (refcount 2) — zero bytes of list data copied. Lines 3–4: is compares identity (are these the same balloon?), id() exposes the address — both confirm. Line 5: append mutates the shared object in place (refcount unchanged, contents changed). Line 7: a new list [9] is created; x is retied to it (old object's refcount drops 2→1, so it survives — y still holds it).

More examples — rebinding chains and del:

rebinding chains + del removes the string, not the balloon 
a = [1]
b = a
c = b        # three strings, one balloon (refcount 3)
del b        # remove ONE string (refcount 2) — balloon floats on
print(a, c)  # [1] [1]
a = "now a string"   # retie a elsewhere (refcount 1: only c)
print(a, c)          # now a string [1]
# del c  → refcount 0 → balloon popped (memory freed)
[1] [1] now a string [1]
⚠️ Common mistake: "boxes" thinkingIf you picture variables as boxes, y = x; y.append(3) changing x feels like paranormal activity. There is no paradox under strings-and-balloons: two strings, one balloon. Every "spooky change at a distance" in Python is shared-object mutation. When it bites, ask: "how many names point at this object?" (sys.getrefcount counts, roughly).

Debugging lens. Suspected aliasing? (1) print(a is b) — same balloon? (2) print(id(a), id(b)) — same address? (3) mutate through one name in a scratch snippet and observe the other. Fix by copying at the binding site: y = x.copy() / list(x) / copy.deepcopy (Chapter 7 teaches which).

📊 Data-Science connection. Passing a million-row structure to a function costs nothing (one reference), which is why Python APIs casually accept huge datasets. But the same mechanism means a cleaning function that mutates its input corrupts the caller's data — the #1 source of "my raw data changed?!" panic. Professional rule (Chapters 11/23): functions either return new objects (pure) or document mutation loudly — never mutate silently.

3.2 Identity, equality, id(): same balloon vs equal balloons

What. Identity (is / id()) asks: are these two names tied to the same object in memory? Equality (==) asks: do these two (possibly distinct) objects have equal value? id(obj) returns the object's identity — in CPython, its memory address (an integer, unique among live objects).

Why both exist. Different questions need different answers: deduplicating data needs value comparison (==); checking "was anything passed at all?" needs identity against the None singleton (is None); aliasing diagnosis needs is. Conflating them is a top-5 Python bug.

== vs is, settled forever 
a = [1, 2]
b = [1, 2]     # a SEPARATE balloon with equal contents
c = a          # same balloon
print(a == b)  # True  — equal VALUE (list __eq__ compares contents)
print(a is b)  # False — DIFFERENT objects
print(a is c)  # True  — same object
print(id(a) == id(c), id(a) == id(b))  # True False — same/different? (raw ids vary per run)
print(None is None)  # True — None is a singleton; ALWAYS test with 'is'
True False True True False True
🚫 Never use 'is' for valuesx is 5, s is "abc", tup is (1,2) sometimes "work" in the REPL because CPython caches/interns small ints and some strings (an implementation detail!). They break unpredictably for larger values (1000 is 10**3 → False). Rule: is only for None (and rarely True/False singletons). Values always compare with ==.

3.3 Mutable vs immutable: the great divide

What. An immutable object can never change its value after creation: int, float, complex, bool, str, bytes, tuple, frozenset, NoneType. Any operation that "modifies" one actually creates a new object and (typically) rebinds your name to it. A mutable object can change in place: list, dict, set, bytearray — same balloon, new shape; every name tied to it observes the change.

Why immutables exist. Four reasons: (1) Hashability — dict keys and set members need stable identities (Chapter 8: mutating a key would corrupt the hash table); (2) Safe sharing — passing an int to ten functions can't corrupt it; (3) Interning/caching — CPython reuses small ints and some strings, saving memory; (4) Reasoning — immutable data never changes under you, eliminating whole bug classes (functional programming, Chapter 20, leans on this).

Intuition. Immutable objects are carved in stone — to "change" the inscription you carve a new stone. Mutable objects are whiteboards — same board, erased and rewritten, and everyone looking at that board sees the latest writing.

Step-by-step (the int case). a = 10: int object 10 created, a bound. a + 5: int addition creates a brand-new int object 15 (the 10 is untouched — it must be, others may reference it). a = …: a retied to 15; 10's refcount drops (freed if zero). Contrast m.append(3): no assignment happens — a method mutates the existing list's internals; the name never moves.

The tuple "loophole" (understand, don't fear). t = ([1], [2]) — the tuple's references are frozen (can't repoint t[0]), but the referenced lists remain mutable (t[0].append(99) works). Immutability is shallow: it locks the container's arrows, not the balloons they point to. Consequence: such tuples are unhashable (can't be dict keys) — hashability requires deep immutability.

⚠️ The #1 aliasing bug family (preview of Chapters 7/11)row = [0]*3; board = [row, row, row] looks like three rows but is one list referenced three times — editing any "row" edits all. Fix: build independent objects: [[0]*3 for _ in range(3)]. Same family: y = x then mutating when you meant to copy (use .copy()), and mutable default arguments (def f(xs=[]) — Chapter 11).
✅ Data-Science connectionPandas' infamous SettingWithCopyWarning is exactly this chapter: "are you mutating the original DataFrame or a copy?" — a question about shared vs independent objects. Master aliasing here in pure Python, and that warning becomes readable instead of terrifying.

3.4 Dynamic typing: names have no type — objects do

What. Python is dynamically typed: a name (x) has no type at all — it can point at an int now and a str later. Only objects carry types, and type compatibility is checked at runtime, when each operation executes. Contrast statically typed languages (C, Java, Rust): each variable is declared with a fixed type (int x;) enforced at compile time — x = "hi" is rejected before the program ever runs.

Why dynamic typing exists. Flexibility and speed of expression: one function can process ints, floats, or Decimals without overloads; exploratory code doesn't pause for declarations; duck typing ("if it quacks like a DataFrame…") enables generic, reusable tools. The price: type mistakes surface during execution (possibly in production, on row 9,000,001) instead of at compile time — mitigated professionally with tests, type hints, and runtime validation (Chapters 11/23).

Intuition + analogy. Static typing is a labeled parking bay ("compact cars only" — enforced at the gate). Dynamic typing is an unlabeled bay with a smart attendant: anything may park, but each operation checks suitability on the spot ("can I tow this with a car hook? no? TypeError!"). Python is additionally strongly typed: it refuses nonsense rather than silently coercing ("5" + 5 → TypeError, unlike JavaScript's "55"). Dynamic ≠ sloppy: checks happen late, but they happen strictly.

dynamic typing + introspection 
x = 10                  # x → int object. The NAME has no type.
print(type(x))          # <class 'int'> — the OBJECT's type
x = "ten"               # retied → str object. Perfectly legal.
print(type(x))          # <class 'str'>
print(isinstance(x, str))   # True — the PREFERRED type check
print(isinstance(True, int))  # True! bool subclasses int (Ch. 4)
<class 'int'> <class 'str'> True True

Type checking done right: prefer isinstance(x, T) over type(x) == T — it respects inheritance (a bool passes isinstance(x, int); subclasses of your classes pass too) and accepts tuples (isinstance(v, (int, float))). Even better, document expectations with type hints (def mean(xs: list[float]) -> float, Chapters 11/23): hints don't enforce at runtime, but tools (mypy, IDEs) catch mistakes while you type — recovering much of static typing's safety without losing flexibility.

⚠️ Common mistake: checking type when you should check behaviorif type(x) == list: … rejects tuples, subclasses, and lazy sequences that would all work fine. Pythonic code checks capability (duck typing: just iterate and let failures raise) or uses isinstance with abstract types. Reserve strict checks for true boundaries (parsing external data, public APIs).

3.5 Naming: rules, conventions, and why names are a user interface

What — the hard rules (grammar). Names consist of letters, digits, and underscores; must not start with a digit; are case-sensitive (Age ≠ age); and must not be keywords (if, for, class, … — see keyword.kwlist). Unicode letters are allowed (café = 1 works) but ASCII is the professional norm.

Why conventions matter more than rules. Names are the user interface of your code: readers (and interviewers) judge clarity from names before reading logic. Python's conventions (PEP 8, Chapter 23) let any Pythonista instantly classify a name:

🚫 Never shadow builtinslist = [1,2], str = "x", id = 5, sum = 0 rebind names the whole language relies on — subsequent list("ab") / str(3) calls explode with bewildering TypeError: 'list' object is not callable. If you inherit such code, del list restores the builtin. Linters (Ruff, Chapter 23) flag this automatically — one more reason to use them.

3.6 Type conversion: casting across the divides

What. Conversion (casting) builds a new object of a target type from a source value: int(x), float(x), str(x), bool(x), list(x). It never mutates the source (sources may be immutable anyway) — it manufactures.

Why explicit conversion exists. Strong typing (§3.4) refuses implicit leaps ("5" + 5 → TypeError) because silent coercion hides bugs. Explicit casts force you to declare intent at every boundary — especially the external-data boundary, where everything arrives as strings (CSV fields, user input, JSON values) and must be converted deliberately, with failure handling (Chapter 14).

conversion rules + traps 
print(int("42"), float("3.5"), str(99))  # 42 3.5 99 — the happy path
print(int(3.9))      # 3 — TRUNCATES toward zero (not round! use round(3.9))
print(int(-3.9))     # -3 — toward zero (math.floor gives -4)
print(bool(0), bool(""), bool("False"))  # False False True(!) — non-empty str is truthy
print(list("abc"))   # ['a', 'b', 'c'] — str is iterable (Ch. 6)
# int("3.5") → ValueError! (int() won't parse decimals) — chain instead:
print(int(float("3.5")))  # 3
42 3.5 99 3 -3 False False True ['a', 'b', 'c'] 3
⚠️ Conversion traps (all common in data work)int("3.5") → ValueError (parse float first) · int(None) → TypeError, float("abc") → ValueError (validate-then-convert, Ch. 14–15) · int(3.9) truncates silently (rounding is round()) · bool("False") is True (any non-empty string!) — parse flags with explicit comparison (s.strip().lower() == "true"), never bool(s).

📊 Data-Science connection. "Convert at the boundary" is the load-bearing rule of Chapters 15 and 25: the moment external strings enter your program, convert to int/float/date once, centrally, with error collection — then analyze clean typed data. Scattered conversions mean scattered crashes and silent corruption.

3.7 Unpacking, swapping, and augmented assignment (binding in action)

binding idioms 
a, b = 1, 2       # unpack: right side packs to tuple (1,2), then binds
a, b = b, a       # SWAP: right side evaluated FIRST → (2,1), then bound. No temp!
first, *rest = [1, 2, 3, 4]  # starred: first=1, rest=[2,3,4]
print(a, b, first, rest)
n = 10
n += 5            # augmented:rebind to n+5 → 15 (for immutables: new object)
print(n)
lst = [1]
alias = lst
lst += [2]        # ⚠️ for LISTS: += mutates IN PLACE (alias sees it!) — unlike lst = lst + [2]
print(lst, alias) # [1, 2] [1, 2]
2 1 1 [2, 3, 4] 15 [1, 2] [1, 2]

Why += differs by type. Augmented assignment calls the in-place method if it exists (list.__iadd__ extends in place) and falls back to x = x + value (rebinding) otherwise. So += on ints/strings rebinds (new object), but on lists mutates (same object, aliases affected). This asymmetry is a genuine language wart — now you know exactly when each happens, and Chapter 5 revisits it with the full operator story.

3.8 Interview questions

Q1: == vs is? When is 'is' correct?
== compares values (via __eq__); is compares identity (same object in memory). [1] == [1] is True; [1] is [1] is False. is is correct for singletons — is None (always), is True/False (rarely). Never for numbers/strings (interning is an implementation detail).
Q2: Mutable vs immutable — define, exemplify, and explain why dict keys must be immutable.
Immutable (int/str/tuple/frozenset/None) can't change in place — "changes" rebind to new objects. Mutable (list/dict/set) can — aliases observe it. Dicts hash keys to buckets; a key mutating after insertion would hash elsewhere, corrupting lookups. Hence hashability requires (deep) immutability.
Q3: Is Python statically or dynamically typed? Strongly or weakly? Trade-offs?
Dynamically typed (names untyped; objects carry types checked at runtime) and strongly typed (no silent nonsense coercions — "5"+5 raises). Trade-off: fast, flexible expression vs runtime-surfaced type errors; professionals compensate with tests, type hints + mypy, and boundary validation.
Q4: What does `x = y` do? What does `x = x + 1` do for an int vs `xs.append(1)` for a list?
x = y binds x to y's object — no copy. x = x + 1 on an int creates a new int and rebinds (old untouched). xs.append(1) mutates the existing list in place (no rebinding; all aliases see it). Draw the balloon diagram — interviewers love it.
Q5: Why is `bool("False")` True, and how do you parse boolean strings correctly?
Truthiness of strings depends on emptiness, not content — any non-empty string is truthy. Parse explicitly: s.strip().lower() in ("true", "1", "yes"). Never bool(user_string).
