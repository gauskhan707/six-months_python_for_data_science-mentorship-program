Control flow

Conditional Logic

▾

What/why. Conditionals let programs decide: execute different code for different data. if/elif/else evaluates conditions top-down and runs the first True branch — at most one branch ever runs. Combined with truthiness (every object's inherent True/False nature, §4.4) and short-circuiting (§5.5), conditions stay expressive without verbosity. This chapter also teaches the design of branching: guard clauses that flatten nesting, the ternary for value-choices, and match for structural dispatch.

9.1 if / elif / else: first-True-wins (with execution traces)

What. if COND: opens a chain; zero or more elif COND: alternatives follow; an optional else: catches "nothing matched". Semantics: test each condition in order; execute the first True branch's block; skip everything else in the chain — including later conditions (which never even evaluate).

grading chain, traced 
score = 82
if score >= 90:        # 82>=90? No → skip block AND move on
    grade = "A"
elif score >= 80:      # 82>=80? YES → run block, EXIT whole chain
    grade = "B"
elif score >= 70:      # NEVER TESTED (chain already exited!)
    grade = "C"
else:                   # skipped (a branch ran)
    grade = "F"
print(grade)  # B
B

Step-by-step. Condition 1 False → its block skipped, chain continues. Condition 2 True → block runs (grade = "B"), chain exits immediately — condition 3 is never evaluated (prove it: put 1/0 in an elif after a True branch — no crash!). else runs only when no condition was True. Consequences: (1) order matters — put the most specific/highest-threshold first (testing >= 80 before >= 90 would swallow all A-students into B!); (2) overlapping conditions make later branches dead code — a linter-flagged smell.

order matters: the swallowed-A bug 
def grade_bad(s):
    if s >= 80:      # ❌ catches 95 too — everything ≥80 is "B"!
        return "B"
    elif s >= 90:    # DEAD CODE — unreachable (any ≥90 already returned)
        return "A"
    return "F"

def grade_good(s):
    if s >= 90:      # ✅ specific first, general later
        return "A"
    elif s >= 80:
        return "B"
    return "F"

print(grade_bad(95), grade_good(95))  # B A — same conditions, different ORDER
B A

Nesting (and its limits). if blocks can contain further ifs for two-dimensional decisions — but each level multiplies the reader's mental state (2 levels = 4 paths, 3 = 8…). Rule: 2 levels occasionally, 3 levels = refactor (guard clauses §9.4, lookup tables, or extracted functions).

nested: outer gate, inner detail 
age, member = 25, True
if age >= 18:            # outer: which price TABLE?
    if member:            # inner: which ROW?
        price = 8
    else:
        price = 12
else:
    price = 5
print(price)  # 8
8

9.2 Truthiness mastery: the complete rulebook

What. In boolean context (if, while, and/or/not, ternary, filter), Python calls bool(obj): False for the falsy list, True otherwise. Falsy — the complete, exact list: False, None, numeric zeros (0, 0.0, 0j, Decimal(0), Fraction(0)), empties ("", b"", [], {}, set(), frozenset(), range(0), ()), and class instances whose __bool__ returns False or __len__ returns 0. Everything else — including "False", "0", [0], {"a": 0}, generators, and all custom objects by default — is truthy.

idiomatic conditions vs verbose traps 
items, name, age, resp = [], "Ali", 0, "y"
if items: print("has items")       # ✅ idiomatic — NOT len(items) > 0
else: print("empty cart")
if name: print("named")            # ✅ — NOT name != ""
if age is not None:                # ✅ 0 is VALID data! NEVER `if age:` here
    print("age known:", age)
if resp in ("y", "yes"):           # ✅ — NOT == "y" or "yes" (always-True bug!)
    print("confirmed")
if (n := len(items)) == 0:         # walrus when you need the value too
    print(f"cart has {n} items")
empty cart named age known: 0 confirmed cart has 0 items
⚠️ The five truthiness traps (memorize)① if x == True: → if x: (and == True fails for truthy non-bools like 1… actually 1 == True is True via int-equality — but "a" == True is False while if "a": passes! — inconsistent, hence banned). ② if age/count/qty: when zero is valid → is not None. ③ if s == "a" or "b": always True → in ("a","b"). ④ bool(user_string) for flags (§3.6 — "False" is truthy!). ⑤ Generators are always truthy (even empty ones — truthiness doesn't consume!) — test emptiness with next(gen, sentinel), never if gen:.

9.3 Combining conditions: and/or/not + De Morgan + readability

compound conditions, done readably 
age, member, banned = 25, True, False
# ✅ Positive, grouped, short-circuited (cheap tests first!):
if age >= 18 and member and not banned:
    print("welcome, member")
# De Morgan's laws — push NOT inward by flipping and↔or:
#   not (A and B) == (not A) or (not B)
#   not (A or B)  == (not A) and (not B)
x = 5
print(not (x > 0 and x < 10))     # False
print(not (x > 0) or not (x < 10))  # False — same (De Morgan)
# Readability: name complex conditions!
is_working_age = 18 <= age < 65   # chained comparison (§5.4)
is_eligible = is_working_age and member and not banned
if is_eligible:
    print("eligible")
welcome, member False False eligible

Best practices. Order and-operands cheap-first, likely-to-fail-first (short-circuit skips the expensive rest: if cheap(x) and costly(x):). Prefer positive conditions (if valid: over if not invalid: — negation taxes every reader). Name any condition needing a comment — the name is the comment. Parenthesize mixed and/or (precedence §5.3).

9.4 Guard clauses: flatten the pyramid of doom

What. A guard clause handles an edge case with an early return/continue/raise at the top, leaving the main logic flat. It inverts nesting: instead of "if valid: [20 lines] else: error", write "if invalid: error-and-exit; [20 flat lines]".

❌ Pyramid of doom (3 levels, happy path buried)
def process(rows):
  if rows:
    if valid(rows):
      if len(rows) < MAX:
        return analyze(rows)
      else: return "too many"
    else: return "invalid"
  else: return "empty"
✅ Guards (flat, happy path last and obvious)
def process(rows):
  if not rows: return "empty"
  if not valid(rows): return "invalid"
  if len(rows) >= MAX: return "too many"
  return analyze(rows)
Each line eliminates one case; survivors reach the goal.

Why guards win. Readers process one eliminated case per line instead of holding nested context; each error sits beside its condition (no scrolling to match elses); adding a new case is one line, not re-indentation surgery. Apply the same shape to loops (if bad: continue) and validation (if bad: raise … — Chapter 14).

9.5 Ternary + dispatch tables + match

Ternary (A if COND else B) chooses between two values (not blocks):

ternary: value-choice, not control flow 
score = 78
status = "pass" if score >= 60 else "fail"   # ✅ one value-choice
print(status)
label = "even" if score % 2 == 0 else "odd"
print(f"{score} is {label}")
# Nested ternary — legal but SMELLY (use if/elif for 3+ outcomes):
grade = "A" if score >= 90 else ("B" if score >= 80 else "C")
print(grade)  # C
# Dispatch TABLE beats long elif-chains for value mapping:
fmt_handlers = {"csv": "parse commas", "json": "parse braces", "xml": "parse tags"}
print(fmt_handlers.get("json", "unknown format"))  # parse braces — no chain at all!
pass 78 is even C parse braces

Structural matching (match/case, 3.10+). For shape-based dispatch — different types/structures/patterns, with variable binding:

match: dispatch + destructuring 
def describe(value):
    match value:
        case None:
            return "missing"
        case True | False:          # OR-pattern (bool BEFORE int — §4.4!)
            return "flag"
        case int() | float():       # TYPE pattern
            return "number"
        case {"name": str(n)}:      # MAPPING pattern + bind n
            return f"user {n}"
        case [first, *rest]:        # SEQUENCE pattern + bind
            return f"list starting {first} (+{len(rest)} more)"
        case _:
            return "something else"

for v in [None, True, 3.5, {"name": "Ali"}, [1, 2, 3], "hi"]:
    print(repr(v), "→", describe(v))
None → missing True → flag 3.5 → number {'name': 'Ali'} → user Ali [1, 2, 3] → list starting 1 (+2 more) 'hi' → something else

When each. Ternary: one condition, two values, fits on a line. Dict-dispatch: many fixed keys → values/functions (data-driven, extensible without code changes). match: shapes/types/structures with binding (parsers, ASTs, API responses, command routers). if/elif: general boolean logic. Nested ternaries and match for two plain booleans are both over-engineering — match the tool to the shape.

9.6 DS-flavored branching + debugging conditions

realistic data checks 
def bucket_age(age):
    if age is None:                 # missing FIRST (None breaks comparisons!)
        return "unknown"
    if not isinstance(age, (int, float)) or isinstance(age, bool):
        return "invalid"            # bool excluded: True is 1 ( §4.4)!
    if age < 0 or age > 130:
        return "implausible"
    if age < 13:
        return "child"
    if age < 20:
        return "teen"
    return "adult"                  # flat guards — no elif needed with returns!

print([bucket_age(a) for a in [None, True, -5, 8, 16, 30, "x"]])
['unknown', 'invalid', 'implausible', 'child', 'teen', 'adult', 'invalid']
🛠️ Debugging conditionsWrong branch taken? (1) Print the condition values, not your assumptions: print(f"{age=!r}, {type(age)=}") (!r shows hidden spaces/quotes). (2) Test each sub-condition separately. (3) Suspect types: "25" >= 18 → TypeError in Py3 (no str↔int comparison — convert first!). (4) Suspect None (None > 0 → TypeError — guard None first, as above).

9.7 Interview questions

Q1: How does if/elif/else execute? Why does order matter? What never evaluates?
Top-down, first-True-branch-wins, at most one runs. Order matters because earlier branches swallow overlapping cases (§9.1's swallowed-A demo — dead code below). Conditions after a True branch never evaluate (side effects skipped — exploitable for guards, dangerous if you relied on them).
Q2: List all falsy values. Why is `if items:` better than `if len(items) > 0:`? What's the generator exception?
False, None, numeric zeros, empty str/bytes/containers, range(0), __bool__/__len__-falsy objects. if items: is shorter, faster (no call), and generic. Exception: generators are always truthy regardless of emptiness — probe with next(g, sentinel).
Q3: What are guard clauses and why do professionals prefer them?
Early-exit handling of edge cases (return/continue/raise) that flattens nesting. Benefits: one case per line, errors beside conditions, happy path prominent at the end, new cases = one line. The alternative pyramid buries logic and complicates diffs.
Q4: Ternary vs if/else vs dict-dispatch vs match — when each?
Ternary: single value-choice on one line. if/else: general logic/blocks. Dict-dispatch: fixed key→value/function mapping (data-driven, no chain). match: structural patterns with binding (types, shapes, sequences, mappings). Nested ternaries and match-for-booleans are smells.
