Performance with Python

▾

What/why. Slow code has causes, not vibes — and the first law is MEASURE FIRST: hunches about hotspots are wrong ~90% of the time (profilers exist because intuition fails). This chapter's ladder: ① Algorithm/structure (O(n²)→O(n), list→set — 1000× wins), ② Vectorize/push loops to C (NumPy/pandas/C-builtins — 100×), ③ Lazy/stream (O(n)→O(1) memory — enables scale), ④ Cache/memoize (recompute→lookup), ⑤ Parallelize (GIL-aware: threads for I/O, processes for CPU) — and ⑥ don't (readable code that meets its budget is done — premature optimization is the root of evil). Targets set the game: is this a 1-second script or a 24/7 service?

24.1 Measure first: timeit + perf_counter + cProfile (instruments, exact)

the three instruments + their jobs 
import time, timeit, cProfile, pstats, io

# ① timeit: MICRO-benchmark snippets fairly (repeats + disables GC + best-of):
t_join = timeit.timeit("''.join(str(i) for i in range(1000))", number=200)
t_plus = timeit.timeit("s=''\nfor i in range(1000): s += str(i)", number=200)
print(f"join: {t_join:.3f}s  plus-loop: {t_plus:.3f}s  → join wins ~{t_plus/t_join:.0f}×")

# ② perf_counter: MACRO-time blocks in real code (monotonic, ns resolution):
start = time.perf_counter()
total = sum(range(1_000_000))
print(f"sum(1M): {time.perf_counter()-start:.4f}s → {total}")

# ③ cProfile: FIND the hotspot (function-level stats — NEVER guess where time goes!):
def work():
    return {i: i*i for i in range(5000)}
buf = io.StringIO()
cProfile.run("work()", sort="cumulative", stream=buf) if False else None  # (see note)
# Real usage:  python -m cProfile -s cumulative script.py  →  per-function table
print("profile rule: optimize the TOP cumulative row (excl. builtins you can't change)")
join: 0.042s plus-loop: 0.310s → join wins ~7× (varies — join always wins) sum(1M): 0.0120s → 499999500000 profile rule: optimize the TOP cumulative row (excl. builtins you can't change)

Instrument discipline. timeit for comparing snippets (fair repeats; report best-of, not mean — noise only inflates). perf_counter for timing stages in real runs (log per-stage timings in pipelines — free production telemetry!). cProfile for finding hotspots (sort cumulative; ignore {built-in} noise; drill into YOUR top rows). Re-profile after every change (fixes relocate bottlenecks — yesterday's #2 is today's #1). Never micro-tune unmeasured code — that's astrology, not engineering.

⚠️ Benchmarking trapsOne run (noise! repeat) · tiny N (constant factors dominate — test realistic sizes) · caching between runs (first-call effects — warm up) · time.time() (wall-clock jumps — use perf_counter) · optimizing what profiles say is 1% (Amdahl: 100× on 1% = 1% total!).

24.2 Big-O for practitioners: the growth table + the usual crimes

Growthn=10³n=10⁶Name + example
O(1)11Constant: dict/set lookup, append, index
O(log n)~10~20Log: bisect, balanced-tree ops
O(n)10³10⁶Linear: single pass, sum, max, map
O(n log n)~10⁴~2×10⁷Linearithmic: sorted() — the price of order
O(n²)10⁶10¹² ✖Quadratic: nested loops over same data (THE crime)
THE crime (O(n²) membership) → THE fix (O(n) set) 
import time
allowed = list(range(3000))
probes = list(range(0, 6000, 2))
t0 = time.perf_counter(); slow = [p for p in probes if p in allowed]; t1 = time.perf_counter()
allowed_set = set(allowed)
t2 = time.perf_counter(); fast = [p for p in probes if p in allowed_set]; t3 = time.perf_counter()
print(f"list-membership: {t1-t0:.3f}s  set-membership: {t3-t2:.4f}s  same={slow == fast}")
# 9M ==-checks vs 3000 hashes — ~1000× at n=3000, INFINITE gap as n grows (O(n²)→O(n)).
list-membership: 0.086s set-membership: 0.0001s same=True (varies — 100–1000× typical)

Crime blotter (recognize on sight). x in list inside a loop (→ set!) · dedupe-by-scan (→ dict/set) · list.insert(0, x) / pop(0) in loops (→ deque) · string += in loops (→ join) · df.append in loops (→ collect + one concat — pandas Part 3!) · re-sorting per query (→ sort once, bisect per query) · nested loops over the same collection (→ index one side into dict/set first). Each is a structure fix — one line, orders of magnitude.

24.3 Push loops to C: builtins + comprehensions + vectorization preview

the speed ladder (same sum-of-squares) 
import timeit
N = 2000
t_loop = timeit.timeit("s=0\nfor i in range(N): s += i*i", globals={"N": N}, number=50)
t_comp = timeit.timeit("sum(i*i for i in range(N))", globals={"N": N}, number=50)
t_map  = timeit.timeit("sum(map(lambda i: i*i, range(N)))", globals={"N": N}, number=50)
print(f"loop: {t_loop:.3f}s  genexpr: {t_comp:.3f}s  map+lambda: {t_map:.3f}s")
print("ladder: explicit-loop (slowest, bytecode/step) < genexpr/builtin (C-accelerated sum) < numpy (C loop, no per-item boxing — Part 3!)")
print("(map+lambda ≈ loop: lambda re-adds per-item Python cost — operator (§20.4) or genexpr instead!)")
loop: ...s genexpr: ...s map+lambda: ...s (ratios vary; genexpr beats loop ~1.5–2×; numpy would beat both ~50×)

Why C-wins exist. Every Python-level operation pays interpreter overhead (bytecode dispatch, object boxing, refcounting — §3.2) per item. Builtins/comprehensions run their inner machinery in C (tight loops, no boxing): sum(genexpr) boxes items but accumulates in C. NumPy (Part 3) removes boxing too (typed arrays, vectorized C loops — 50–100× over Python loops). The ladder rule: fewer Python-steps per item = faster — but readability gates every climb (a clear loop beating its budget stays a loop!).

24.4 Memory: generators + streaming + __slots__ (O(n) → O(1))

list vs generator footprint (the enabling win) 
import sys
N = 200_000
lst = [i*i for i in range(N)]
gen = (i*i for i in range(N))
print(f"list: {sys.getsizeof(lst)/1024:.0f} KiB  generator: {sys.getsizeof(gen)} bytes")
print("math: list pays ~8B pointer + int-object (~28B) per item (~7MB here); generator pays a FRAME (~100B) total.")
print("rule: STREAM whenever you consume once (§19.5 pipeline!); MATERIALIZE only to reuse/sort/len/index.")
# tracemalloc (find the LEAK, not just the size):
#   import tracemalloc; tracemalloc.start() → run → tracemalloc.get_traced_memory() → snapshot.compare_to()
# __slots__: many small objects (millions of rows-as-objects) — drop per-instance __dict__:
class Point:
    __slots__ = ("x", "y")     # fixed fields, no __dict__ (~40-60% smaller per instance!)
    def __init__(self, x, y):
        self.x, self.y = x, y
list: ... KiB generator: ... bytes (list ~1000× the generator — exact bytes vary)

Memory discipline. Stream single-pass flows (Ch. 15/19 pipelines scale to ∞ rows at constant RAM). Release big refs promptly (del/scope-exit — CPython refcounts free immediately, §3.2). Prefer iterators across stage boundaries (map/filter/islice — §20.3). Suspect a leak? tracemalloc snapshots diffed across iterations name the growing allocation site (usually: appending cache with no bound, or listeners/handlers never removed).

24.5 Caching + parallelism: reuse work, then multiply workers (GIL-aware!)

Cache (Ch. 20's lru_cache, strategic). Recompute→lookup for pure, repeated, hashable-arg calls (parsed configs, compiled regexes — re caches internally!, fib-style recursion — §11.6/20.4). Bound it (maxsize) on wild inputs; never cache IO/time/random. Parallelism (GIL map). CPython's GIL serializes Python bytecode across threads — so: threads for I/O-bound (network/disk waits release the GIL — concurrent.futures.ThreadPoolExecutor, 10–100× throughput on fetches) vs processes for CPU-bound (separate interpreters, separate GILs — ProcessPoolExecutor, ~N× on N cores; pays pickling + startup). NumPy/pandas ops release the GIL internally (vectorized code parallelizes differently — Part 3). Async (asyncio) = cooperative I/O concurrency (huge fan-out, one thread — beyond Part 1's scope; know the name).

executor map (same interface, different engines) 
from concurrent import futures

def fetch(url):
    return f"data-of-{url}"          # stand-in for requests.get (I/O-bound → THREADS)

urls = ["a", "b", "c", "d"]
with futures.ThreadPoolExecutor(max_workers=4) as pool:
    print(list(pool.map(fetch, urls)))     # 4 concurrent fetches (GIL released while waiting!)

def heavy(n):
    return sum(i*i for i in range(n))      # CPU-bound → PROCESSES (shown single-call here)
print(heavy(100000))
# with futures.ProcessPoolExecutor() as pool: list(pool.map(heavy, [...]))  # needs __main__ guard (Ch. 16!) + picklable fns

24.6 Interview questions

Q1: "My Python is slow" — your exact process?
Measure-first: reproduce at realistic N → profile (cProfile cumulative) → top row is the suspect → classify (algorithm/structure? Python-loop? memory? recompute?) → fix at that level (set/dedupe·builtin/genexpr·stream·cache) → re-profile (bottlenecks relocate!) → stop at budget. Never micro-tune unmeasured; Amdahl governs (100× on 1% ≈ nothing). Cite a real crime→fix (membership list→set).
Q2: GIL: what, and how does it shape threads vs processes vs async vs NumPy?
GIL serializes Python-bytecode execution per interpreter → threads don't parallelize CPU work (fine for I/O — waits release it; ThreadPool for fetches). CPU parallelism: processes (separate GILs; pickling cost) or C-extensions releasing the GIL (NumPy vectorized ops). Async: single-threaded cooperative I/O fan-out (not parallelism — concurrency). Choose by bound: I/O→threads/async, CPU→processes/vectorize.
Q3: List vs generator trade-offs — when must you materialize?
Generators: O(1) memory, lazy, single-pass (no len/index/reuse/sort) — for pipelines consumed once (§19.5). Materialize (list) to: iterate repeatedly, index/slice, len(), sort, or debug-inspect. Size math: pointer+object per item vs fixed frame (~1000× at scale). Default streaming at boundaries; materialize deliberately with a comment (WHY reuse needs it).

24.7 Exercises

Level 1 · Understand
  1. timeit 5 idiom pairs (join vs +=, set vs list membership, genexpr vs loop, in dict vs in list, sort-once+bisect vs re-sort); report ×-factors.
  2. Profile a 3-stage script with cProfile; identify the top row; verify "hunch vs profile" differ (write both down first!).
  3. getsizeof ladder: int/str/tuple/list/dict/set/generator of N items; explain per-item costs (§3.2 boxing).
Level 2 · Apply
  1. Take an O(n²) script (nested membership/dedupe); fix via set/dict-index; show timings at 3 sizes proving the growth change (plot optional).
  2. Convert a list-pipeline to a generator pipeline; prove O(1) memory (tracemalloc peak) at 10× rows; keep outputs identical (assert).
  3. ThreadPool a 20-URL fetch (simulated latency); show wall-time ≈ slowest-single (not sum); then explain why CPU work wouldn't scale the same (GIL demo).
Level 3 · Interview
  1. "1B-row log, 8GB RAM, 5-minute budget": architecture memo (streaming stages? chunking? which structure per stage? where processes? what telemetry?) with Big-O + memory math per stage.
  2. Find a REAL slowdown in your code via profiling (not guessing); fix; present before/after profile excerpts + the one-line lesson (crime→fix pattern name).
