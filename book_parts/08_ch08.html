8
Collections

Tuples, Sets and Dictionaries

▾

What/why. Lists carry ordered, changeable data — but three other shapes dominate real code: tuples (fixed records that must never change), sets (unique membership + group mathematics), dicts (label → value lookups — the backbone of records, configs, counters, caches, and JSON). Under the hood, sets and dicts are hash tables: near-instant O(1) average lookup by hashing immutable keys. This chapter teaches each collection deeply — mechanics, methods, idioms, traps — then gives you the decision framework professionals use to choose between all four.

8.1 Tuples: immutable records with superpowers

What. A tuple is an ordered, immutable, heterogeneous sequence — a list whose slots are frozen at birth. Literals use parens (optional!): (1, 2), 1, 2 (same thing), () empty, (5,) one-tuple (the comma is mandatory). Hashable iff all elements are hashable; slightly smaller and faster than lists.

Why tuples exist (four jobs). (1) Fixed records — coordinates, RGB, name+age pairs: the shape is the meaning, and immutability guarantees nobody reshapes it. (2) Dict keys / set members — {(0,0): "start"} (lists can't — unhashable). (3) Safe multi-returns — return (quotient, remainder) / divmod. (4) Unpacking/swapping — x, y = point, a, b = b, a (the machinery runs on tuples).

Intuition. If a list is a whiteboard list (grows, shrinks, reorders), a tuple is an engraved plaque: made once, read forever. Functions return plaques ("here are your two results, exactly two, in this order") and dicts file plaques as labels.

tuples: creation, unpacking, star, swap, keys 
point = (10, 20)       # parens optional: point = 10, 20 (same object!)
one = (5,)             # trailing comma REQUIRED — (5) is just int 5
empty = ()
print(point, one, empty, type((5)))
x, y = point           # UNPACK: bind each slot (count must match!)
a, b = 1, 2
a, b = b, a            # swap: right packs to (2,1) FIRST, then unpacks → 2 1
first, *rest = (1, 2, 3, 4)   # starred: first=1, rest=[2,3,4] (a LIST!)
*head, last = (1, 2, 3, 4)    # star anywhere: head=[1,2,3], last=4
print(x, y, a, b, first, rest, head, last)
grid = {(0, 0): "start", (2, 3): "goal"}  # tuples as keys (lists CAN'T)
print(grid[(2, 3)])
print((1, 2) + (3,), (1, 2) * 2)  # concat/repeat BUILD NEW tuples (immutable!)
(10, 20) (5,) () <class 'int'> 10 20 2 1 1 [2, 3, 4] [1, 2, 3] 4 goal (1, 2, 3) (1, 2, 1, 2)

Step-by-step (the swap). a, b = b, a: the right side packs current values into a temporary tuple (2, 1) before any binding happens; then the left side unpacks positionally: a → 2, b → 1. No temp variable, no data loss — atomic by construction. The starred target (*rest) always collects into a list (mutable, since length varies) — even when unpacking a tuple.

More examples — records, returns, iteration:

tuples as records + named access preview 
users = [("Ali", 30, "Lahore"), ("Zara", 25, "Karachi")]
for name, age, city in users:   # unpack IN the loop — self-documenting
    print(f"{name} ({age}) from {city}")
def stats(xs):
    return min(xs), max(xs), sum(xs)/len(xs)  # return ONE tuple of three
lo, hi, avg = stats([4, 1, 9])
print(lo, hi, avg)
# Tuple methods: only TWO exist (immutables need no mutators!)
t = (1, 2, 2, 3)
print(t.count(2), t.index(3))  # 2 3
# Many plaques → upgrade to NAMED records (readability):
from collections import namedtuple
User = namedtuple("User", ["name", "age"])
u = User("Ali", 30)
print(u, u.name, u[1])  # User(name='Ali', age=30) Ali 30 — tuple + attribute access!
Ali (30) from Lahore Zara (25) from Karachi 1 9 4.666666666666667 2 3 User(name='Ali', age=30) Ali 30
⚠️ The shallowness loophole (from §3.3)t = ([1], [2]): the tuple's arrows are frozen (t[0] = x → TypeError) but the pointed-to lists are mutable (t[0].append(99) works!). True immutability needs immutable elements. Such tuples are also unhashable (hash(t) → TypeError) — so they can't be dict keys. Rule: hashable ⟺ deeply immutable (for builtins).
💡 Tuple vs list — the real ruleHeterogeneous + fixed shape → tuple (("Ali", 30) — position means something). Homogeneous + variable length → list ([88, 92, 75] — all "scores"). When a tuple record grows past ~3 fields or gets passed around, graduate to namedtuple (above) or a @dataclass (Chapter 18) — named fields beat user[2] everywhere.

8.2 Sets: uniqueness, membership, and group mathematics

What. A set is an unordered, mutable collection of unique, hashable elements. Literals use braces: {1, 2, 3}; empty set is set() ({} is a dict!). Backed by a hash table: membership/add/remove average O(1). Elements must be immutable (hashable) — no lists/dicts inside.

Why sets exist (three jobs). (1) Deduplication — set(messy_list) collapses repeats. (2) Fast membership — x in big_set is O(1) vs O(n) list scan (§5.6's 1000× proof). (3) Group math — union/intersection/difference/symmetric-difference as operators (| & - ^) and methods — answering "in both?", "only in A?", "in exactly one?" directly.

Intuition. A set is a bouncer with a perfect guest list: no duplicates get in, entry checks are instant (hash the name, check the bucket), and comparing two parties' lists (who's at both? who only made one?) is the whole job. Order? The bouncer doesn't do order — sets are unordered (iteration order is arbitrary and version-dependent; never rely on it).

set operations: the complete map 
ds = {"Ali", "Zara", "Omar"}
ml = {"Zara", "Hina", "Omar", "Daniyal"}
print(sorted(ds | ml))   # UNION: everyone
print(sorted(ds & ml))   # INTERSECTION: in both → Zara, Omar
print(sorted(ds - ml))   # DIFFERENCE: only in ds → Ali
print(sorted(ds ^ ml))   # SYMMETRIC DIFF: in exactly one
print({"a"} < {"a", "b"}, {"a"} <= {"a"})  # proper subset / subset
print(ds.isdisjoint({"X"}))  # True — no overlap at all
# Mutating methods (in-place, return None — §7.3's rule!):
ds.add("Hina"); ds.discard("Ghost")   # discard: no error if absent (vs remove()!)
ds.update(["X", "Y"])                 # add many
print(sorted(ds))
# Dedup that PRESERVES order (sets don't!) — the pro idiom:
items = ["b", "a", "b", "c", "a"]
print(list(dict.fromkeys(items)))  # ['b', 'a', 'c']

Step-by-step (why dict.fromkeys dedups in order). dict.fromkeys(items) builds {"b": None, "a": None, "c": None} — dicts ignore duplicate keys (keeping first-insertion position) and preserve insertion order (guaranteed 3.7+). list(…) takes the keys → ['b','a','c']. O(n), order-stable — strictly better than list(set(items)) whenever order matters (which is usually).

sets in data jobs: overlap, coverage, invalid detection 
required = {"name", "age", "email"}
row = {"name": "Ali", "age": 30}
missing = required - row.keys()      # keys-view supports set ops!
print("missing:", missing)           # {'email'}
valid_cities = {"Lahore", "Karachi", "Islamabad"}
seen = {"Lahore", "Paris", "Karachi"}
print("invalid:", seen - valid_cities)  # {'Paris'} — instant data validation
print("coverage:", sorted(seen & valid_cities))  # sorted: set ORDER varies per run!
# frozenset: the IMMUTABLE (hashable!) set — for set-valued dict keys / constants:
fs = frozenset([1, 2, 2])
print(fs, hash(fs) is not None)  # frozenset({1, 2}) True
missing: {'email'} invalid: {'Paris'} coverage: ['Karachi', 'Lahore'] frozenset({1, 2}) True
⚠️ Set trapsIteration order is arbitrary (never index/assume — sort first for stable output) · {} is a dict; set() is empty set · elements must be hashable ({[1]} → TypeError) · remove(x) raises if absent (use discard for "ensure absent") · mutating methods return None (s = s.add(x) → None disaster, same as sort).

8.3 Dictionaries: the king of data structures

What. A dict maps hashable keys to arbitrary values: {"name": "Ali", "age": 30}. Mutable, insertion-ordered (guaranteed 3.7+), average O(1) get/set/delete via hashing. Keys: almost always str/int/tuple (hashable immutables). Values: anything, including nested dicts/lists.

Why dicts exist (five jobs). (1) Records — user["name"] beats user[0] (labels beat positions). (2) Lookups/mappings — id→name, code→price. (3) Counters/histograms — word→count (or Counter). (4) Caches/memo tables — args→result (lru_cache automates this, Ch. 20). (5) JSON-shaped data — APIs, configs, documents (Chapter 15: JSON ↔ dict is nearly 1:1).

Intuition: hashing in 60 seconds. hash("name") scrambles the key into a huge integer; modulo table-size picks a bucket; the entry lives there. Lookup re-hashes and jumps straight to the bucket — no scanning. That's the O(1): compute where it must be, instead of searching. Collisions (two keys, one bucket) are resolved internally (open addressing in CPython) — you never see them, except as the reason worst-case is O(n) but average-case O(1). And now the key rule is obvious: if a key mutated after insertion, its hash would point to the wrong bucket — hence keys must be immutable.

dict essentials: access, defaults, merge, remove, views 
user = {"name": "Ali", "age": 30}
print(user["name"])               # direct — KeyError if missing (loud = good sometimes)
print(user.get("city"))           # None — safe probe (never raises)
print(user.get("city", "Lahore")) # default when missing (NOT stored)
user["city"] = "Lahore"           # add / overwrite (same syntax!)
user.setdefault("tags", []).append("vip")  # get-or-CREATE, then use — atomic idiom
print(user)
user.update({"age": 31, "vip": True})  # bulk merge (overwrites age, adds vip)
print(user.pop("vip"))            # remove AND return → True
print(user.pop("ghost", None))    # safe pop with default (no KeyError)
del user["city"]                  # remove (KeyError if missing)
# VIEWS: live windows, not copies — reflect later changes, support set ops on keys:
print(user.keys(), user.values(), user.items())
user["new"] = 1
print(user.keys())  # dict_keys([...,'new']) — the view UPDATED (it's live!)
Ali None Lahore {'name': 'Ali', 'age': 30, 'city': 'Lahore', 'tags': ['vip']} True None dict_keys(['name', 'age', 'tags']) dict_values(['Ali', 31, ['vip']]) dict_items([('name', 'Ali'), ('age', 31), ('tags', ['vip'])]) dict_keys(['name', 'age', 'tags', 'new'])

Step-by-step (setdefault). user.setdefault("tags", []): key missing → store the default [] under "tags" and return it; the .append("vip") then mutates that stored list. One lookup, atomic, no if "tags" not in user dance. Contrast .get(k, []) + append: appends to a temporary that's discarded — the classic "my append vanished" bug. (For grouping/counters at scale: collections.defaultdict / Counter below.)

counting + grouping: manual, then the stdlib upgrades 
votes = ["a", "b", "a", "c", "a"]
counts = {}                                   # manual counter (know the pattern!)
for v in votes:
    counts[v] = counts.get(v, 0) + 1
print(counts)  # {'a': 3, 'b': 1, 'c': 1}
from collections import Counter, defaultdict
print(Counter(votes))           # Counter({'a': 3, 'b': 1, 'c': 1}) — + most_common!
print(Counter(votes).most_common(2))  # [('a', 3), ('b', 1)]
groups = defaultdict(list)      # missing key → auto-creates list()!
for w in ["apple", "ant", "bear", "bee"]:
    groups[w[0]].append(w)      # no setdefault needed
print(dict(groups))  # {'a': ['apple', 'ant'], 'b': ['bear', 'bee']}
# Merge (3.9+): | creates NEW, |= updates in place:
print({"a": 1} | {"b": 2})      # {'a': 1, 'b': 2}
{'a': 3, 'b': 1, 'c': 1} Counter({'a': 3, 'b': 1, 'c': 1}) [('a', 3), ('b', 1)] {'a': ['apple', 'ant'], 'b': ['bear', 'bee']} {'a': 1, 'b': 2}
🚫 Never resize a dict while iterating itfor k in d: del d[k] → RuntimeError: dictionary changed size during iteration. (Changing values of existing keys is fine; adding/removing keys is not.) Fixes: iterate list(d.items()) snapshot, collect keys-then-delete, or build a new dict: d = {k: v for k, v in d.items() if keep(k, v)}.
⚠️ More dict trapsd[k] on missing → KeyError (choose deliberately: loud [] vs safe .get vs creating .setdefault) · .get(k, []).append(x) appends to garbage (use setdefault/defaultdict) · views are live (snapshot with list() before sorting/storing) · update returns None (same mutator rule) · inversion loses data on duplicate values ({"a":1,"b":1} → {1:"b"} — last wins silently!).

8.4 Hashing, equality contracts, and performance

The contract (interview-grade). (1) Objects that compare == must have equal hashes (hash(1) == hash(1.0) == hash(True) — and indeed {1, 1.0, True} collapses to {1}!). (2) Hashes must be stable for the object's lifetime as a key — hence immutability. (3) Unequal objects should usually differ in hash (collisions only cost speed, never correctness).

Debugging lens. "My key is right there but lookup fails!" → the key's hash or equality differs from what you think: hidden whitespace ("Lahore " vs "Lahore"), type mismatch (1 vs "1" — note 1 == "1" is False so hashes differ), float dust, or (custom classes) broken __hash__/__eq__ (Chapter 18). Diagnose: print(repr(key)) for both sides, compare type()s.

8.6 Interview questions

Q1: Why must dict keys be immutable/hashable? What breaks otherwise?
Dicts hash keys to storage buckets. A key mutating after insertion would hash to a different bucket — lookups would miss an entry that's "right there", and the table would corrupt. Hence: immutable keys (str/int/tuple-of-immutables) with stable hashes. Demo: try {[1]: "x"} → TypeError: unhashable.
Q2: d[k] vs .get() vs .setdefault() vs defaultdict — when each?
d[k]: missing is a bug — crash loudly (fail fast). .get(k, default): missing is routine — probe without storing. .setdefault: get-or-create atomically (grouping into plain dicts). defaultdict(factory): repeated get-or-create with a factory (cleaner grouping/counters at scale).
Q3: How do dicts achieve O(1) lookup? What's the worst case?
Hash the key → bucket index → jump directly (open addressing in CPython). Average O(1); worst case O(n) under pathological hash collisions (all keys one bucket) — vanishingly rare with real hashes; CPython also randomizes string hashing (PYTHONHASHSEED) against collision attacks.
Q4: set vs list for membership testing — complexity and the crossover?
in on list: O(n) scan. On set: O(1) hash. For repeated lookups, convert once (set(big), O(n) build) then enjoy O(1) each — §5.6 measured ~2500× at n=200k. One-off single lookup on small data: list is fine (no build cost).
