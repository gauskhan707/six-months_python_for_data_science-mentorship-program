Design · style

Functional Python

▾

What/why. Functional style treats computation as pipelines of transformations over data — map (transform each), filter (keep some), reduce (fold many to one) — favoring pure functions (same input → same output, no mutation) and immutable flow (new collections, not in-place edits). Python is deliberately multi-paradigm: it offers the functional toolkit (map/filter/reduce, any/all, sorted(key=), itertools, functools, operator) while blessing comprehensions and loops as equals. The honest stance this chapter teaches: borrow functional tools where they clarify, keep explicit code where it reads better — with precise rules for each call.

20.1 map / filter / reduce: the trinity (with comprehension twins)

What. map(f, it): lazy iterator of f(x) per item. filter(p, it): lazy iterator of items where p(x) is truthy (filter(None, it) drops falsies!). functools.reduce(f, it, init): folds left — acc = f(acc, x) per item, starting at init (or the first item if omitted — empty + no-init → TypeError). All lazy except the final reduce (must consume everything to fold).

trinity + twins + reduce mechanics 
from functools import reduce
nums = [1, 2, 3, 4, 5]
print(list(map(lambda x: x * 2, nums)))        # [2,4,6,8,10] — twin: [x*2 for x in nums]
print(list(filter(lambda x: x % 2 == 0, nums)))  # [2,4] — twin: [x for x in nums if ...]
print(reduce(lambda a, b: a + b, nums, 0))     # 15 — twin: sum(nums)!
# reduce, step by step (acc=0): f(0,1)=1 → f(1,2)=3 → f(3,3)=6 → f(6,4)=10 → f(10,5)=15
print(list(filter(None, [0, 1, "", "a", [], [2]])))  # [1, 'a', [2]] — drop FALSIES!
print(list(map(str.strip, ["  a ", "b  "])))   # NAMED fn — map's best look (no lambda!)
print(list(map(int, ["1", "2"])))              # [1, 2] — builtin as mapper
# Multi-iterable map (stops at shortest — zip-like!):
print(list(map(lambda a, b: a + b, [1, 2], [10, 20, 30])))  # [11, 22]
[2, 4, 6, 8, 10] [2, 4] 15 [1, 'a', [2]] ['a', 'b'] [1, 2] [11, 22]

The verdict rule (memorize). map(f, …)/filter(p, …) with an existing named function/builtin (map(str.strip, lines), map(int, cells)) — clean, lazy, idiomatic. With a lambda — the comprehension twin almost always reads better ([x*2 for x in xs] beats map(lambda x: x*2, xs) on every axis: named intent, no lambda tax, familiar). reduce: reach for the named builtin first (sum/min/max/any/all/math.prod) — genuine folds (operator.mul products pre-3.8, function composition, merging) earn reduce.

20.2 any / all: the quantifiers (short-circuiting!)

existential + universal checks, lazily 
nums = [1, 2, 3, 4, 5]
print(any(x > 4 for x in nums))   # True — stops AT 5 (short-circuits!)
print(all(x > 0 for x in nums))   # True — must verify ALL
print(any([]), all([]))            # False True — vacuous truth (all of nothing = True!)
# Probe the short-circuit (watch what RUNS):
def probe(x):
    print(f"  check {x}")
    return x > 2
print(any(probe(x) for x in [1, 2, 3, 4]))  # checks 1,2,3 then STOPS (4 never probed)
# Real uses: validation gates
rows = [{"age": 30}, {"age": -1}]
print("any invalid:", any(r["age"] < 0 for r in rows))
print("all have age:", all("age" in r for r in rows))
True True False True check 1 check 2 check 3 True any invalid: True all have age: True

Why all([]) == True. Vacuous truth: "every element satisfies P" with no elements has no counterexample — True (matches math/logic; also makes all(checks) the correct default-pass gate). Beginners expect False — now you know, and can explain it in interviews (it's asked!).

20.3 itertools: the lazy combinator library (infinite-safe)

itertools working set 
import itertools
print(list(itertools.chain([1, 2], "ab", (3,))))   # flatten ONE level → [1,2,'a','b',3]
print(list(itertools.islice(range(10**9), 5)))     # lazy take (infinite-safe!) → [0..4]
print(list(itertools.islice(range(10), 2, 8, 2)))  # islice(iter, start, stop, step)
print(list(itertools.islice(itertools.count(10, 2), 4)))  # count is INFINITE — islice takes 4!
print(list(itertools.repeat("x", 3)))              # ['x','x','x'] (repeat() alone = infinite!)
print(list(itertools.islice(itertools.cycle("AB"), 5)))  # ABABA (cycle infinite — islice takes 5!)
# groupby: groups CONSECUTIVE runs (SORT first for global grouping!)
data = sorted(["ant", "apple", "bear", "bee", "avocado"])
for key, grp in itertools.groupby(data, key=lambda w: w[0]):
    print(key, "→", list(grp))
# Combinatorics (CAREFUL: sizes explode — n=100 pairs = 4950, triples = 161700!):
print(list(itertools.combinations([1, 2, 3], 2)))  # pairs, no repeat, order-free
print(list(itertools.product("AB", "12")))         # cartesian: A1 A2 B1 B2
[1, 2, 'a', 'b', 3] [0, 1, 2, 3, 4] [2, 4, 6] [10, 12, 14, 16] ['x', 'x', 'x'] ['A', 'B', 'A', 'B', 'A'] a → ['ant', 'apple', 'avocado'] b → ['bear', 'bee'] [(1, 2), (1, 3), (2, 3)] [('A', '1'), ('A', '2'), ('B', '1'), ('B', '2')]

groupby` trap (bites everyone once). It groups consecutive equal keys — unsorted input yields multiple fragments per key (['a1','b1','a2'] → a:[a1], b:[b1], a:[a2] — TWO 'a' groups!). For global grouping: sorted first (O(n log n)) or defaultdict(list) (O(n), any order — §8.3). Also: groups are lazy iterators sharing the source — consume each fully before advancing (materialize with list(grp) immediately, as above).

20.4 functools + operator: memoize, partialize, and ditch lambdas

lru_cache + partial + operator (lambda killers) 
import functools, operator
@functools.lru_cache(maxsize=None)   # MEMOIZE: cache arg→result FOREVER (pure fns only!)
def fib(n):
    return n if n < 2 else fib(n-1) + fib(n-2)
print(fib(100))                      # instant (each n computed once — §11.6)
print(fib.cache_info())              # hits/misses/size — PROVE the memoization!
# cachetools-style caution: args must be HASHABLE (no lists!); unbounded growth on wild inputs → maxsize=N + TTL externally

def power(base, exp):
    return base ** exp
square = functools.partial(power, exp=2)   # FREEZE some args → new fn (no lambda!)
print(square(9))                           # 81 — partial(power, exp=2)(9) = power(9, exp=2)
from operator import itemgetter, attrgetter, methodcaller, mul
rows = [{"n": "b", "v": 2}, {"n": "a", "v": 1}]
print(sorted(rows, key=itemgetter("v")))   # sort by ['v'] — faster + clearer than lambda!
print(sorted("ba", key=methodcaller("upper")))  # call .upper() per item
print(functools.reduce(mul, [1, 2, 3, 4], 1))  # 24 — operator.mul beats lambda a,b!
print(list(map(operator.add, [1, 2], [10, 20])))  # [11, 22] — no lambda anywhere
354224848179261915075 CacheInfo(hits=98, misses=101, maxsize=None, currsize=101) 81 [{'n': 'a', 'v': 1}, {'n': 'b', 'v': 2}] ['a', 'b'] 24 [11, 22]

lru_cache` contract (exact). Caches by argument equality+hash — same args → same object returned (identity too!). Requires: pure function (no side effects — they'd run once then vanish!), hashable args (tuples/frozensets, not lists/dicts), bounded input space (else maxsize + eviction). Thread-safe (locked). cache_info()/cache_clear() for ops. Poison risk: caching functions of time/random/IO freezes the first answer — a real production bug shape.

20.5 Purity, immutability flow, and when loops win (the judgment)

✅ Functional wins
any/all gates · sorted(key=itemgetter) · lru_cache on pure recursion · itertools lazy pipelines (chain/islice/count) · map with named fns · operator over lambdas · Counter/groupby reductions · immutable transforms (new = f(old)) in concurrent/pipeline code.
❌ Explicit wins
Side effects (I/O, mutation, logging) · complex per-item branching · early exit with cleanup · per-item try/except · map/filter with lambda (comprehension twin!) · reduce where a builtin exists · anything a teammate re-reads twice. Readability > paradigm purity — always.

Purity pays in data pipelines. Pure stages (cleaned = clean(raw), no mutation) are: trivially testable (assert clean(x) == y), safely reorderable/parallelizable, replayable (re-run any prefix), and cacheable (lru_cache on deterministic transforms). Impurity (in-place mutation, globals, prints) breaks all four. Architecture: pure core, imperative shell — I/O at edges (read inputs, write outputs), pure transforms inside (Project 5's Dataset methods model this).

20.6 Interview questions

Q1: map/filter vs comprehensions — when is each better? What about reduce?
map/filter win with existing named functions/builtins (map(str.strip, lines) — lazy, clean). With lambda, comprehension twins almost always read better. reduce loses to named builtins (sum/min/max/any/math.prod) — genuine folds (composition, merging, custom monoids) earn it. Laziness: map/filter return iterators (single-use!); comprehensions build (reusable).
Q2: Why is all([]) True? Give a production use where that default matters.
Vacuous truth — no counterexample exists. Matters: validation gates (all(checks) with zero checks = pass — correct for "nothing to violate"), permission conjunctions, and CI "all jobs green" with zero jobs. any([]) = False symmetrically ("something found" needs evidence).
Q3: lru_cache contract: requirements, risks, introspection?
Requires pure fn + hashable args + bounded input space. Risks: caching time/IO/random (frozen answers!), unbounded growth (use maxsize), unhashable args (TypeError), memory leaks via long-lived caches. Introspect: cache_info() (hits/misses), cache_clear(). Thread-safe. (§20.4 demo.)

  1. Time fib(30) ± lru_cache with cache_info() evidence; explain the exponential→linear collapse via call counts.
  2. Lazy pipeline: chain two files' lines → filter errors → islice first 10 — all O(1); prove no full read (instrument with probes).
  3. Replace 5 lambdas with operator (itemgetter/attrgetter/methodcaller/add/mul); measure readability delta (lines + re-reads).
Level 3 · Interview
  1. Implement my_map/my_filter/my_reduce as lazy generators from scratch; match builtin edge semantics (empty + no-init TypeError for reduce).
  2. Design a pure-core/imperative-shell refactor of an I/O-mixed script: draw the boundary, name each pure function, and show the before/after test-ability (write 3 tests impossible before).
