Abstraction

Scope and Namespaces

▾

What/why. A namespace is a mapping of names → objects: a function's locals, a module's globals, the builtins, a class's attributes, a comprehension's scope. Scope is the region of code where a namespace is directly visible. Python resolves every name reference with one rule — LEGB: search Local → Enclosing → Global → Built-in, stopping at the first hit. This single rule explains shadowing, UnboundLocalError, why global/nonlocal exist, why loop variables leak but comprehension variables don't, and why closures work. Short chapter, foundational payoff.

12.1 Namespaces: kinds, lifetimes, and how to inspect them

What — the five namespace kinds:

  • Local: a function call's frame — parameters + body bindings. Born at call, dead at return (except cells captured by closures — §11.7). Inspect: locals().
  • Enclosing: outer function frames surrounding nested defs — the closure capture zone. Lifetimes extend while closures reference them.
  • Global (= module): a module's top-level bindings. "Global" really means module-global — each module has its own (that's why import doesn't collide across files). Lives for the process. Inspect: globals().
  • Built-in: len, print, str, … (+ exceptions, True/False/None). Always last in line. Inspect: dir(__builtins__).
  • Attribute/class namespaces: obj.attr, class bodies — resolved by the attribute protocol (Chapter 18), not LEGB. (LEGB covers bare names; dotted names are a different lookup.)
namespaces are dicts (mostly) — inspect them 
x = "global"
def outer():
    x = "enclosing"
    y = 1
    print("locals in outer:", sorted(locals().keys()))  # ['x', 'y'] (+ maybe inner later)
    def inner():
        x = "local"
        print("inner sees:", x)   # L wins → 'local'
    inner()
    print("outer sees:", x)       # E → 'enclosing'
outer()
print("module sees:", x)          # G → 'global'
print("globals has x:", "x" in globals())
print("len" in dir(__builtins__)) # B → True
locals in outer: ['x', 'y'] inner sees: local outer sees: enclosing module sees: global globals has x: True True

12.2 The assignment rule (the sentence that explains UnboundLocalError)

What — the rule, exact: reading a name searches LEGB at runtime; but any assignment to a name anywhere in a function body makes that name local everywhere in that function — decided at compile time, before a single line runs. So reading it before the local assignment executes → UnboundLocalError (a subclass of NameError), even if a global of the same name exists and even if the assignment sits in a branch that never runs.

UnboundLocalError: cause + three fixes 
count = 0
def bad():
    print(count)   # 💥 UnboundLocalError — 'count' is LOCAL here (assigned on next line)
    count = 1      # ...this assignment, ANYWHERE in body, poisons the whole body
# bad()  # uncomment to see: UnboundLocalError: cannot access local variable 'count'

# Fix 1 — global: rebind the MODULE name (works, but smelly — §12.4)
def fix_global():
    global count
    count += 1     # rebinding needs the declaration...

def fix_param(c):  # Fix 2 — PURE (best): pass in, return out. No shared state.
    return c + 1

bag = [0]
def fix_mutate():  # Fix 3 — MUTATE without rebinding: no declaration needed!
    bag.append(1)  # lookup finds global; .append mutates (no assignment to 'bag')
    print("len:", len(bag))

fix_global(); print(count)   # 1
count = fix_param(count); print(count)  # 2
fix_mutate()
1 2 len: 2

Step-by-step (the += case). count += 1 means count = count + 1: the right side reads (LEGB → would find global… but the name is already classified local at compile time because of the assignment) → read of unbound local → UnboundLocalError. global count reclassifies the name as module-level for the whole body — reads and writes both hit the module. bag.append(1) involves no assignment to bag — pure LEGB read finds the global list, method mutates it. (Still avoid globals — §12.4.)

nonlocal (closures' write key, §11.7). nonlocal n reclassifies a name as enclosing-function-level (nearest enclosing binding, compile-checked — error if none exists). Three rebinding scopes, three declarations: local (default), enclosing (nonlocal), module (global). There is no "nonlocal-or-global" fallback — Python demands you say which.

12.3 Shadowing, leaks, and comprehension scope

shadowing (legal, confusing) + the leak asymmetry 
len = "oops"          # ⚠️ shadows the BUILTIN in this module (works until you call len()!)
print(len)            # 'oops' — G shadows B (LEGB!)
del len               # restore sanity (deletes module binding; builtin visible again)
print(len("abc"))     # 3 — phew

for i in range(3):    # for-targets bind in the ENCLOSING function scope...
    pass
print("leaked:", i)   # 2 — ...and LEAK after the loop (§10.5)
# Comprehension targets do NOT leak (own implicit scope since Py3):
vals = [j * 2 for j in range(3)]
try:
    print(j)
except NameError as e:
    print("no leak:", e)
# Same for generator expressions, dict/set comprehensions, lambda params, except-as (deleted after!):
try:
    1 / 0
except ZeroDivisionError as e:
    print("caught:", e)
try:
    print(e)  # NameError! `except ... as e` is DELETED at block end (avoids cycle refs)
except NameError:
    print("except-target cleaned up ✓")
oops 3 leaked: 2 no leak: name 'j' is not defined caught: division by zero except-target cleaned up ✓

Why the asymmetry. for/while/if create no scope in Python — only def, class, lambda, comprehensions/generator-expressions, and except-as (deleted after) manage bindings specially. Rationale: flat is simple; functions are the unit of isolation. Practical fallout: reuse of loop names (i, row) across distant loops in one long function causes stale-value bugs — another reason functions stay short (Ch. 11/23).

⚠️ Shadowing trapsModule name shadows builtin (list/str/id/sum/type — §3.5's ban) · parameter shadows global (reader confusion — rename one) · local shadows enclosing (usually a bug — did you forget nonlocal?) · from x import * silently shadows (Chapter 16's ban). Linters flag all four automatically.

12.4 Best practices: why global is a smell (and what replaces it)

Why global hurts. It creates hidden coupling: the function's behavior depends on invisible module state (untestable in isolation, order-dependent, un-reusable across threads/contexts, refactor-hostile — every reader must hold the whole module in mind). Globals also defeat the "fresh frame per call" isolation (§11.1) that makes functions trustworthy.

Replacements, by situation: shared config → parameters with defaults or a frozen dataclass passed around (Ch. 18); accumulated state → return values (total = process(total, row)), closures (§11.7), or a class (Ch. 18); module-level constants → UPPER_SNAKE globals that are read, never rebound (reading globals is harmless — only rebinding needs global and creates the smell); true singletons/caches → explicit objects with clear ownership. Legitimate global uses exist (lazy one-time init, registry patterns) — they're rare, documented, and wrapped in functions.

12.5 Interview questions

Q1: State LEGB with one example per level, and say what happens on total miss.
Local (frame: params/body) → Enclosing (outer defs, nearest first) → Global (module top) → Built-in (len/print/…) → NameError. Example: nested defs each binding x plus a module x plus builtin use — innermost wins at each print (§12.1 code). Note: attribute lookups (obj.x) bypass LEGB entirely (Chapter 18's protocol).
Q2: Why does `x += 1` on a global fail without `global`, but `lst.append(1)` works?
x += 1 is x = x + 1 — an assignment, making x local at compile time; the right-side read then hits an unbound local → UnboundLocalError. lst.append(1) assigns nothing to lst — LEGB read finds the global, method call mutates it. (Both patterns should usually be replaced by params/returns.)
Q3: Loop variables leak but comprehension variables don't — explain.
for creates no scope — targets bind in the enclosing function (leaking after). Comprehensions/generator-expressions get an implicit function-like scope (Python 3+), so their targets are local and vanish after. Same reason except … as e is deleted after its block (plus cycle-GC hygiene).
