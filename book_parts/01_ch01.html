Foundations

What Python Actually Is

▾

The one-paragraph truth this whole book rests on. A computer's processor only executes machine code — patterns of bits that open and close transistors. Humans cannot think in bits, so we write source code in a programming language, and a translator converts it into something the machine can run. Python is a high-level, interpreted, dynamically typed, garbage-collected language: its interpreter reads your source, compiles it to an intermediate bytecode, and executes that bytecode step by step on a virtual machine. This chapter unpacks every word of that paragraph — slowly, visually, and completely — because every mystery you will ever meet in data work (why loops are slow, why NumPy is fast, why versions matter, why environments exist) traces back to this execution model.

🗺️ How to read this chapterEach concept below follows the book's teaching pattern: What → Why → Intuition → Analogy → Visual → Syntax → Smallest example → Execution trace → More examples → Mistakes → Debugging → Best practices → Data-Science link. Chapter-level interview questions, exercises, mini-challenge, and summary close the chapter. Don't skim — this mental model pays rent in every later chapter.

1.1 Programming: exact instructions for a literal machine

What. Programming is the act of writing exact, unambiguous, ordered instructions that a machine follows deterministically — same instructions, same starting state, same result, every time. A program is a text file (or collection of files) containing those instructions. Running a program means the machine reads the instructions and performs them.

Why it exists. Computer hardware is generic: a CPU only knows a few hundred primitive operations (add two numbers, move bytes between memory locations, compare values, jump to another instruction). Hardware cannot "average customer ages" or "recognize cats" — it can only grind through primitives billions of times per second. Software — programs — is what converts that raw generic speed into specific, useful behavior without rewiring a single circuit. The same laptop becomes a spreadsheet, a video game, or a neural-network trainer depending purely on which program it runs.

Intuition. Imagine hiring the world's fastest intern — one who executes ten billion simple actions per second — but who has zero common sense, zero memory of intent, and zero tolerance for ambiguity. Tell this intern "fetch the red folder" and they freeze: which shelf? what is red, precisely? what does fetch mean — bring here, or open? Programming is learning to speak to this intern: breaking every desire into steps so small and so precise that even a mindless executor gets them right. The computer does precisely what you wrote — never what you meant. Every bug you will ever meet is a gap between those two things.

Real-world analogy: the recipe and the robot cook. A human recipe says "sauté the onions until soft." A human cook fills in the gaps (which pan? how much oil? what heat? what does 'soft' mean?). A robot cook needs: take pan P (mass 800 g) → place on burner 2 → set burner to 1,800 W → pour 15 ml oil → wait until oil temperature ≥ 160 °C → add 200 g diced onion (5 mm cubes) → stir every 20 s → stop when 90% of pieces deform under 2 N pressure. That exhausting level of explicitness is programming. High-level languages like Python are pre-agreed shorthand so you can write closer to "sauté until soft" while the toolchain expands it into robot-grade steps.

Smallest possible example. The smallest meaningful program has three parts — input, transformation, output:

the smallest honest program 
age = 30          # input/state: remember the value 30 under the name 'age'
double = age * 2  # transformation: compute something new
print(double)     # output: show it to the human
60

Step-by-step execution. Line 1: the interpreter creates the integer object 30 in memory and binds the name age to it (Chapter 3 explains this binding deeply). Line 2: it looks up age (finds 30), multiplies by 2 (creates 60), binds the name double. Line 3: it calls the builtin print function, which converts 60 to the characters 6, 0 and writes them to standard output (your screen), plus a newline. Nothing magical — three explicit steps, executed top to bottom.

More examples — programs are everywhere, at every scale:

  • A 3-line script that renames 2,000 downloaded files — a program.
  • A Jupyter notebook exploring a dataset with plots — a program (a stateful, cell-ordered one — §1.9).
  • The Pandas library itself (~500,000 lines of Python/C/Cython) — a program other programs build on.
  • A production ML pipeline retraining nightly on fresh data — a program with scheduling, logging, and monitoring wrapped around it.
⚠️ Common mistake #1: "the computer should know what I mean"Beginners write average = total / count and are angry when count is 0 ("it should just know there's no data!"). The machine knows nothing. Defensive, explicit code — if count == 0: … else: … — is not bureaucracy; it is the job. Chapters 9 and 14 turn this into reflex.
⚠️ Common mistake #2: confusing the program with its outputprint(60) and 60 look identical on screen, but one is an instruction that produces text and the other is a value sitting in memory. Mixing up "showing" vs "computing" causes half of beginner confusion (Chapter 2 and 11 return to this).

Debugging lens. When a program misbehaves, never ask "why is the computer wrong?" — ask "what did I actually tell it to do?" Read your code as the literal intern would: execute each line by hand on paper with a concrete input, tracking every variable's value. This technique — hand-tracing — solves an astonishing fraction of bugs and is the seed of Chapter 22's full workflow.

Best practice. Start every program by writing, in plain words (a comment or a notebook cell), the three answers: what goes in? what comes out? what are the steps in between? If you can't state them in English, you can't state them in Python yet.

📊 Data-Science connection. A data analysis is a program: raw data in → cleaning/transformation steps → findings out. The analysis-as-program viewpoint is why professionals write analyses as re-runnable scripts (same input → same output) instead of point-and-click steps nobody can reproduce. Chapters 15, 25 and the Projects build this habit into muscle memory.

1.2 Programming languages: levels of abstraction

What. A programming language is a formal notation — vocabulary plus grammar rules — for writing programs, together with a translator that converts that notation into machine-executable form. Languages sit on a spectrum from low-level (close to hardware: machine code, assembly) to high-level (close to human thought: Python, R, SQL).

Why levels exist. There is a fundamental trade-off: machine-efficiency vs human-efficiency. Low-level code runs fast and controls hardware precisely, but expressing "average these ages" takes dozens of lines managing registers and memory addresses. High-level code expresses it in one line, at the cost of translation overhead. No single level is "best" — systems combine them (and Python's data stack is the perfect example: you write easy Python; NumPy's internals are hand-tuned C and Fortran).

Intuition + analogy. Think of giving directions. Machine code is turn-by-turn wheel rotations ("rotate left axle 4.2 turns…"). Assembly is street-by-street ("turn left on Main…"). Python is intent-level ("take me to the airport, avoid tolls") — with a very competent driver (the interpreter + libraries) filling in the route. Higher level = less control over the exact route, vastly less effort per trip.

Visual: the same task at three levels. Task: add two numbers and print the result.

LevelWhat it looks likeWho manages memory/registers?

Why this matters for you. Python deliberately buys human speed (fast to write, read, and change) with machine speed (each operation does more hidden work). For data science this trade is overwhelmingly worth it: analyst time costs far more than CPU time, datasets are processed by C-speed kernels anyway (Chapter 24), and most programs wait on data loading, not computation. The skill is knowing where the boundary lies — which this book teaches explicitly rather than leaving as folklore.

💡 Key vocabulary (used all book long)Syntax = grammar rules (violations → SyntaxError). Semantics = meaning of correct code (what it does). Standard library = modules shipped with Python (csv, json, math…). Third-party package = code others wrote that you install (numpy, pandas…). Runtime = everything present while your program executes.

1.3 Compiled vs interpreted: when translation happens

What. Every high-level program must eventually become machine code. When and how that translation happens defines the spectrum. In a compiled language (C, Rust, Go), a compiler translates the entire program to machine code before it ever runs, producing a standalone binary (e.g., .exe). In an interpreted language (Python, JavaScript, R), an interpreter translates and executes the program while it runs — typically line/block by block, with no separate build step visible to you.

Why two approaches exist. Compilation front-loads translation cost for maximum execution speed and early error detection, at the price of a slow edit→compile→run feedback loop and platform-specific binaries. Interpretation buys a fast, flexible feedback loop (edit→run instantly; same code runs anywhere an interpreter exists) at the price of per-execution translation overhead. Data science — exploratory, iterative, "try ten things before lunch" — overwhelmingly favors the interpreted loop.

Analogy: the translated book vs the live interpreter. A compiled program is a book translated to your language before you arrive: translation took months, but now you read at full speed. An interpreted program is a speech with a live interpreter whispering in your ear: no up-front wait, you can interrupt and ask questions (the REPL!), but every sentence passes through a middleman. Python adds a twist (§1.6): it quickly prepares notes (bytecode) before the live interpretation — a hybrid most modern languages share.

Smallest examples. Compiled (C) — two visible steps: gcc prog.c -o prog then ./prog. Interpreted (Python) — one step: python prog.py. That missing build step is the entire day-to-day difference, and it compounds: data scientists re-run analyses hundreds of times a day.

⚠️ Common mistake: "interpreted means no compilation at all"Wrong — and interviewers probe exactly this. CPython always compiles your source to bytecode first (§1.6); "interpreted" means you never run a compiler manually and the final execution interprets bytecode on a VM. Java and C# live in the same hybrid middle (source → bytecode → VM/JIT). Pure line-by-line interpretation without any bytecode is rare today.
✅ Data-Science connectionThe interpreted loop is why exploration is joyful (tweak → re-run in a second), and compilation is why the fast parts are fast (your one-line df.groupby(...).mean() drops into precompiled C loops over millions of rows). Chapter 24 makes this division of labor quantitative.

1.4 Python: the language, its philosophy, its versions

What. Python is a high-level, interpreted, dynamically typed, garbage-collected programming language created by Guido van Rossum (first release 1991) and developed openly ever since. "Python" properly names three related things: the language specification (grammar + meaning), the reference interpreter program you run, and the ecosystem (standard library + community packages). Context tells you which is meant.

Why it exists / design philosophy. Python optimizes for readability and developer productivity: code should read as close to English as a formal notation allows, there should be one obvious way to do things, and complexity should be hidden until needed. This is written down as the Zen of Python (import this) — "Readability counts", "Explicit is better than implicit", "Simple is better than complex". These aren't slogans; they explain real decisions: indentation-defined blocks (no brace noise), significant whitespace enforcing visual structure, batteries-included standard library, and errors that say what happened in words.

Python 2 vs 3 — the one historical fact worth knowing. Python 3 (2008) fixed deep design mistakes (notably Unicode text handling) in ways that broke backward compatibility with Python 2. The community split for a decade; Python 2 reached end-of-life in January 2020. Today "Python" unambiguously means Python 3. If you ever inherit Python 2 code (print x without parentheses is the tell), migrate it — do not learn Python 2.

Versions within Python 3 — why they matter. Minor releases arrive yearly and add syntax and standard-library features your code may depend on. An interviewer asking "which Python do you use?" is checking professional awareness. Use 3.11+ (3.11/3.12/3.13) for this book.

1.5 Interpreter, runtime, CPython, and the other Pythons

What — four terms, precisely separated:

  • Python, the language: the specification — what for, def, is mean. A document and a test suite, not a program.
  • Python, the interpreter: the program you invoke (python / python3) that reads .py files and carries them out. It contains a parser, a compiler (source→bytecode), and a virtual machine.
  • The runtime: everything present while your program runs — the interpreter process, loaded modules, the memory manager, the garbage collector, the call stack. "Runtime error" means: the code parsed fine, but something failed during execution (bad value, missing file, zero division). This is why tracebacks say where execution died, not where the typo is.
  • CPython: the standard, official, reference implementation of Python — written in C, downloaded from python.org, installed by default almost everywhere. When anyone says "install Python", they mean CPython. This book assumes CPython unless stated.

Why multiple implementations exist. Because the language (specification) is separate from any implementation (program that runs it), different teams built Python-runners optimized for different niches:

ImplementationWritten in / runs onWhy it exists
CPython (the default)CReference behavior; biggest ecosystem; what you use
PyPyPython (+ JIT compiler)Much faster pure-Python loops via just-in-time compilation; alternative GC
MicroPython / CircuitPythonC, stripped downRuns on microcontrollers (ESP32) with kilobytes of RAM

Intuition. Think "English" (language) vs "a specific translator" (implementation): Shakespeare in English can be performed by many theater companies — same script, different staging, pacing, and special effects. CPython is the Royal Shakespeare Company: the definitive staging everyone compares against. Practical note: libraries with C extensions (NumPy, Pandas) are built and tested primarily against CPython — another reason data science standardizes on it.

💡 Interview-ready distinctions"CPython is the reference implementation of the Python language, written in C. The interpreter is the program that executes my code; the runtime is the execution environment — memory manager, GC, loaded modules — in which it runs. Alternatives like PyPy (JIT, faster loops) and MicroPython (embedded) trade compatibility for niche advantages; data science standardizes on CPython because the C-extension ecosystem targets it."

1.6 The execution model: source → tokens → AST → bytecode → virtual machine

What. When CPython runs your file, it passes through five stages — the first three are front-end (understanding your text), the last two are execution:

Figure 1.3 — The CPython pipeline (memorize this)
1 · 📝 Source text (.py) — decoded as UTF-8
↓ lexer (tokenizer)
2 · 🎟️ Tokens — NAME(print), OP((), STRING('Hello'), …
↓ parser
3 · 🌳 AST — Abstract Syntax Tree ("call print with 'Hello'")
↓ compiler (auto + cached in __pycache__)
4 · 🧩 Bytecode — LOAD_NAME, LOAD_CONST, CALL… (.pyc)
↓ Python Virtual Machine: fetch → decode → execute, repeat
5 · ⚙️ Effects — C routines, OS calls, output, memory updates

Stage by stage, with the why:

  • 1 · Decoding. Files store bytes; Python needs characters. CPython decodes .py source as UTF-8 by default (a # coding: … cookie can override — legacy). Wrong encoding → SyntaxError: Non-UTF-8 code before anything else happens.
  • 2 · Lexing. The character stream is chopped into tokens — the smallest meaningful units (names, numbers, strings, operators, indentation markers). This is where "is == one token or two =?" gets decided. You can watch it: python -m tokenize hello.py.
  • 3 · Parsing. Tokens are assembled into an Abstract Syntax Tree encoding grammatical structure ("a call of function print with one constant argument"). All SyntaxErrors are raised here — meaning: if any line has broken grammar, nothing runs, not even the good lines above it. Inspect trees yourself with the ast module (ast.dump(ast.parse('print("Hi")'))).
  • 4 · Compiling to bytecode. The AST becomes bytecode: compact numeric instructions for the virtual machine. CPython caches it as .pyc files under __pycache__/ (keyed by source size + timestamp) so re-running an unchanged file skips stages 1–4. Bytecode is portable (same .pyc runs on Windows/Linux/macOS) but version-specific (3.11 bytecode won't load on 3.12 — the folders are even tagged, e.g. __pycache__/prog.cpython-312.pyc).
  • 5 · The PVM loop. The Python Virtual Machine executes bytecode one instruction at a time: fetch the next instruction, decode what it means, execute it (usually by calling a fast C routine), repeat. The PVM is a stack machine: instructions push values onto an evaluation stack and pop them off to compute — no named registers like real CPUs.

Seeing bytecode yourself — the dis module. "Disassemble" any code to watch stages 4–5 vocabulary:

disassembly of print("Hello") 
import dis
dis.dis('print("Hello")')
# (Exact bytecode varies by Python version — the SHAPE is the lesson:
#  load print, load 'Hello', call it, return. Compare yours!)
(bytecode listing — yours will differ slightly by version; look for LOAD print → LOAD 'Hello' → CALL → RETURN)

Line-by-line (exact names vary slightly by version; the shape is stable): PUSH_NULL/LOAD_NAME print — push the builtin function object print onto the stack (resolved from the builtins namespace). LOAD_CONST 'Hello' — push the string object. PRECALL/CALL 1 — pop 1 argument + the callable, invoke it, push the result (None). RETURN_VALUE — finish this code unit. Each of these steps is one trip around the PVM loop, each implemented as optimized C code.

Stack-machine intuition — trace 2 + 3 * 4 by hand. Bytecode (simplified): LOAD 2, LOAD 3, LOAD 4, MUL, ADD. Walk the stack: push 2 → [2]; push 3 → [2,3]; push 4 → [2,3,4]; MUL pops 3,4 pushes 12 → [2,12]; ADD pops both, pushes 14 → [14]. That push/pop dance is execution. Now you see why tight Python loops are slow (millions of loop-trips, each fetching/decoding/dispatching) and why NumPy wins (one CALL into a C loop that never touches the PVM per element) — Chapter 24's entire argument in one paragraph.

💡 .pyc caching rules (practical)CPython writes __pycache__ only for imported modules, not for the script you run directly. Stale caches are auto-detected (source mtime/size recorded inside the .pyc). You can ignore these folders entirely (git-ignore them) — but their existence proves compilation really happens, and deleting them never breaks anything (they regenerate).
⚠️ Common mistake: "my edit didn't take effect!"Running old behavior after editing usually means: you ran a different file (wrong folder — check with pwd/ls), a different interpreter (wrong venv — sys.executable, Ch. 17), or — rarest — a stale notebook kernel (restart it, §1.9). It is essentially never a stale .pycache.

1.7 Complete trace: what happens when print("Hello") executes

The promise from the chapter title — here it is, end to end. Assume hello.py contains exactly one line, run as python hello.py:

  1. Process start. The OS launches the python executable: CPython initializes — memory allocator, type system, builtin namespace (print, len, …), import machinery, and the sys module (with sys.path including the script's folder first).
  2. Read + decode. CPython opens hello.py, reads its bytes, decodes as UTF-8 → the text print("Hello")\n.
  3. Lex. Text → tokens: NAME('print'), OP('('), STRING('Hello'), OP(')'), NEWLINE.
  4. Parse. Tokens → AST: Expr(Call(func=Name('print'), args=[Constant('Hello')])). Any grammar violation anywhere in the file would abort here, running nothing.
  5. Compile. AST → bytecode (the dis listing above). For a directly-run script this bytecode is not cached to .pyc (only imports are).
  6. Execute on the PVM. The fetch→decode→execute loop runs: resolve print in builtins → create the 'Hello' string object on the heap → CALL invokes the builtin's C implementation → which encodes the text (via sys.stdout's encoding, usually UTF-8) and issues a write system call to file descriptor 1 (standard output), appending \n (the default end). Your terminal emulator renders the bytes as glyphs.
  7. Cleanup + exit. Temporary references are released; objects with zero references are freed immediately (reference counting — interview topic, §1.12 Q5); cyclic garbage is left for the cyclic GC; remaining stdout buffers are flushed; the process exits with status code 0 (success).
Figure 1.4 — The print("Hello") journey
⌨️ python hello.py
↓ init: builtins, sys.path, memory
📖 read bytes → decode UTF-8 → text
↓ lex → parse (SyntaxError gate)
🌳 AST → bytecode (dis listing)
↓ PVM loop: LOAD print, LOAD 'Hello', CALL
🖨️ C builtin → encode → write(1, "Hello\n")
↓ flush, free, exit 0
Hello (on your screen)

Why memorize this trace? Because it is a map of where things can go wrong: file-not-found (step 2), undecodable bytes (2), SyntaxError (4), NameError for print if shadowed (6 — never name a variable print!), UnicodeEncodeError on misconfigured terminals (6), buffering surprises when piping output (7 — python -u / flush=True). Professionals debug by asking which stage failed — you now know the stages.

1.8 Your tools: terminal, editor vs IDE vs notebook

What — the four tools, precisely:

  • Terminal / shell: a text interface to the operating system (cmd/PowerShell on Windows, Terminal + bash/zsh on macOS/Linux). You type commands; the OS obeys. For Python: running scripts (python analysis.py), installing packages (pip install …), managing environments and files. Non-negotiable skill — every professional workflow touches it.
  • Code editor (VS Code, Sublime, Zed): a text editor supercharged for code — syntax highlighting, auto-indent, extensions (Python support, linting, formatting), integrated terminal. Lightweight and fast.
  • IDE — Integrated Development Environment (PyCharm, Spyder): editor + visual debugger + profiler + test runner + refactoring tools + environment manager in one heavy but powerful package.
  • Notebook (Jupyter Notebook / JupyterLab): a browser UI of cells mixing executable code, rich output, plots, and Markdown notes — backed by a kernel (a live Python process holding all state).

Why four tools instead of one. They optimize different phases of work: exploring (notebooks: try, see, plot, narrate), building (editor/IDE: multi-file code, debugging, tests), running reliably (terminal + scripts: automation, pipelines, servers). Professionals use all of them weekly and switch deliberately.

1.9 Scripts vs notebooks: the most important workflow decision

What. A script (.py) is plain text executed top to bottom, fresh process, every run — identical input always produces identical behavior. A notebook (.ipynb) is a JSON document of cells executed in whatever order you click, sharing one long-lived kernel process whose state accumulates invisibly across cell runs.

Why the distinction is career-relevant. Scripts are reproducible, testable, diffable, schedulable: the unit of production. Notebooks are explorable and narratable: the unit of thinking. Catastrophes happen when the two are confused — "but it worked in my notebook!" (because cell 12 ran twice and cell 4 never re-ran after your edit). Know both; use each for its job.

The hidden-state trap, concretely. Notebook cells: [1] x = 10, [2] x = x + 5, [3] print(x). Run 1→2→3: prints 15. Now re-run cell 2 "just to check", then cell 3: prints 20 — but anyone reading top-to-bottom expects 15. The notebook lies: displayed outputs no longer match top-down execution. Multiply by 60 cells, deleted cells, and reordered runs, and you get results nobody — including future-you — can reproduce. The discipline: Kernel → Restart & Run All before trusting or sharing any notebook; if it breaks, fix the order-dependence.

DimensionScripts (.py)Notebooks (.ipynb)

Best practice — the promote-to-script workflow. Explore in notebooks, ship as scripts. When notebook logic works and matters (a cleaning pipeline, a feature computation, anything re-run or shared): move it into tested functions in a .py module, import it back into the notebook, and re-run-all to prove equivalence. This book teaches script-first thinking from Chapter 2 so the promotion feels natural by Chapter 25.

1.10 Installing Python (all platforms) + verifying PATH

What PATH is (the 30-second version). When you type python, the OS searches the folders listed in the PATH environment variable, left to right, and runs the first python it finds. "Python is installed but the terminal can't find it" always means: the installer didn't add Python's folder to PATH, or another python shadows it. Diagnose with where python (Windows) / which -a python python3 (macOS/Linux).

  • Windows: download the 64-bit installer from python.org/downloads → on the FIRST screen tick "Add python.exe to PATH" → Install Now → open a new terminal → python --version. (Microsoft Store Python also exists but causes path/permission quirks — python.org builds are the safe default.)
  • macOS: python.org installer, or brew install python. Note: macOS ships a system python3 for the OS itself — never pip install into it (Chapter 17's virtual environments exist precisely for this).
  • Linux: sudo apt install python3 python3-venv python3-pip (Debian/Ubuntu) or equivalent. Command is usually python3, not python.
  • Data-science bundle (optional): Miniconda (minimal) or Anaconda (everything) ships Python + NumPy/Pandas/Jupyter prebuilt — convenient, heavier, and uses conda environments (same isolation idea as Chapter 17's venv).

1.11 Common mistakes & debugging field guide

❌ Trap 1 — Store/alias limbo (Windows)
Typing python opens the Microsoft Store. Cause: no python.org Python on PATH; Windows' app-execution alias intercepts. Fix: install from python.org with "Add to PATH", restart the terminal, verify with where python.
✅ Habit — always verify the binary
python -c "import sys; print(sys.executable)" tells you exactly which interpreter runs your code. When behavior surprises you, this command is step zero. Chapter 17 builds full environment hygiene on top of it.
❌ Trap 2 — pip installs, python can't import
pip install requests succeeds but import requests fails. Cause: pip and python belong to different installations. Fix: always use python -m pip install … — guarantees the installer targets that interpreter.
✅ Habit — python -m everything
python -m pip, python -m venv, python -m pytest. The -m flag runs a module as part of that interpreter — immune to PATH mixups.
❌ Trap 3 — editing one file, running another
"My change did nothing!" Cause: terminal is in a different folder, or similarly-named files (prog.py vs prog (1).py). Fix: pwd + ls before running; keep one file per concept while learning.
✅ Habit — orient before executing
Before python x.py: confirm folder (pwd), confirm file (ls), confirm interpreter (sys.executable). Ten seconds that prevent thirty-minute mysteries.

1.12 Interview questions (with model answers)

Q1: Is Python compiled or interpreted? Explain precisely.
Both, in a hybrid pipeline: CPython automatically compiles source to bytecode (cached in __pycache__/*.pyc), then the Python Virtual Machine interprets that bytecode via fetch→decode→execute. "Interpreted" means there's no manual build step producing machine code — but compilation absolutely happens. Mention dis to prove it: dis.dis('print("Hi")').
Q2: What is CPython? Name two other implementations and their niches.
CPython is the reference implementation written in C — the default "Python". PyPy uses a JIT for much faster pure-Python loops; MicroPython targets microcontrollers with kilobytes of RAM. Data science standardizes on CPython because NumPy/Pandas C extensions target it.
Q3: Walk me through what happens when you run `python hello.py`.
Process init (builtins, sys.path, memory) → read + UTF-8 decode → lex to tokens → parse to AST (SyntaxError gate — nothing runs if it fails) → compile to bytecode → PVM executes (resolve names, create objects, call C builtins, write to stdout) → flush, free, exit 0. Then narrate the §1.7 print("Hello") trace.
Q4: Scripts vs notebooks — when do you use each?
Notebooks for exploration (inline plots, narrative, fast iteration); scripts for anything re-run, shared, tested, or scheduled (deterministic top-down execution, clean git diffs, pytest). Discipline: Restart & Run All before trusting a notebook; promote working logic into tested modules.
Q5 (advanced preview): How does CPython free memory?
Primarily reference counting: every object tracks how many references point at it; at zero, it's freed immediately. Reference cycles (A→B→A) defeat counting, so a generational cyclic garbage collector (the gc module) periodically finds and frees unreachable cycles. Full depth: Chapters 3 and the Advanced interview section.

1.13 Exercises

Level 1 · Understand
  1. In your own words (2–3 sentences each): source code, bytecode, interpreter, virtual machine, runtime. No copying definitions.
  2. Run the §1.4 sys snippet and the §1.10 verification ritual. Record: version, executable path, and whether python or python3 works.
  3. Explain to a friend why Python needs no manual compile step yet still "compiles". Use the book-vs-live-interpreter analogy.
Level 2 · Apply
  1. dis.dis("x = 1 + 2") and dis.dis("2 + 3 * 4"): annotate every instruction and hand-trace the evaluation stack.
  2. Create hello.py, run it, then create helper.py + main.py (where main imports helper). Compare: which run created __pycache__, and why exactly?
  3. Run python -m tokenize hello.py and ast.dump(ast.parse(open('hello.py').read())). Map three tokens to their AST nodes.
Level 3 · Interview
  1. "Python is slow." Give the precise, fair, interviewer-respecting response: PVM overhead per operation; C kernels for hot paths; I/O-bound vs CPU-bound; developer-time economics; measure-then-vectorize (Ch. 24). Deliver it aloud in 90 seconds.
  2. Your teammate's identical script runs fine for them but crashes for you at import time. List your diagnostic steps in order (interpreter? path? cwd? venv? versions?) and the command for each.
