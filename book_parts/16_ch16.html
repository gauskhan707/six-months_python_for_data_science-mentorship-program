Scale & ecosystem

Modules and Packages

▾

What/why. A module is one .py file — a namespace you can import. A package is a folder of modules forming a dotted namespace (sales_tool.analysis), marked by __init__.py. Imports exist to split programs into understandable, reusable, testable pieces instead of one giant script — and to tap the standard library ("batteries included": csv, json, pathlib, math, datetime, collections, itertools, statistics, argparse, logging…) plus 500k+ third-party packages. This chapter teaches import mechanics completely: forms, search order, the __main__ guard, package layout, and the circular-import trap — so multi-file programs feel inevitable, not magical.

16.1 Import forms: what each binds (exactly)

import forms + namespace effects 
import math                 # binds NAME 'math' → module. Use: math.sqrt(16)
from pathlib import Path    # binds NAME 'Path' → the class. Use: Path("x")
import collections as col   # binds ALIAS 'col' (community: numpy as np, pandas as pd)
from math import sqrt, pi   # binds 'sqrt' + 'pi' directly
from math import sqrt as sq # aliased from-import (dodge collisions)
print(math.sqrt(16), sqrt(25), sq(36), pi, col.Counter("aab"))
# from math import *        # 🚫 NEVER in real code: mystery names, collisions, no traceability
print("module:", math.__name__)          # modules know their names (paths vary by install!)
4.0 5.0 6.0 3.141592653589793 Counter({'a': 2, 'b': 1}) module: math

Step-by-step (from pathlib import Path). ① Import system finds + loads the pathlib module object (executing it once, caching in sys.modules). ② Looks up attribute Path on it. ③ Binds only Path in your namespace (pathlib itself stays unbound — pathlib.Path would NameError!). Contrast import pathlib: binds the module; you reach everything through it (verbose but explicit — the default for stdlib in this book).

Style rules (PEP 8). Imports at the top, grouped: ① stdlib, ② third-party, ③ local — alphabetical within groups, blank line between. One import per line (import os, sys banned). from-imports for names used heavily, plain import for namespaces (and always for modules with common attribute names — os.path beats a bare path). Aliases only for established conventions (np, pd, plt) or genuine collision-dodging.

🚫 from x import * — the four sins① Mystery names: readers can't tell where sqrt came from. ② Silent collisions: two star-imports overwrite each other's names (last wins, no warning). ③ Linter blindness: undefined-name detection breaks. ④ API fragility: upstream additions shadow your names on upgrade. (Packages control it via __all__ — which exists for their interactive convenience, not your code.)

16.2 How Python finds modules: sys.path, sys.modules, and shadowing

What — search order (exact): ① sys.modules cache (already imported? reuse — modules execute once per process). ② The script's directory (or cwd for -c/REPL; the cwd for -m — §16.4!). ③ PYTHONPATH environment entries. ④ Installed distributions (site-packages — your venv's, Chapter 17). ⑤ The standard library. Inspect live: import sys; print("\n".join(sys.path)).

import machinery, observed 
import sys
print("exe set:", bool(sys.executable))  # WHICH python exists (print it raw in YOUR venv check — Ch. 17)
print("path ok:", isinstance(sys.path, list) and len(sys.path) > 0)  # [0] = script dir (or ''/cwd nuances)
import math
print("cached:", sys.modules["math"] is math)  # True — second import reuses, never re-runs
print("stdlib?", "site-packages" not in getattr(math, "__file__", "builtin"))
# Find WHERE a name would come from (diagnose shadowing!):
import importlib.util
print("json found:", importlib.util.find_spec("json") is not None)  # (print the spec raw to see its origin!)
exe set: True path ok: True cached: True stdlib? True json found: True

The shadowing catastrophe. Your script's directory is first on sys.path — so a file named random.py, math.py, csv.py, or email.py in your folder hijacks the stdlib module of that name for every import in the process (including imports inside other libraries!). Symptoms: AttributeError: module 'random' has no attribute 'randint' (your file isn't the stdlib!), ImportError loops. Rule: never name files after stdlib/third-party modules (check: python -c "import NAME" succeeding = taken). Diagnose with print(module.__file__) — if it points at your folder, you've been shadowed.

💡 Modules run ONCE (import caching)import x twice (even from different files) executes x.py once; later imports reuse sys.modules["x"]. Consequences: module-level code is initialization (runs at first import — keep it light/pure!); "reloading" needs importlib.reload(x) (fiddly — stale references linger; prefer restarting the process); circular imports see half-initialized modules (§16.5).

16.3 The __main__ guard: library AND script in one file

What. When Python loads a file, it sets the module-global __name__: to "__main__" if the file is the entry point (run directly: python stats_utils.py), or to the module name if imported (import stats_utils → __name__ == "stats_utils"). The guard if __name__ == "__main__": runs demo/CLI/self-test code only in direct execution — imports stay side-effect-free.

stats_utils.py — the guarded dual-purpose file 
# stats_utils.py
"""Tiny stats helpers (importable + directly runnable)."""

def mean(xs):
    if not xs:
        raise ValueError("mean of empty")
    return sum(xs) / len(xs)

def main():
    import sys
    nums = [float(x) for x in sys.argv[1:]] or [1, 2, 3]
    print("mean:", mean(nums))

if __name__ == "__main__":   # direct run ONLY: python stats_utils.py 4 5 6
    main()                   # import SKIPS this (no prints, no argv parsing, no exit!)

Why without-the-guard hurts. Unguarded script code (prints, file writes, sys.exit, heavy compute, input prompts) runs at import time — slowing every importer, breaking tests (a stray input() hangs pytest!), and executing side effects in contexts that never asked. Professional rule: module top level = definitions + constants only; all action lives in functions, entered via main() + guard (or a real entry point — §16.6).

Anatomy of main(). Parse args → call pure library functions → print/write results → return exit code (int) → raise SystemExit(main()) as the guard body for proper exit statuses (Project 5's CLI does exactly this). Keep main() thin: orchestration only — logic belongs in testable functions (Chapter 23).

16.4 Packages: folders as namespaces + absolute vs relative imports

What. A package is a directory containing __init__.py (executed on first import of anything in the package; keep it tiny: version, key re-exports, nothing heavy) plus modules/subpackages. Dots navigate: sales_tool.analysis.mean_by. (Namespace packages without __init__.py exist (3.3+) for split-across-folders mega-projects — ignore until you need them.)

professional project layout (memorize this shape) 
sales_tool/                    # PROJECT ROOT (has README, requirements, .git)
├── pyproject.toml             # modern metadata+deps (or requirements.txt — Ch. 17)
├── README.md                  # setup + usage (3 commands to green!)
├── sales_tool/                # THE PACKAGE (import sales_tool...)
│   ├── __init__.py            # tiny: __version__, maybe key re-exports
│   ├── readers.py             # load CSV/JSON → Dataset (I/O boundary)
│   ├── analysis.py            # PURE functions (mean_by, totals...) — testable!
│   └── cli.py                 # argparse + main() + __main__ guard (thin shell)
└── tests/
    ├── __init__.py
    └── test_analysis.py       # pytest: imports sales_tool.analysis (Ch. 23)

Absolute (preferred) vs relative (fragile). Absolute: from sales_tool.analysis import mean_by — full path from project root; explicit, greppable, refactor-safe; works everywhere once the root is importable. Relative: from .analysis import mean_by / from ..x import y — relative to the current package; breaks the moment someone runs the file directly (python sales_tool/cli.py → "attempted relative import with no known parent package"). Rule: absolute everywhere; run package code with python -m sales_tool.cli from the root (-m sets up package context + cwd on path — §16.5's table).

__init__.py: tiny and deliberate 
# sales_tool/__init__.py
"""Sales analysis toolkit."""
__version__ = "0.1.0"
from sales_tool.analysis import mean_by  # curated shortcut: sales_tool.mean_by works
__all__ = ["mean_by", "__version__"]     # controls `from sales_tool import *` (still avoid *)

16.5 Circular imports + script-vs--m (the two import riddles)

Circular imports (a imports b, b imports a). At runtime: importing a starts executing it → hits import b → starts executing b → hits import a → finds a half-initialized in sys.modules → b grabs names that don't exist yet → ImportError/AttributeError. Fixes (best first): ① restructure — move shared code to a third module both import (the real fix — cycles signal misplaced responsibilities); ② move one import inside the function that needs it (lazy — hides the smell, acceptable for genuinely optional/heavy deps); ③ import the module not names (import a + a.name at call time — works if use happens post-init).

python pkg/mod.py` vs python -m pkg.mod (know cold).

python pkg/mod.pypython -m pkg.mod (from root)

Rule: run multi-file projects from the root with -m + absolute imports. The script-path form is for single-file scripts only.

16.7 Interview questions

Q1: Module vs package? What's __init__.py for? What goes in it?
Module = one .py file (a namespace). Package = directory of modules under a dotted name, marked by __init__.py (runs on first import of anything inside). Keep it tiny: __version__, curated re-exports, __all__ — never heavy compute/side effects (they'd run at import time for every importer).
Q2: What does `if __name__ == "__main__"` do and why is it mandatory in dual-purpose files?
Direct runs set __name__ = "__main__"; imports set it to the module name. The guard confines script behavior (arg parsing, prints, exits) to direct execution, keeping imports side-effect-free (fast, test-safe). Without it: imports trigger I/O/prompts/exits — breaking tests and library use.
Q3: How does Python find imports? Name the shadowing failure and its diagnosis.
Order: sys.modules cache → script dir → PYTHONPATH → site-packages (venv!) → stdlib. Shadowing: your random.py hijacks stdlib random (script dir is first!) → bizarre AttributeErrors. Diagnose: print(mod.__file__) — your folder = shadowed. Never name files after oms, and the three fixes ranked.
Mechanism: a→b→a sees a half-initialized module in sys.modules (names missing) → ImportError/AttributeError. Fixes: ① restructure (shared code → third module — the real fix), ② lazy function-level import, ③ module-not-names import + deferred attribute use. Cycles signal misplaced responsibilities — treat as design feedback.

16.8 Exercises

Level 1 · Understand
  1. Print sys.path from a script vs REPL vs -m; identify path[0] in each and explain the differences.
  2. Build a 2-file project (lib with 2 functions + guarded demo; script importing it). Show import-silence vs direct-run output.
  3. Plant a shadowing bug (statistics.py in cwd importing stdlib statistics elsewhere); diagnose via __file__; fix by renaming.
Level 2 · Apply
  1. Reproduce a circular import; read the traceback precisely (which name is missing where?); fix by extracting a shared module.
  2. Convert a flat 100-line script into the §16.4 layout (package + tests + guard + -m runs). All behavior identical, imports absolute.
  3. Write a package __init__.py with version + curated re-export + __all__; demonstrate import pkg; pkg.name working.
Level 3 · Interview
  1. Explain sys.modules caching consequences: import-time side effects, why reload is fiddly, and how singletons-via-module work (and their test-isolation downside).
  2. Design lazy/optional imports for a heavy dependency (e.g., matplotlib only when plotting): function-level vs TYPE_CHECKING vs try/except-ImportError with helpful message. Argue trade-offs.
