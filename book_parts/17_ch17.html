Scale & ecosystem

Virtual Environments and Package Management

▾

What/why. Real projects depend on external packages with conflicting version needs (Project A requires Pandas 1.5's behavior; Project B needs Pandas 2.0's). Installing everything into one global Python = dependency hell: upgrading for B silently breaks A ("but it worked yesterday!"). A virtual environment is an isolated, per-project Python setup (own interpreter link + own site-packages); pip installs packages into the active environment; a requirements file records exact versions so anyone (teammate, CI, future-you) can recreate the setup bit-for-bit. No venv = not reproducible = not professional. This chapter makes isolation reflexive.

Why versions conflict in practice. Libraries evolve: bug fixes (safe), features (safe-ish), breaking changes (removed args, renamed methods, new defaults — Pandas 2.0's copy-on-write changed mutation semantics!). Your code pins to behavior you tested; the global upgrade moves the floor. Venvs freeze each project's floor independently. Bonus isolation: system Python protection — your OS uses its Python for itself; sudo pip install once broke Ubuntu upgrades famously (Debian now blocks it entirely — PEP 668's "externally managed" error, which is the OS begging you to use a venv).

17.2 The daily workflow (memorize this sequence)

venv lifecycle: create → activate → verify → install → freeze → recreate 
# 1. CREATE (once per project, at project root):
python -m venv .venv
# 2. ACTIVATE (every NEW terminal — activation is per-shell!):
# macOS/Linux (bash/zsh):   source .venv/bin/activate
# Windows cmd:               .venv\Scripts\activate.bat
# Windows PowerShell:        .venv\Scripts\Activate.ps1
# 3. VERIFY you are INSIDE it (prompt shows (.venv) — trust, but verify):
python -c "import sys; print(sys.executable)"
# .../myproj/.venv/bin/python  ← path MUST contain .venv!
pip install --upgrade pip            # fresh venvs ship old pip — upgrade first
# 4. INSTALL what you need:
pip install pandas matplotlib requests
# 5. FREEZE exact versions (the reproducibility contract):
pip freeze > requirements.txt
# 6. RECREATE anywhere (teammate/CI/new machine):
python -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt
# 7. LEAVE when done:
deactivate

Step-by-step (what activation actually does). Surprisingly little: it prepends .venv/bin (or Scripts) to your shell's PATH and tweaks the prompt. That's it — python/pip now resolve to the venv's copies (which point sys.path at the venv's site-packages). Deactivation restores PATH. Consequences: activation is per-terminal (new tab = reactivate!); scripts with absolute venv paths (.venv/bin/python job.py) don't need activation at all (preferred for cron/schedulers — explicit beats ambient).

What lives inside .venv/. bin/ (python symlinks, pip, activate scripts), lib/pythonX.Y/site-packages/ (your installs + pip's metadata), pyvenv.cfg (base interpreter pointer). Size: ~20MB empty, 100MB–2GB with data stacks. It's disposable by design: corrupted? rm -rf .venv + recreate from requirements.txt (2 minutes) beats debugging it (2 hours). Never commit .venv/ (gitignore it — it's binary-heavy and machine-specific); commit requirements.txt + the Python version.

17.3 pip: installing precisely (specifiers, upgrades, inspection)

pip command map 
pip install requests                 # latest compatible release
pip install "pandas==2.2.2"          # EXACT pin (quotes guard < > from shells!)
pip install "numpy>=1.24,<2"        # compatible range (library-style)
pip install -r requirements.txt      # bulk install from file
pip install -e .                     # EDITABLE: install THIS project (src/ layout dev!)
pip install --upgrade pandas         # bump within constraints (then RE-FREEZE!)
pip show pandas                      # version, location, requires (which venv? check!)
pip list                             # everything installed here
pip list --outdated                  # upgrade candidates (upgrade deliberately, test after)
pip check                            # dependency CONFLICTS? (run after installs!)
pip cache purge                      # reclaim disk (wheels cached in ~/.cache/pip)

Specifier semantics (PEP 440, the working set). ==2.2.2 exact · >=2.0,<3 range (comma = AND) · ~=2.2 compatible-release (≈ >=2.2,<3 — same major) · no specifier = latest (fine for experiments, never for committed files). pip's resolver backtracks across transitive deps — conflicts surface as loud errors (better than silent breakage!) or pip check findings. When resolution fails: pin the top-level combatants explicitly and let the rest follow.

⚠️ pip trapspip vs python mismatch (different installs!) → always python -m pip … (§1.11). Installing outside any venv (global litter) → verify sys.executable first. --upgrade without re-freeze (teammates still on old pins — drift!). Upgrading one package breaking another (run pip check + test suite after every upgrade). sudo pip (system-Python surgery — PEP 668 now refuses; use venvs or pipx for CLI tools).

17.4 requirements discipline: pins for apps, ranges for libraries

requirements.txt (apps/analyses: EXACT pins) 
# requirements.txt — generated: pip freeze (then REVIEW: keep direct deps, note why)
# App/analysis contract: reproduce MY exact setup, bit for bit.
numpy==1.26.4
pandas==2.2.2
matplotlib==3.8.4
python-dateutil==2.9.0.post0     # transitive (pulled by pandas/matplotlib) — pinned anyway!
# Verify after install:
# python -c "import pandas, numpy, matplotlib; print(pandas.__version__, numpy.__version__)"

Apps pin exactly; libraries range-pin. An app/analysis ("run MY code identically") freezes every transitive dep (pip freeze output, reviewed). A library ("work inside OTHERS' setups") declares compatible ranges in pyproject.toml (pandas>=2.0,<3) — exact pins in libraries cause conflicts for downstream users. Hybrid pro move: requirements.in (direct deps, ranges, human-edited) compiled to requirements.txt (full transitive freeze) via pip-tools — intent + reproducibility, both.

The reproducibility stack (full honesty). Bit-identical reproduction needs: ① Python version (3.12.4 — record in README/.python-version), ② pinned direct deps, ③ pinned transitive deps (lockfile!), ④ OS/arch-compatible wheels (Linux/macOS/Windows builds differ — CI matrix!), ⑤ seeds + config for stochastic code (random.seed/stable — Ch. 25). requirements.txt covers ②–③; Docker covers ④; discipline covers ①/⑤. Modern lockers (uv, Poetry, PDM) automate ②–③ with uv.lock/poetry.lock — same principle, stronger guarantees. (Conda/environment.yml is the parallel universe for non-Python binaries — same isolation idea.)

17.6 Interview questions

Q1: Why virtual environments? Precisely what breaks without them?
Isolation per project (own interpreter-link + site-packages) so dependency versions can't collide across projects or with system Python. Without: upgrading for B breaks A (dependency hell), system tools break (sudo pip), and setups can't be recreated ("works on my machine"). Venv + pinned requirements + recorded Python version = reproducibility. Recreate-cost is ~2 minutes, so venvs are disposable.
Q2: requirements.txt vs pyproject.toml vs lockfiles — who pins what?
requirements.txt (pip freeze): exact transitive pins — app/analysis reproducibility. pyproject.toml dependencies: compatible ranges — library compatibility declarations. Lockfiles (uv.lock/poetry): exact transitive pins + hashes, generated from ranges — both intent and reproducibility. Full stack adds Python version + OS + seeds.
Q3: `pip install X` succeeded but `import X` fails. Diagnose in order.
① pip↔python mismatch (different installs!) — use python -m pip always. ② Wrong venv active (or none) — check sys.executable vs install target (pip show X → Location). ③ Name ≠ import (pip scikit-learn imports as sklearn; Pillow → PIL). ④ Shadowing (§16.2) — print(X.__file__).

17.7 Exercises

Level 1 · Understand
  1. Create a venv; activate; prove sys.executable points inside; install one package; pip freeze; deactivate; delete; recreate from the file. Time the recreate.
  2. Show pip show pandas Location differing between two venvs; explain what activation changed to cause it (echo $PATH before/after).
Level 2 · Apply
  1. Run two venvs with different versions of one package; run the same version-printing script in each. Write the README + .gitignore you'd ship.
  2. Break a venv deliberately (upgrade one package into a pip check conflict); resolve by pinning; document the conflict + resolution.
Level 3 · Interview
  1. Compare venv+pip vs uv vs conda on: speed, lock strength, non-Python binaries, disk layout. Recommend one per scenario (solo analysis, team app, GPU/geo stack).

17.8 Mini-challenge 🏆

Challenge

Harden a project. Take any multi-file script: add venv + requirements.txt (frozen, reviewed) + .gitignore + README 3-command setup + a check_env.py asserting (python version, key package versions, cwd-independent imports). Delete your venv, hand the folder to someone (or a fresh terminal), and go green from README alone. If it fails, the README is wrong — fix the README, not the human.
