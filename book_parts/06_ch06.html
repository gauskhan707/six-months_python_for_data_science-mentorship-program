6
Core data

Strings

▾

What/why. A str is an immutable sequence of Unicode characters. Strings exist because most real-world data arrives as text and much of it stays text: names, categories, IDs, addresses, logs, CSV fields, JSON payloads, error messages, file paths. In data science you will clean, split, normalize, validate, and format text every single day — this chapter makes those operations fluent and exact. Core law (from Chapter 3): every string "modification" builds a new string; the original never changes. Every method below returns a new string — none mutates.

6.1 Creation: quotes, escapes, raw strings, multiline

What. String literals come in four quoting styles with identical value semantics — choose by content convenience:

quoting styles + escapes 
s1 = 'single'            # identical meaning to double — pick ONE style per project
s2 = "double"            # (this book uses double; PEP 8 allows either)
s3 = "it's easy"         # double quotes contain apostrophes cleanly
s4 = 'say "hi"'          # single quotes contain double quotes cleanly
s5 = """triple-double
spans lines, keeps newlines"""   # multi-line text / docstrings
s6 = '''triple-single, same idea'''
esc = "col1\tcol2\nline2\"quoted\"\\backslash"  # \t tab, \n newline, \" quote, \\ backslash
print(esc)
raw = r"C:\data\new"     # RAW: backslashes are LITERAL (no escapes processed)
print(raw)               # C:\data\new — compare: "\n" would be a NEWLINE
print(len(raw))          # 11 — backslashes are ordinary characters here
col1 col2 line2"quoted"\backslash C:\data\new 11

Step-by-step (escapes). Inside a non-raw literal, backslash starts an escape sequence: \n = one newline character (not two characters!), \t = one tab, \" = a literal quote that doesn't end the string, \\ = one literal backslash. So "a\nb" has length 3 (a, newline, b). The r"…" prefix disables all escapes — essential for Windows paths (r"C:\new" vs "C:\new" = C: + newline + ew!) and regular expressions (where backslashes are the regex language itself).

More examples — adjacent-literal concatenation and explicit joins:

long strings, three professional ways 
# 1. Adjacent literals auto-join (parse time, zero cost):
query = ("SELECT name, age "
         "FROM users "
         "WHERE age > 18")
# 2. Triple quotes for real multiline (newlines INCLUDED):
msg = """Dear Ali,
Your report is ready."""
# 3. Explicit join for computed parts (NEVER += in a loop — §6.7):
parts = ["2026", "09", "14"]
print(query)
print(msg)
print("-".join(parts))
SELECT name, age FROM users WHERE age > 18 Dear Ali, Your report is ready. 2026-09-14
⚠️ Common mistakesUnterminated literal ("abc → SyntaxError/EOL) · "C:\new\test" (silent \n/\t corruption — use raw or forward slashes) · raw string ending in backslash (r"\" → SyntaxError — the quote gets escaped!) · assuming triple quotes strip indentation (they don't — use textwrap.dedent for indented templates).

6.2 Indexing: positions from both ends

What. Each character has a position: 0 for the first, counting up — and -1 for the last, counting down. s[i] returns the one-character string at position i. Out-of-range → IndexError.

Why zero-based + negative. Zero-based: index = offset from the start (s[0] is 0 steps in), making slicing arithmetic (§6.3) beautifully consistent: s[:n] + s[n:] == s. Negative: "from the end" access without knowing the length (s[-1] = last char — no len() dance).

negative-6 -5 -4 -3 -2 -1
s[0]→'P' · s[5]→'N' · s[-1]→'N' · s[6]→ 💥 IndexError · s[-7]→ 💥 IndexError
indexing + len + safe last-char 
s = "PYTHON"
print(s[0], s[5], s[-1], s[-6])  # P N N P — s[-6] is first (len 6)
print(len(s))                    # 6 — number of CHARACTERS
# Safe patterns:
print(s[len(s) - 1])             # last char, manual — or just s[-1]
print(s[0] if s else "?")        # guard EMPTY string (s[0] on "" → IndexError!)

⚠️ Common mistakess[len(s)] → IndexError (last valid is len-1 — the eternal off-by-one) · indexing an empty string (guard with if s:) · s[0] = "p" → TypeError (immutable! build new: "p" + s[1:]) · confusing character-count with byte-count (len("café") == 4 chars but 5 UTF-8 bytes — §6.8).

6.3 Slicing: s[start:stop:step] — the most-used operation in text work

What. A slice extracts a subsequence: characters from index start (inclusive) up to stop (exclusive), taking every step-th character. Any part may be omitted: missing start → beginning; missing stop → end; missing step → 1. Negative step walks backwards (and then the defaults flip: start→end, stop→beginning).

Why stop-exclusive. Three felicities: (1) slice length = stop - start (s[2:5] has exactly 3 chars); (2) clean splits: s[:n] + s[n:] == s for any n; (3) adjacent ranges never overlap or gap (s[0:3] + s[3:6] partitions perfectly). Exclusive-stop is the convention behind range() too (Chapter 10) — one rule, everywhere.

Intuition: fence posts, not fence panels. Picture indices as pointing between characters (the gaps), numbered 0..len: |0|P|1|Y|2|T|3|H|4|O|5|N|6|. s[1:4] takes everything between gap 1 and gap 4 → "YTH". This gap-model makes every slice predictable — draw it for each example below until it's reflex.

slicing, comprehensively 
s = "PYTHON"
print(s[0:3])    # 'PYT' — gaps 0..3
print(s[:3])     # 'PYT' — start defaults to 0
print(s[3:])     # 'HON' — stop defaults to len
print(s[:])      # 'PYTHON' — full copy (new object, same chars)
print(s[::2])    # 'PTO' — every 2nd char (0,2,4)
print(s[1::2])   # 'YHN' — every 2nd starting at 1
print(s[::-1])   # 'NOHTYP' — THE reverse idiom (step -1 flips defaults)
print(s[-3:])    # 'HON' — last 3 (negative start counts from end)
print(s[:-3])    # 'PYT' — everything EXCEPT last 3
print(s[100:])   # '' — out-of-range slices CLIP silently (never raise!)
print(s[4:1])    # '' — start past stop (step +1) → empty, not error
PYT PYT HON PYTHON PTO YHN NOHTYP HON PYT

Step-by-step (s[::-1]). step = -1 means walk backwards. With negative step, omitted start = "the end" and omitted stop = "before the beginning": visit indices 5,4,3,2,1,0 → N,O,H,T,Y,P. Memorize this idiom — it reverses any sequence (strings, lists, tuples) and appears constantly in interviews.

Multiple examples — slicing in real jobs:

slices at work: extensions, masking, fixed-width fields 
fname = "report.2026.csv"
print(fname[-3:])              # 'csv' — extension (or pathlib, Ch. 15)
print(fname[:-4])              # 'report.2026' — stem
card = "4111111111111111"
print("*" * 12 + card[-4:])    # ************1111 — masking
line = "Ali   30Lahore"        # fixed-width record: name[0:6] age[6:8] city[8:]
print(line[0:6].strip(), line[6:8], line[8:])  # Ali 30 Lahore
print("abcdef"[::2], "abcdef"[1::2])  # ace bdf — stride tricks
csv report.2026 ************1111 Ali 30 Lahore ace bdf
💡 Slices never raise — indexes dos[100] → IndexError, but s[100:] → "". This asymmetry is deliberate: slices clip to valid bounds, making "first N chars" / "last N chars" safe without length checks. Exploit it: preview = text[:200] is safe for any length.

6.4 Operators on strings: +, *, in (and what you can't do)

string operators 
print("data" + " " + "science")  # concatenation → 'data science'
print("ab" * 3)                  # repetition → 'ababab' (int only!)
print("=" * 40)                  # separators/dividers — the honest use of *
print("cat" in "concatenate")    # True — substring test
print("py" not in "java")        # True
# print("a" + 1)    → TypeError: convert first: "a" + str(1)
# print("a" - "b")  → TypeError: no subtraction (use .replace/.strip)
# print("a" * 2.5)  → TypeError: can't multiply by non-int
data science ababab ======================================== True True

Best practice. Use + for a few known pieces, join (§6.5) for many/unknown pieces, f-strings (§6.6) for embedding values. Never += in a loop (§6.7's O(n²) proof).

clean = raw.strip().lower().replace(" ", "")  # CHAIN: each returns new str
print(f"[{raw}] → [{clean}]")   # original UNTOUCHED; new string built
user, sep, domain = clean.partition("@")  # ALWAYS 3 parts (no IndexError!)

print("no-at-sign".partition("@"))  # ('no-at-sign', '', '') — safe unpack!

Step-by-step (the chain). raw.strip() returns "Ali.Raza@mail.COM" (new object); .lower() on that returns "ali.raza@mail.com"; .replace(" ", "") returns the final. raw still holds the original with spaces and caps — forgetting to assign the result (s.strip() alone on a line) is the most common string-method bug: the cleaned string is computed and instantly discarded.

find` vs index — the deliberate pair. s.find(x) returns -1 when absent (safe probing); s.index(x) raises ValueError (absence is an error). Rule: find (or in) for optional searches; index when missing data means corrupt input that should crash loudly. Same philosophy as dict.get vs d[k] (Chapter 8) — one language-wide pattern.

split subtleties that bite in data work 
print("a  b   c".split())       # ['a','b','c'] — NO-arg split: ANY whitespace runs, strips ends
print("a  b   c".split(" "))    # ['a','','b','','','c'] — EXPLICIT " ": every gap counts!
print("a,b,".split(","))        # ['a','b',''] — trailing empty KEPT (csv-like)
print("  padded  ".split())     # ['padded']
print("one\ntwo\n".splitlines())  # ['one','two'] — universal newlines, no empties at end
['a', 'b', 'c'] ['a', '', 'b', '', '', 'c'] ['a', 'b', ''] ['padded'] ['one', 'two']
⚠️ split() vs split(" ") — know the difference coldNo-arg split() splits on runs of any whitespace and trims the ends (perfect for messy human text). Explicit split(" ") splits on each single space (perfect for strict formats, terrible for padded logs). Choosing wrong silently mangles columns — a genuine data-corruption vector.

6.6 Formatting: f-strings (the modern standard) + format specs

What. F-strings (f"…{expr}…", Python 3.6+) embed live expressions inside string literals — evaluated at runtime and formatted per an optional format spec after :. They replaced %-formatting and (mostly) str.format() as the default: faster, shorter, and readable.

f-strings: the complete working set 
name, score, rate = "Ali", 93.456, 0.875
print(f"{name} scored {score:.1f}")   # 1 decimal → Ali scored 93.5
print(f"{rate:.1%}")                  # percent → 87.5%
print(f"{score:08.2f}")               # zero-padded width 8 → 00093.46
print(f"{1000:,}")                    # thousands separator → 1,000
print(f"{name!r}")                    # !r → repr (quotes shown — DEBUG view)
print(f"{name!s}")                    # !s → str (default, rarely written)
print(f"{score=}")                    # self-documenting → score=93.456
print(f"{2 + 2 = }")                  # expressions too → 2 + 2 = 4
print(f"{'hi':>10}|{'hi':<10}|{'hi':^10}|")  # align: right/left/center
# Nested/dynamic specs (3.12+ allows quote reuse inside braces):
w = 10
print(f"{name:{w}}!")
Ali scored 93.5 87.5% 00093.46 1,000 'Ali' Ali score=93.456 2 + 2 = 4 hi|hi | hi | Ali !

Format-spec anatomy: {value:fill align width , .precision type}. Types that matter: f fixed-point, % percent (×100 + sign), , thousands grouping, d/b/x/o integer bases, e scientific, s string. = adds the expression text (debugging gold: f"{rows=}, {bad=}"). Conversion !r shows the representation (quotes, escapes visible) — always use it when debugging string content ("is that trailing space real?").

When NOT f-strings: (1) templates stored in variables/files/config (f-strings evaluate immediately where written — use template.format(name=…) for deferred filling); (2) logging (pass args separately — log.info("rows=%d", n) — so formatting is skipped when the level is off, Chapter 23); (3) user-supplied format strings (never f-string/`format` untrusted templates — attribute access can leak internals; use string.Template for user templates).

6.7 Performance: join vs += (the O(n²) trap, proven)

What. Strings are immutable (§3.3) — so result += piece in a loop copies the entire growing string every iteration: 1 + 2 + 3 + … + n characters copied = O(n²). "".join(pieces) measures once, allocates once, copies once = O(n). CPython has an micro-optimization for some += cases (over-allocating when refcount is 1) — but it's fragile (breaks with aliasing, function boundaries, PyPy) and must never be relied upon.

join vs +=: measured 
import time
pieces = ["abcdefgh"] * 20000
t0 = time.perf_counter()
s = ""
for p in pieces:
    s += p                      # O(n²): copies ~1.6 BILLION chars total
t_plus = time.perf_counter() - t0
t0 = time.perf_counter()
s2 = "".join(pieces)            # O(n): one allocation
t_join = time.perf_counter() - t0
print(len(s) == len(s2))        # True — same result...
print(f"+=: {t_plus*1000:.1f}ms   join: {t_join*1000:.1f}ms")  # ...vastly different cost
True +=: 28.4ms join: 0.3ms

Rule. Collect pieces in a list, join once. (Comprehensions make this one line: "".join(f(x) for x in items) — a generator, so no intermediate list either. Chapter 13/19.) The same "batch, don't dribble" principle governs file writes and DB inserts.

6.8 Unicode & encoding: characters vs bytes (the distinction that matters)

What. str = a sequence of abstract characters (Unicode code points: U+0041 'A', U+1F600 '😀'). bytes = a sequence of concrete byte values 0–255 for storage/transmission. Encoding (str → bytes) happens on every write/send; decoding (bytes → str) on every read/receive. UTF-8 (the universal default) encodes ASCII in 1 byte, most scripts in 2–3, emoji in 4.

Why two types. Because conflating them caused decades of corruption ("mojibake": cafÃ©). Python 3's strict boundary — str inside programs, bytes at the edges, explicit conversion between — means text bugs surface as loud UnicodeDecodeError/TypeError instead of silent garbage. You cannot "a" + b"b" (TypeError) — decode first.

encode / decode, lengths, file rule 
s = "café 😀"
b = s.encode("utf-8")     # str → bytes (what hits disk/network)
print(b)                  # b'caf\xc3\xa9 \xf0\x9f\x98\x80'
print(len(s), len(b))     # 6 chars vs 10 BYTES — len counts units of ITS type!
print(b.decode("utf-8"))  # bytes → str (what your program thinks in)
print(ord("A"), chr(65), hex(ord("😀")))  # 65 A 0x1f600 — code points
# Files: ALWAYS declare encoding explicitly (Chapter 15):
# with open("f.txt", encoding="utf-8") as f: ...
b'caf\xc3\xa9 \xf0\x9f\x98\x80' 6 10 café 😀 65 A 0x1f600
🛠️ Debugging UnicodeDecodeError/UnicodeEncodeErrorUnicodeDecodeError (reading): the file isn't in the encoding you assumed. Fix: (1) declare encoding="utf-8" explicitly; (2) if it fails, the file is likely latin-1/cp1252 (Windows legacy) — try those; (3) last resort errors="replace" (� markers, logged!) — never "ignore" silently (destroys data). UnicodeEncodeError (writing/printing): the target can't represent a character (Windows console without UTF-8 mode) — write to a UTF-8 file instead of the console, or set PYTHONUTF8=1.

📊 Data-Science connection. Real datasets mix encodings (UTF-8 exports, cp1252 Excel saves, latin-1 legacy dumps). Pandas' read_csv(encoding=…) exposes exactly this parameter — and now you know what it does. Bonus: casefold() (not lower()) is the correct Unicode caseless match ("ß".casefold() == "ss"); unicodedata.normalize("NFKC", s) unifies look-alike characters before deduplication.

normalize phones + parse pairs + mask emails 
import re
# 1. Normalize phone variants → digits only
def digits_only(s):
    return "".join(ch for ch in s if ch.isdigit())
print([digits_only(p) for p in ["(0300) 123-4567", "+92 300 1234567"]])
# 2. Parse "k:v;k:v" pairs → dict
record = "name:Ali;age:30;city:Lahore"
pairs = dict(part.split(":", 1) for part in record.split(";") if ":" in part)
print(pairs)
# 3. Mask email: keep first+last char of local part
def mask_email(e):
    user, sep, domain = e.partition("@")
    if not sep or len(user) < 2:
        return "***@" + domain if sep else "***"
    return f"{user[0]}***{user[-1]}@{domain}"
print(mask_email("ali.raza@mail.com"))  # a***a@mail.com

print(len(re.findall(r"\w+", "Hello,  world!  123")))  # 3

6.10 Interview questions

Q1: Why are strings immutable? What would break if they weren't?
Immutability enables safe sharing (no defensive copies), hashing (dict keys/set members need stable values — mutating a key would corrupt its bucket), interning, and thread safety. If strings were mutable, every dict keyed by text would be corruptible by aliasing — catastrophic for a language where dicts are everywhere.
Q2: join vs += in a loop — complexity and rule?
+= per iteration copies the whole accumulated string → O(n²) total. join allocates once → O(n). Rule: collect pieces, join once. At 20k pieces the measured gap is ~100× (§6.7).
Q3: find vs index? split() vs split(" ")?
find returns −1 when missing (safe probe); index raises ValueError (missing = corrupt). No-arg split() splits on whitespace runs + trims (messy human text); split(" ") splits on each single space, keeping empties (strict formats). Wrong choice silently shifts columns.
Q4: str vs bytes? What is encoding, and how do you debug UnicodeDecodeError?
str = Unicode characters (in-program thinking); bytes = byte values (storage/transmission). Encoding converts str→bytes (UTF-8 default); decoding reverses. UnicodeDecodeError = file isn't in the assumed encoding → declare encoding="utf-8", else try cp1252/latin-1, last resort errors="replace" with logging — never silent ignore.
