Design

Object-Oriented Programming

▾

What/why — from absolute zero. As programs grow, bare functions + dicts sprawl: which dicts have which keys? which functions may touch them? what states are legal? OOP answers by bundling data (attributes) + allowed operations (methods) into objects stamped from classes (blueprints). Four payoffs: encapsulation (valid states enforced in one place — invalid objects unmakeable), abstraction (callers use simple methods, never internals), inheritance (shared behavior written once), polymorphism (interchangeable parts behind one interface). You've used objects all book long ("hi".upper(), [1].append(2), df.head()) — now you learn to design them. (Python is multi-paradigm: OOP + functions + data — use each where it fits, §18.8.)

18.1 Your first class: __init__, self, attributes, methods (line by line)

Account: the complete minimal class 
class Account:
    """A tiny bank account. Balances never go negative (enforced!)."""

    def __init__(self, owner, balance=0):  # CONSTRUCTOR: runs at Account(...)
        if balance < 0:                       # validate AT BIRTH (encapsulation!)
            raise ValueError("balance can't be negative")
        self.owner = owner                # ATTRIBUTE: data living ON the instance
        self.balance = balance            # self.x = "this object's x" (per-instance!)

    def deposit(self, amount):            # METHOD: function bound to instances
        if amount <= 0:
            raise ValueError("deposit must be positive")
        self.balance += amount            # mutate THIS object's state
        return self.balance               # return new balance (composable!)

    def __repr__(self):                   # developer view (REPL, logs, debugging)
        return f"Account({self.owner!r}, {self.balance!r})"

a = Account("Ali", 100)   # INSTANTIATE: allocate + __init__(a, "Ali", 100)
b = Account("Zara")       # SEPARATE object, own attributes (balance=0 default)
print(a)                  # Account('Ali', 100) — __repr__ used
print(a.deposit(50))      # 150 — a.deposit(50) ≡ Account.deposit(a, 50) (!)
print(a.balance, b.balance)  # 150 0 — independent state ✓
print(a.owner)            # attribute READ (no call — data, not action)
Account('Ali', 100) 150 150 0 Ali

Step-by-step (Account("Ali", 100)). ① Python allocates a blank instance object. ② Calls __init__(new_obj, "Ali", 100) — self is the new object (passed automatically, first position). ③ Body validates + stores owner/balance on the instance (in its attribute dict — inspect via vars(a)). ④ The now-initialized object is returned and bound to a. b = Account("Zara") repeats independently — two objects, two attribute dicts, zero sharing.

self`, precisely (the #1 beginner confusion). self is not magic — just the conventional name for the instance, passed automatically when you call obj.method(args) (rewritten as Class.method(obj, args)). Inside methods: self.x = this object's stored state (persists between calls); bare x = a local variable (dies at return). Forget self in the signature → TypeError (method called with 1 arg, defined with 0 — the instance still passed!). Forget self. on assignment → you made a local, state lost. Class-body assignments (species = "human") are class attributes — shared across instances (§18.2's trap).

18.2 Class attributes vs instance attributes (+ the mutable-class-attr trap)

shared vs per-instance state 
class Dog:
    species = "Canis familiaris"   # CLASS attribute: ONE copy, shared by ALL dogs
    def __init__(self, name):
        self.name = name           # INSTANCE attribute: per-dog
        self.tricks = []           # ✅ mutable state in __init__ (per-instance!)

d1, d2 = Dog("Rex"), Dog("Tom")
print(d1.species, d2.species)      # shared read ✓
d1.tricks.append("roll")           # touches ONLY d1's list
print(d1.tricks, d2.tricks)        # ['roll'] [] ✓
Dog.species = "C. familiaris"      # change on CLASS → visible via ALL instances
print(d2.species)
d1.species = "wolf?!"              # ⚠️ assignment on INSTANCE → SHADOWS (class untouched!)
print(d1.species, d2.species, Dog.species)  # wolf?! C. familiaris C. familiaris

class BrokenTeam:
    members = []                   # ❌ MUTABLE CLASS ATTRIBUTE — shared trap!
    def __init__(self, name):
        self.name = name
    def join(self, who):
        self.members.append(who)   # mutates THE CLASS'S list (no instance list exists!)
t1, t2 = BrokenTeam("a"), BrokenTeam("b")
t1.join("x")
print(t2.members)  # ['x'] — LEAKED across teams! (Fix: self.members = [] in __init__)
Canis familiaris Canis familiaris ['roll'] [] C. familiaris wolf?! C. familiaris C. familiaris ['x']

Lookup rule (read vs write asymmetry). Read obj.attr: instance dict → class → parent classes (MRO — §18.5) → AttributeError. Write obj.attr = v: always the instance dict (shadowing any class attr of that name!). Mutate obj.attr.append(x): reads (finds class's list!) then mutates in place — no rebinding, so the shared object changes. Hence: class attributes for constants/defaults shared intentionally (immutable!); ALL mutable/per-object state in __init__.

18.3 Encapsulation: privacy conventions + validating properties

What. Encapsulation = the object guards its own validity: construction validates (__init__ raises on garbage), mutation funnels through methods/properties that re-validate. Python's privacy is by convention, not enforcement: _x = "internal, don't touch from outside" (still accessible — we're adults); __x = name-mangled to _Class__x (anti-collision for inheritance, not security — §18.5).

@property: validation with attribute syntax. Start with plain attributes; when validation/computation is needed, upgrade to a property without changing any caller (obj.x reads/writes identically) — the killer feature vs Java-style getters/setters.

Temperature: validated + computed properties 
class Temperature:
    def __init__(self, celsius):
        self.celsius = celsius          # routes through the SETTER (validates at birth!)

    @property
    def celsius(self):                  # READ: t.celsius (no parens — looks like data!)
        return self._celsius

    @celsius.setter
    def celsius(self, value):           # WRITE: t.celsius = v (validates EVERY time!)
        if value < -273.15:
            raise ValueError("below absolute zero")
        self._celsius = value           # real storage: _-conventional "private"

    @property
    def fahrenheit(self):               # COMPUTED, read-only (no setter → assign raises!)
        return self._celsius * 9/5 + 32

t = Temperature(25)
print(t.celsius, t.fahrenheit)  # 25 77.0
try:
    t.celsius = -300            # invalid states UNMAKEABLE — the setter refuses!
except ValueError as e:
    print("rejected:", e)       # rejected: below absolute zero
# t.fahrenheit = 32             # 💥 AttributeError: can't set attribute (read-only!)
25 77.0 rejected: below absolute zero

Step-by-step (t.celsius = -300). Assignment to a data descriptor (property with setter) invokes the setter function with (t, -300) instead of touching the instance dict → validation raises → _celsius untouched (still 25). Reads invoke the getter. Callers keep simple obj.x syntax forever — this is why Python needs no getters: start simple, armor later, break nothing.

18.4 staticmethod, classmethod, and alternate constructors

three method kinds, each justified 
class Temperature2:
    def __init__(self, celsius):
        self.celsius = celsius

    def doubled(self):                  # INSTANCE method (default): needs SELF state
        return Temperature2(self.celsius * 2)

    @staticmethod
    def c_to_f(c):                      # STATIC: no self/cls — pure utility, namespaced here
        return c * 9/5 + 32

    @classmethod
    def from_fahrenheit(cls, f):        # CLASS method: gets the CLASS — alt CONSTRUCTOR
        return cls((f - 32) * 5/9)      # cls(...) respects SUBCLASSES (hardcoded name wouldn't!)

    @classmethod
    def from_kelvin(cls, k):
        return cls(k - 273.15)

t = Temperature2.from_fahrenheit(98.6)  # reads as English: "temperature FROM fahrenheit"
print(t.celsius, Temperature2.c_to_f(0))  # 37.0 32.0
class Sub(Temperature2): pass
print(type(Sub.from_fahrenheit(32)))     # Sub — cls preserved inheritance ✓ (hardcode would give Temperature2!)
37.0 32.0 <class '__main__.Sub'>

When each. Instance methods: behavior needing object state (default — 90%). @staticmethod: stateless utility that belongs to the concept's namespace (c_to_f lives with temperatures). @classmethod: needs the class itself — alternate constructors (from_csv, from_json, from_fahrenheit), inherited-friendly factories, class-level polymorphism. Interview one-liner: "instance = self, static = neither, class = cls".

18.5 Inheritance, polymorphism, super(), and MRO

What. Inheritance: class CsvReader(Reader) — CsvReader is-a Reader, gaining its interface + implementation, overriding what differs. Polymorphism: code written against the base (def load_all(reader: Reader, …)) works with any subclass — interchangeable parts. super() calls the next implementation up the chain (extend, don't replace). MRO (Method Resolution Order — Class.__mro__, C3 linearization) defines the lookup chain for multiple inheritance.

Reader hierarchy + polymorphism + super() 
class Reader:                                   # BASE: defines the INTERFACE
    def read(self, path):
        raise NotImplementedError("subclasses implement read()")

class CsvReader(Reader):                        # IS-A Reader (inheritance)
    def read(self, path):
        return f"rows from {path}"              # OVERRIDE (specialize)

class JsonReader(Reader):
    def read(self, path):
        return f"object from {path}"

def load_all(reader: Reader, paths):            # POLYMORPHISM: ANY Reader works here
    return [reader.read(p) for p in paths]

print(load_all(CsvReader(), ["a.csv"]))         # ['rows from a.csv']
print(isinstance(CsvReader(), Reader))          # True — substitutable ✓

class LoggedCsvReader(CsvReader):               # extend WITHOUT rewriting:
    def read(self, path):
        print(f"[log] reading {path}")
        return super().read(path)               # super() = CsvReader.read here
print(load_all(LoggedCsvReader(), ["b.csv"]))
print(LoggedCsvReader.__mro__)                  # (Logged, Csv, Reader, object) — lookup chain!
['rows from a.csv'] True [log] reading b.csv ['rows from b.csv'] (<class '__main__.LoggedCsvReader'>, <class '__main__.CsvReader'>, <class '__main__.Reader'>, <class 'object'>)

Design rules (the judgment part). ① Inherit for is-a (CsvReader is a Reader); compose (hold a helper: self.reader = CsvReader()) for has-a/uses-a — composition beats tangled hierarchies (favor it by default!). ② Keep hierarchies shallow (2–3 levels; deep trees = fragile base-class problem). ③ super().__init__(…) in subclass constructors (extend parent init, don't silently skip it). ④ Prefer duck typing ("if it has .read(path), it's a reader") over isinstance chains — Python's polymorphism is behavioral, not nominal. (Abstract bases (abc.ABC + @abstractmethod) enforce the interface at instantiation — use when the contract must be unbreakable.)

⚠️ Inheritance trapsForgetting super().__init__ (parent state never built — AttributeErrors later) · overriding without matching signature (Liskov violation — substitutability breaks) · multiple inheritance diamonds (MRO usually saves you, but need for MI often signals composition would fit) · __x name-mangling across inheritance (_Class__x — subclass __x is a different attr, by design anti-collision).

18.6 Dunder methods: teaching objects Python's verbs

What. Dunder (double-underscore) methods hook your classes into Python's syntax and builtins: define __len__ and len(obj) works; __getitem__ → obj[k]; __iter__ → for x in obj; __eq__ → ==; __add__ → +. This is how list/dict/str themselves work — you're extending the language, not fighting it.

Playlist: len, getitem, iter, contains, eq, add 
class Playlist:
    def __init__(self, name, songs=()):
        self.name, self.songs = name, list(songs)
    def __repr__(self):                       # UNAMBIGUOUS dev view (REPL/logs) — ALWAYS define!
        return f"Playlist({self.name!r}, {self.songs!r})"
    def __str__(self):                        # pretty human view (print/str) — optional
        return f"{self.name} ({len(self)} songs)"
    def __len__(self): return len(self.songs) # len(p) ✓
    def __getitem__(self, i): return self.songs[i]  # p[0], p[1:] ✓ (slices free!)
    def __iter__(self): return iter(self.songs)     # for s in p ✓
    def __contains__(self, s): return s in self.songs  # "x" in p ✓
    def __eq__(self, o):                      # p1 == p2 (value equality!)
        return isinstance(o, Playlist) and (self.name, self.songs) == (o.name, o.songs)
    def __add__(self, other):                 # p1 + p2 → merged NEW playlist
        return Playlist(f"{self.name}+{other.name}", self.songs + other.songs)

p = Playlist("gym", ["a", "b"])
print(p)                 # __str__: gym (2 songs)
print(repr(p))           # __repr__: Playlist('gym', ['a', 'b'])
print(len(p), p[0], "a" in p, [s.upper() for s in p])
print(p + Playlist("run", ["c"]))  # merged (3 songs)
gym (2 songs) Playlist('gym', ['a', 'b']) 2 a True ['A', 'B'] gym+run (3 songs)

__repr__` vs __str__ (exact). repr(): unambiguous, developer-facing (REPL echo, logs, containers' contents, tracebacks) — goal: "paste it back to rebuild" (Playlist('gym', ['a','b'])). str(): pretty, user-facing (print, f-strings) — goal: readable. Fallback: str without __str__ uses __repr__. Rule: always define __repr__ (debugging depends on it); add __str__ when humans read it. (__eq__ without __hash__ makes instances unhashable — define both or neither (§8.4's contract); dataclasses automate this — §18.7.)

18.7 dataclasses: records without boilerplate (+ when NOT to use them)

dataclass: __init__/__repr__/__eq__ generated 
from dataclasses import dataclass, field

@dataclass                 # generates __init__, __repr__, __eq__ from annotations!
class Point:
    x: float
    y: float
    label: str = "origin"   # default allowed (immutable defaults fine)

p, q = Point(1, 2), Point(1, 2)
print(p)                    # Point(x=1, y=2, label='origin') — free repr!
print(p == q)               # True — VALUE equality, free!

@dataclass
class Team:
    name: str
    members: list = field(default_factory=list)  # ✅ mutable default done RIGHT (fresh per instance)
t1, t2 = Team("a"), Team("b")
t1.members.append("x")
print(t1.members, t2.members)  # ['x'] [] — independent ✓ (vs §18.2's trap!)

@dataclass(frozen=True)    # IMMUTABLE record (hashable! dict keys!)
class FrozenPoint:
    x: float
    y: float
print(hash(FrozenPoint(1, 2)) is not None)  # True
# fp = FrozenPoint(1,2); fp.x = 5 → FrozenInstanceError (frozen = unchangeable)
Point(x=1, y=2, label='origin') True ['x'] [] True

When dataclasses (vs plain class vs NamedTuple vs dict). Dataclass: mutable-or-frozen records with behavior + validation (__post_init__ validates!). Plain class: complex lifecycles, rich polymorphism, heavy encapsulation. NamedTuple: tiny immutable records, tuple-compatible. Dict: dynamic/schemaless JSON-ish bags. Rule of thumb: fixed schema known at write time → dataclass (catches typos via attributes, documents shape via annotations, equality/repr free).

✅ Data-Science connection (OOP pays off here)Scikit-learn's API is OOP: estimators are objects with .fit(X, y)/.predict(X) (polymorphism — swap models without rewriting pipelines; Pipeline composes them). Datasets → dataclasses; pipelines → classes with .run(); custom transformers → subclasses of base estimators (inheritance done right). Learn OOP now; every ML library reads as prose later.

18.8 Interview questions

Q1: Class vs instance vs instance-attribute vs class-attribute? The mutable trap?
Class = blueprint (methods live here, shared). Instance = object built from it. Instance attrs (self.x, in __init__) = per-object state. Class attrs (body-level) = shared across instances. Trap: mutable class attr (members = []) is ONE list mutated via all instances — reads find it (lookup chain), .append mutates in place. Fix: initialize mutables in __init__ (or field(default_factory=…)).
Q2: What is self, exactly? What breaks without it?
self = the instance, passed automatically as the first arg on obj.method(…) calls (Class.method(obj, …)). Without it in the signature: TypeError (instance still passed, nowhere to land). self.x = persistent per-object state; bare x = dying local. It's convention (any name works) but universal — renaming it is a readability crime.
Q3: @staticmethod vs @classmethod vs instance method — with the cls-inheritance proof?
Instance: needs self state (default). static: neither — namespaced utility. class: receives cls — alternate constructors + inherited factories. Proof: Sub.from_x(…) returns Sub via cls(…); a hardcoded ClassName(…) would wrongly return the parent (§18.4 demo).
Q4: Inheritance vs composition — when each? What is polymorphism in Python (duck typing)?
Inherit is-a (CsvReader is a Reader), shallow (2–3 levels), super().__init__ to extend. Compose has-a/uses-a (pipeline has a reader — injected, swappable). Default to composition. Polymorphism: uniform interface, interchangeable implementations — in Python, behavioral (duck typing: "has .read(path)" suffices) rather than nominal; abc enforces contracts when required.
Q5: __str__ vs __repr__? __eq__/__hash__ contract?
__repr__: unambiguous dev view (REPL/logs/containers) — always define. __str__: pretty human view (print) — optional (falls back to repr). Defining __eq__ without __hash__ sets __hash__ = None (unhashable!) — equal objects must hash equal (§8.4); define both, neither, or freeze (dataclass frozen=True/eq babysits this).

18.9 Exercises

Level 1 · Understand
  1. Counter class (inc/dec/reset/value + __repr__); prove obj.method(x) ≡ Class.method(obj, x) by calling both forms.
  2. Add a validated @property (reject bad values with messages); show birth-validation + set-validation + read-only computed property.
  3. Reproduce the mutable-class-attr trap with id() proof; fix two ways (__init__, dataclass default_factory).
Level 2 · Apply
  1. Dataset class: rows (list of dicts) + filter(pred) (chainable, returns Dataset!) + column(name) + __len__/__iter__/__getitem__ + head(n). Chain two filters.
  2. Convert a 3-field record class to @dataclass (+ __post_init__ validation + one computed property + frozen=True variant as dict key).
  3. Playlist-style dunders on your Dataset: ==, + (concat), in (row membership). Argue each dunder's semantics.
Level 3 · Interview
  1. Design Reader ABC (abc) + CSV/JSON subclasses + DataPipeline(reader, steps) via composition (injected reader, swappable steps). Defend every inheritance-vs-composition choice in comments a reviewer would respect.
  2. Implement __eq__ + __hash__ by hand for a small value class; prove dict/set correctness; then show the dataclass one-liner equivalent. When would you still hand-roll? (Hint: normalization, casefold, tolerance.)
